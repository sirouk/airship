# Inference providers and agent model-awareness

> **Archived:** moved under `docs/archive/` during the provider-neutral simplification. This file is historical context only and is not normative. See [`../../SIMPLIFICATION.md`](../../SIMPLIFICATION.md) and the living docs in `docs/` for the current contract.

**Verdict.** The provider layer is one of the most genuinely-built parts of Airship, and it is honestly labeled — but the "multi-provider, OAuth-preferred, model-aware agent" promise is roughly 55% real. Chutes is the only provider wired truly end-to-end and proven live: cpk_/cak_ bearer -> /v1/models discovery -> E2EE `POST api.chutes.ai/e2e/invoke` with per-instance nonce -> decrypted OpenAI SSE -> real streamed tool calls (src/inference/chutes/transport.ts:248-340, openai.ts:23-195), with an opt-in live gate (transport.live.test.ts). OpenAI (Responses), Anthropic (Messages, with the required `anthropic-dangerous-direct-browser-access` header), xAI (Responses) and Ollama/LM Studio (OpenAI-compatible loopback) all have complete, bounded, cancellable, tool-call-capable transports (browser-cloud.ts:114-438, local/openai-transport.ts:80-209) — every one supports real function calling — but none of the three cloud vendors has ever been run against its real endpoint (no live gate exists; e2e/provider-fabric-acceptance.spec.ts and fabric.test.ts stub the transport), and I found a concrete payload defect that would 400 the mandatory activation probe for all three. On OAuth: I probed the real Chutes IdP and it publishes `token_endpoint_auth_methods_supported: [...,"none"]`, `code_challenge_methods_supported: ["plain","S256"]`, and `access-control-allow-origin: *` on both /idp/authorize and /idp/token — so production browser PKCE is genuinely possible today and the client code is already written; it is simply not configured, so every static build falls back to "paste a cpk_". For OpenAI/Anthropic/xAI, consumer OAuth from a static browser app is factually unavailable (no third-party client registration exists for any of them; ChatGPT/Claude-Code sign-in are first-party product flows), and the repo says exactly that — that honesty should stay. Agent awareness is real but shallow: `inspect_inference_connections` is registered into the live tool registry (app.tsx:1472-1504) and returns the live cross-provider roster, and a creation-time roster is baked into the immutable system prompt (operating-charter.ts:86-113) — but the agent sees only model id + modalities + coarse features, never context window, max output, price, or availability trend, and for OpenAI/Anthropic every model reports "capabilities-unknown" because those directories carry no capability fields and nothing fills the gap. Switching is per-session, not per-turn: it takes one dropdown click, does not require a profile revision (bindProfileToRuntime is a deliberate no-op), but always starts a brand-new session with an empty transcript (fork is `historyCopied: false`), so "on-the-fly switching" in the sense the user means does not exist. Finally, the generic registry's entire OAuth apparatus — `connectOAuth`, the public-PKCE gate, `createChutesProviderDescriptor` — is dead code referenced only by tests, so the registry's documented "Chutes is mirrored into the generic registry" integration has not actually happened.

## 1. OpenAI/Anthropic/xAI sessions run with context compression completely disabled because no context window is ever discovered
`cloud-no-context-window` · kind **inert** · effort **medium**

**Evidence.** src/inference/providers/browser-cloud.ts:178-208 (OpenAI/xAI) and :328-355 (Anthropic) build `InferenceModelDescriptor`s that never set `contextWindowTokens` or `maxOutputTokens` — the fields exist in contracts.ts:153-154 and model-catalog.ts:145-169 validates them, but no cloud code path populates them. src/ui/app.tsx:4978-4991 `contextPolicyForProviderModel` returns `undefined` when `!model.contextWindowTokens`, so `createProfileSessionManifest` pins no `contextPolicy`. src/core/agent.ts:169-171: `const pinnedContextCompression = session.manifest.contextPolicy ? ... : undefined` and :178 `const contextSummary = pinnedContextCompression ? await planContextCompression(...) : ...` — no policy means no compression, ever, for the life of that session. Chutes and local providers do get a policy (app.tsx:4952-4976 from `AirshipModel.contextTokens`; local/catalog-adapter.ts:84 from Ollama `/api/show` model_info and LM Studio `max_context_length`). Anthropic additionally runs with a hardcoded `max_tokens: 8192` (browser-cloud.ts:111,373,704-709).

**Impact.** A long OpenAI or Anthropic conversation never summarizes and simply grows until the vendor returns a context-length 400, with no Airship-side warning, while the identical conversation on Chutes or Ollama compresses correctly. Anthropic replies are also silently capped at 8k output tokens regardless of the model's real limit.

**Fix.** Do NOT add a model-name/family capability table; it is explicitly forbidden by docs/PROVIDER_FABRIC.md:23 invariant 5 and the comments at src/core/agent.ts:167-168 and src/core/context-policy.ts:12, and would be rejected on the honesty contract. Build the honest paths instead:

1) Operator-declared window (primary, fully browser-feasible). Add an optional per-model context-window / max-output override to the connection surface in src/ui/provider-connections-view.tsx (near the MenuSelect at :296-310) and persist it into the model row through the fabric so the descriptor for that row carries contextWindowTokens/maxOutputTokens with row-level `source: { kind: "manual", observedAt }` (src/inference/providers/contracts.ts:155-159; already validated by model-catalog.ts:145-169 and labelled "Manual metadata" at provider-connections-view.tsx:534). Do not touch `capabilities` — MODEL_CAPABILITIES (contracts.ts:11-22) has no context-length member and ModelCapabilityEvidence carries no number.

2) Honest session provenance. src/ui/app.tsx:4978-4990 contextPolicyForProviderModel currently stamps `{ kind: "provider-catalog", field: "contextTokens" }` unconditionally. It must branch: keep provider-catalog only when the number came from a provider directory, and emit `{ kind: "runtime-config", label: "operator-declared context window" }` for a manual value — that variant is already accepted by canonicalContextWindowSource (src/core/context-policy.ts:173-182) and SessionContextPolicy (src/core/contracts.ts:96-99), so no contract change is needed.

3) Per-request Anthropic cap, not per-transport. Transports are per-connection and constructed at connect time before any model is selected (src/inference/fabric.ts:158-162 staging, :202-206 committed, cached in #transports by connection id and reused by preflight at :434 for every model), so BrowserCloudTransportOptions.maxOutputTokens (browser-cloud.ts:35,111,842-844) cannot be per-model. Either add an optional maxOutputTokens to InferenceRequest (src/core/contracts.ts:179-188), sourced from the pinned session manifest/route, or pass a `(modelId) => number | undefined` resolver into BrowserCloudTransportOptions, and consume it in buildAnthropicPayload (browser-cloud.ts:702-717).

4) Fix the 8192 default, which is a live bug and not merely a silent cap. Anthropic rejects max_tokens above a model's limit with HTTP 400, and its /v1/models directory still lists 4096-max-output models, so every turn on those models fails today. When no declared value exists, the unconfigured default at browser-cloud.ts:111 must not exceed the smallest limit Anthropic will accept for a listed model (i.e. lower it), or the request must be driven by a declared/probed value.

5) Surface the unknown (CANON 3.5: missing capability stays visibly unavailable rather than simulated). When activateExternalInference (app.tsx:3660-3700) resolves contextPolicy === undefined, the connection card and runtimeStatus must state that context compression is unavailable because no context window was declared for this model. Today nothing in src/ui mentions compression at all.

6) Optional live-probe upgrade: Anthropic's 400 bodies declare the real max-output and prompt limits, but browser-cloud.ts request() currently discards error bodies via discardBounded (:277, :428). Reading a bounded error body there would allow recording the value with `source.kind: "live-probe"` instead of "manual"; treat this as a follow-on, not a prerequisite.

Regression coverage: extend src/inference/providers/browser-cloud.test.ts (which already exercises the Anthropic max_tokens path at :136,:173) to assert an operator-declared value flows through per model, and add an app-level test that a cloud route with a declared window pins a runtime-config contextPolicy while an undeclared one both pins nothing and raises the unavailable-compression notice.

## 2. Switching model or provider always starts an empty conversation; there is no way to continue the current thread on a different model
`no-mid-conversation-switch` · kind **clunky** · effort **large**

**Evidence.** All three switch paths end by replacing the transcript: src/ui/app.tsx:3626-3630 (Chutes model switch) `setMessages([{...welcomeMessage, content: "<model> is active in a new pinned session..."}])`; :3711-3716 (external provider/model activation) the same; :3402-3435 (new Chutes connection). Each calls `createProfileSession(candidateRuntime, ...)` which mints a fresh manifest via `createProfileSessionManifest` (:4834-4880). The explicit fork path cannot help: src/sessions/library.ts:43 and :172 hardcode `historyCopied: false`, and src/ui/app.tsx:3979-3993 `activateForkedSession` also resets `setMessages([...welcomeMessage...])`. `bindProfileToRuntime` (app.tsx:5210-5216) is a deliberate no-op, so switching does NOT require a new profile revision — it is per-session, never per-turn. `SessionLibrary.fork` already accepts `request.manifest` (library.ts:136) but app.tsx:1856-1859 never passes one.

**Impact.** The user's requirement of 'on-the-fly switching' with an agent that 'routes appropriately' is unmet: you can switch in one click, but you lose the working conversation and must re-explain the task to the new model. Cheap-model-for-grunt-work / strong-model-for-hard-parts — the core reason to hold several providers at once — is impossible today.

**Fix.** Ship a context-carrying fork, but scope it correctly -- it is more than the two files the auditor named, because the provider request is rebuilt exclusively from journal events, so a UI-only carry would be theater.

1) src/sessions/library.ts: add forkWithRoute(sourceId, {manifest, carryContext, expectedSourceHead, sourcePoint}). The manifest plumbing already exists (:136); what is new is that after journal.createSession (:165) it appends one out-of-turn genesis event (type "context.transferred") whose payload holds the bounded canonicalized prior messages plus {sourceSessionId, sourceHeadSequence, sourceHeadDigest, transcriptDigest}, reusing the bounds in materializeSessionMessages (20k events / 500 messages / 512 KiB). Relax the literal type historyCopied: false (:43, :172) to a discriminated "carried" | "none" so the flag stays honest rather than becoming a lying boolean.

2) src/core/agent.ts: teach materializeMessages (:667-754) to emit the carried messages as the transcript prefix, exactly where the context.summary.updated projection is spliced in today (:687-691). Without this the new model never sees the carried thread.

3) src/core/session-audit.ts: add "context.transferred" to KNOWN_EVENT_TYPES (:35-56) -- unknown types currently raise EVENT_TYPE_UNKNOWN (:629-637) -- and give it a validation arm modeled on the context.summary.updated arm (:663+): must be sequence 2, outside any turn, payload digest must match the manifest.lineage commitment written at library.ts:138-145, and it must never claim receipts or posture from the source session.

4) src/sessions/domain.ts: render the carried prefix in materializeSessionMessages and mark those rows as ancestor-provenance so assessSessionHistory does not read them as turns produced under this pin.

5) src/ui/app.tsx: route switchChutesModel (:3536) and activateExternalInference (:3645) through the new fork instead of createProfileSession + setMessages([welcomeMessage]) (:3626-3631, :3715-3720), and do the same for activateForkedSession (:3979-3993) when carry is requested. Render a non-dismissable "carried from <session> at seq N -- produced by <prior model>, not by <new model>" divider.

Two costs the auditor did not budget: (a) charter v6 (src/core/operating-charter.ts:10-23) tells the model the thread is pinned to exactly one provider/model, so it needs a sentence describing carried ancestor context -- which bumps AIRSHIP_CORE_CHARTER_VERSION and therefore every newly resolved system-prompt digest; (b) carrying provider A's outputs into a provider B request is a real cross-provider data transfer and should be an explicit user choice (opt-in toggle on the model control), not the silent default.

## 3. The agent's model roster carries no context window, output limit, or price, and OpenAI/Anthropic models report zero capabilities
`agent-model-metadata-thin` · kind **inert** · effort **medium**

**Evidence.** src/inference/providers/contracts.ts:257-263 — the per-model row in `InferenceAvailabilityConnection` is exactly `{id, label, availability, supportedCapabilities}`; contextWindowTokens/maxOutputTokens exist on `InferenceModelDescriptor` (:153-154) but are dropped by `createInferenceAvailabilitySnapshot` (session-route.ts:168-178). The prompt projection drops even more: operating-charter.ts:86-113 emits only `id [input=...;features=...]`. src/inference/providers/browser-cloud.ts:765-769 `openAiUnknownCapabilities()` returns `Object.freeze({})` and Anthropic hardcodes `capabilities: Object.freeze({})` (:341), so those rows render as `capabilities-unknown`. Chutes model rows do carry rich metadata — pricing, contextTokens, tags, telemetry (src/models/types.ts:109-138) — and `selectModel` genuinely ranks on trust/availability/price/context (src/models/domain.ts:166-230), but that ranking is used only once, at connect time in src/ui/access-view.tsx:182,322; it never reaches the agent or any per-turn routing. `"tool-calling"` is consumed only for UI labels and prompt facets (app.tsx:5072,5172; provider-connections-view.tsx:37) and never gates a request payload.

**Impact.** An agent asked to 'use the cheap model for this' or 'pick something with a big context window' has no data to do it, and on OpenAI/Anthropic it cannot even tell whether a model supports tools or vision. The prompt's model list is close to a bare ID list, so 'agent model-awareness' is nominal.

**Fix.** Carry declared model metadata across all four hops (the auditor's version skips one hop and would throw on the proposed facet syntax):

1. src/inference/providers/contracts.ts:257-263 — extend the availability model row with optional `contextWindowTokens?: number`, `maxOutputTokens?: number`, and `pricing?: Readonly<{usdPerMillionInput?: number; usdPerMillionOutput?: number; authority: "llm-models"|"chutes-management"|"mixed"}>`. Omit `pricing` entirely when `ModelTokenPricing.authority === "unavailable"` (fail closed rather than emit a zero).

2. src/inference/providers/session-route.ts:168-178 — copy `model.contextWindowTokens` / `model.maxOutputTokens` through. CORRECTION: `InferenceModelDescriptor` (contracts.ts:143-158) has NO pricing field, so pricing cannot come "from the descriptor" as proposed. Either add `pricing?` to the descriptor and populate it only in adapters that actually publish prices, or keep pricing exclusive to the Chutes path in step 3. Today only src/inference/local/catalog-adapter.ts:84 sets contextWindowTokens (from Ollama `.context_length` / LM Studio `max_context_length`); browser-cloud.ts never does, which is the sibling `cloud-no-context-window` finding.

3. src/ui/app.tsx:5066-5083 (inside `combinedInferenceAvailability`; the "5064-5100" range in the finding also covers unrelated connection fields) — map `model.contextTokens ?? model.maxModelTokens`, `model.maxOutputTokens`, and `model.pricing.input.usdPerMillion` / `model.pricing.output.usdPerMillion` (TokenUnitPrice, src/models/types.ts:55-66) onto the new fields, gated on `pricing.authority !== "unavailable"`.

4. MISSING HOP the auditor skipped: src/ui/app.tsx:5164-5183 (`inferenceDirectoryFromAvailability`) and src/core/operating-charter.ts:42-46 (`InferenceModelPromptDefinition`). Editing the emitter alone changes nothing — the prompt definition type has no context/price fields today, so both must gain them before operating-charter.ts can render them.

5. src/core/operating-charter.ts:96-105 — append bounded facets. CORRECTION: `in$=3.00` as literally proposed would throw, because `$` fails both `promptToken` (:141-147, `^[A-Za-z0-9][A-Za-z0-9._:/+@-]{0,255}$`) and `promptFacet` (:149-155, `^[a-z0-9][a-z0-9._+-]{0,63}$`). Use facet-safe keys and a dedicated numeric guard (Number.isSafeInteger / Number.isFinite plus an upper bound, mirroring the existing modelCount check at :92-94) rather than routing numbers through promptFacet, e.g. `ctx=200000;out=64000;usd-in=3.00;usd-out=15.00`.

6. Tests: src/inference/providers/provider-registry.test.ts:409-432 asserts the snapshot and prompt projection; the added fields are optional so extend rather than rewrite. Also note `renderInferenceAvailabilityForPrompt` (session-route.ts:234-268) is referenced only by that test — the live prompt path is inferenceDirectoryFromAvailability -> composeAirshipOperatingPrompt (src/profiles/domain.ts:360), so fixing only the renderer would be invisible in production.

Browser feasibility: confirmed. All values are already resident in page memory (Chutes catalog via src/models/parser.ts, local models via the local adapters); no new network call or server. AIRSHIP_CORE_CHARTER stays byte-stable, so only newly created sessions get new prompt digests and existing pins replay their stored bytes unchanged.

## 4. No live gate exists for OpenAI, Anthropic or xAI, so their browser CORS and wire behavior are asserted, never proven
`no-live-cloud-provider-gate` · kind **absent** · effort **medium**

**Evidence.** The only live inference gate is src/inference/chutes/transport.live.test.ts:11-14 (`CHUTES_TEST_API_KEY`). `grep -rln 'OPENAI_API_KEY|ANTHROPIC_API_KEY|XAI_API_KEY|AIRSHIP_OPENAI...'` over the repo returns nothing. src/inference/providers/browser-cloud.test.ts drives a stub fetch; e2e/provider-fabric-acceptance.spec.ts drives the UI with injected connections (:61,90-95); e2e/local-inference-product-journey.spec.ts:49-94 intercepts loopback with `page.route`. docs/MASTER_PROMPT_ACCEPTANCE.md line 33 correctly downgrades 'no mocks in the critical path' to Conditional for exactly this reason. Meanwhile the code makes provider-specific bets that only a live call can settle: xAI is streamed against `${origin}/v1/responses` (browser-cloud.ts:222) although its declared catalog route is the xAI-specific `/v1/language-models` (:101), and Anthropic depends on `anthropic-dangerous-direct-browser-access: true` (:421) being honored for the caller's org.

**Impact.** Three of the five advertised providers have never executed a real request. Any of them could be broken today (see the empty-tools finding) and every test would still pass, so the acceptance ledger's Conditional status can never be promoted.

**Fix.** Two gates, because a Node test cannot prove browser CORS and claiming otherwise would break the honesty contract.

1. Wire/protocol gate (Node): add src/inference/providers/browser-cloud.live.test.ts in the shape of src/inference/chutes/transport.live.test.ts:11-14, with one env-gated describe per vendor -- `const openai = process.env.AIRSHIP_OPENAI_API_KEY?.trim(); const describeOpenAi = openai ? describe : describe.skip;` and likewise AIRSHIP_ANTHROPIC_API_KEY / AIRSHIP_XAI_API_KEY plus AIRSHIP_{OPENAI,ANTHROPIC,XAI}_MODEL, matching the naming convention already used by LIVE_ACCEPTANCE_ENVIRONMENT in scripts/release-live.mjs. Construct the real OpenAiBrowserTransport / AnthropicBrowserTransport / XaiBrowserTransport from src/inference/providers/browser-cloud.ts with the platform fetch (no vi.fn) and assert: (1) listModels() length > 0 and source.sourceUrl equals the vendor's declared catalog route -- this is what settles the xAI /v1/language-models (:101) vs /v1/responses (:222) split; (2) a tools: [] stream() reaches a `completed` event -- the case fabric.ts's connect path leaves as invoke: {state:"unknown"}; (3) a with-tools stream() yields a `tool-call` event. Scope the claim explicitly in the file header: Node/undici performs no CORS enforcement, so this proves protocol only.

2. Browser reachability gate: add e2e/live-cloud-providers.spec.ts plus a playwright.live-cloud.config.ts cloned from playwright.live.config.ts (vite preview of the built artifact on a fixed 127.0.0.1 origin, screenshot/trace/video off so the memory-only credential is never recorded), modeled on e2e/live-chutes-vision.spec.ts: enter a disposable key in the connect UI and complete one streamed turn per vendor. The successful authenticated streamed response from a real cross-origin page IS the CORS proof, including the preflight that x-api-key / authorization / anthropic-version force; a denial surfaces as the fetch TypeError that normalizeFetchFailure() reports as "network, provider, or CORS".

Do NOT assert `response.headers.get("access-control-allow-origin")` as the auditor proposed. Access-Control-Allow-Origin is not a CORS-safelisted response header and is not exposed by default, so a browser always returns null; and in Node, undici sends no Origin header and issues no preflight, so most vendors omit ACAO entirely and the assertion would fail while the browser path works fine. It proves nothing in either runtime.

Wire both as additional optional stages in scripts/release-live.mjs (not scripts/release-gate.mjs, which is the static-artifact gate) -- skipped when the vendor key is absent, so the Chutes gate stays green. Then amend docs/MASTER_PROMPT_ACCEPTANCE.md line 33 to actually name OpenAI/Anthropic/xAI among the providers whose gates are outstanding (it currently names only Google, semantic-model, WASIX, WebContainer and Chutes) and cross-link docs/PROVIDER_FABRIC.md:73-88 as the weaker dated manual-probe evidence that these gates supersede.

## 5. Local providers are locked to four hardcoded loopback origins and the UI never tells the user the exact CORS setting to change
`local-endpoint-allowlist-and-cors-guidance` · kind **clunky** · effort **medium**

**Evidence.** src/inference/local/endpoint-policy.ts:23-28 `DEFAULT_LOCAL_MODEL_ORIGINS` is exactly `127.0.0.1:11434`, `localhost:11434`, `127.0.0.1:1234`, `localhost:1234`; :67-73 rejects any other origin outright, and index.html:13 `connect-src` lists only those four, so a user running Ollama on a non-default port (`OLLAMA_HOST=:11500`) or a second LM Studio instance simply cannot connect. Discovery and streaming themselves are real (ollama.ts:33-131 `/api/version` + `/api/tags` + concurrent `/api/show`; lm-studio.ts:52-78 `/api/v1/models` with `/api/v0/models` fallback; local/openai-transport.ts:80-209 real SSE + tool calls). The failure mode is diagnosed honestly (endpoint-policy.ts:115-129 `cors-or-private-network-access`, :77-83 mixed-content info) but the UI guidance is one generic sentence: src/ui/provider-connections-view.tsx:230 'Your browser and local service must allow this Airship origin through CORS and browser local-network access.'

**Impact.** From an https deployment, Ollama's default origin allowlist and Chromium's local-network-access gating will block the probe, and the user is told only that 'CORS' failed — not that they need `OLLAMA_ORIGINS=https://<their-airship-origin>` (or the LM Studio server CORS toggle), and not that Airship is only ever going to try port 11434/1234. Two of the user's requested providers will look broken to most people running the hosted build.

**Fix.** Two parts; part 1 is the high-value one and is independently shippable.

(1) Diagnostic-driven remediation block (no security surface touched). In src/ui/provider-connections-view.tsx, keep safeProviderErrorMessage as-is (it truncates at 320 chars at :506, so do NOT append guidance to it). Instead add a separate remediation state: in run() at :92-96, when `caught instanceof LocalProviderError && caught.diagnostic.code === "cors-or-private-network-access"`, also store the provider id, and render a copyable block next to the error at :241 computed from `location.origin` — for Ollama: `OLLAMA_ORIGINS=<origin> ollama serve` (plus `OLLAMA_HOST` note); for LM Studio: the developer-tab "Enable CORS" / "Serve on local network" toggles; plus a line that Chromium may require a local-network-access permission prompt for an https page reaching loopback. LocalProviderError is already exported from src/inference/local/index.ts (via ./endpoint-policy), and fabric.ts connectLocal rethrows the original error, so no plumbing change is needed. Add a case to src/ui/provider-connections-view.test.ts asserting the remediation text is derived from location.origin and is not emitted for other diagnostic codes.

(2) Port flexibility must stay wildcard-free. Do NOT use `http://localhost:* http://127.0.0.1:*` — scripts/check-static-security.mjs:24-27 and scripts/release-gate.mjs:967-971 throw on any "*" in connect-src. Instead enumerate a small explicit set of extra loopback origins (e.g. 11434-11436 and 1234-1236 on both localhost and 127.0.0.1) as exact origins, added identically to index.html:13 AND public/_headers:2 (check-static-security.mjs:17 requires the two policies to serialize identically apart from frame-ancestors), and to DEFAULT_LOCAL_MODEL_ORIGINS at endpoint-policy.ts:23-28. Leave the loopback-host check at :60-65 and validateAllowedOrigin at :87-113 untouched. Then update endpoint-policy.test.ts:12 (currently pins http://localhost:7777 as a throw) to a port still outside the widened set, expose the chosen port via the existing `options.endpoint` path that ollama.ts:25 / lm-studio.ts:24 already accept, and update docs/LOCAL_MODEL_PROVIDERS.md ("custom-port hosts are rejected ... only ... ports 11434 and 1234") so the documented boundary still matches the code. If the enumerated set is judged too coarse, ship part (1) alone and have the remediation block state plainly that Airship only probes the listed ports, which is strictly more honest than today's text.

## 6. Signing out of Chutes drops page memory but never revokes the refresh token the IdP is still honoring
`no-oauth-token-revocation` · kind **absent** · effort **small**

**Evidence.** src/auth/chutes-credential-broker.ts:194-197 `clear()` only calls `#replaceState(undefined)`; :349-356 wipes the in-memory record and aborts any refresh task. Nothing in src/auth/ references a revocation call (`grep -rn revoke src/auth` finds only `#retiredRefreshTokenDigests` and abort plumbing). The live Chutes discovery document I fetched publishes `revocation_endpoint: https://api.chutes.ai/idp/token/revoke`, and the production registration is configured for `refreshTokenLifetimeDays: 30` (chutes-oauth.ts:82).

**Impact.** After a user signs out — or on a shared/kiosk device — a refresh token that leaked via XSS or an extension stays valid at the provider for up to 30 days, even though the UI states the session is gone. It is a quiet gap between what sign-out claims and what it does.

**Fix.** Add `revokeChutesToken({ token, tokenTypeHint, clientId, signal, fetch, registration })` to src/auth/chutes-oauth.ts, next to refreshChutesOAuthToken. Mirror the existing endpoint switch at chutes-oauth.ts:2-5: post to "https://api.chutes.ai/idp/token/revoke" in production and to a new same-origin dev route in DEV, reusing the requestTokenSet fetch policy (method POST, application/x-www-form-urlencoded body of token/token_type_hint/client_id, cache "no-store", credentials "omit", redirect "error", referrerPolicy "no-referrer", AbortSignal.timeout of a few seconds), and validate the token with the existing validateToken("crt_", ...)/parseChutesCredential guards so a malformed value is never sent. Because the checked-in localhost registration is confidential (chutes-oauth.ts:37), extend scripts/local-chutes-oauth-bridge.ts with a second route (e.g. "/__airship/chutes/oauth/revoke" -> "https://api.chutes.ai/idp/token/revoke") that adds the process-held secret and allows only the fields token, token_type_hint, client_id; browser JS must still never hold the secret.

Call it from the real sign-out path, not from the unwired broker: in src/ui/app.tsx, inside releaseChutesAuthority() at line 3488, capture `const releasedTokens = oauthTokens.current;` before line 3505 sets it to undefined, then after all synchronous teardown completes fire a detached best-effort `void revokeChutesToken({ token: releasedTokens.refreshToken, tokenTypeHint: "refresh_token", ... }).then(() => revokeChutesToken({ token: releasedTokens.accessToken, tokenTypeHint: "access_token", ... }))` guarded by `connection.kind === "chutes-oauth"` (skip for cpk_ API keys, which have no revocation grant). releaseChutesAuthority must stay synchronous and must not retain the token beyond that closure, so teardown never waits on or is blocked by the network.
