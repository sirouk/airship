# Real multi-language shell (Bash, Python, Rust, JS, WASI)

> **Archived:** moved under `docs/archive/` during the provider-neutral simplification. This file is historical context only and is not normative. See [`../../SIMPLIFICATION.md`](../../SIMPLIFICATION.md) and the living docs in `docs/` for the current contract.

**Verdict.** The WASI Preview 1 runner is the strongest, most under-used asset in this repo: I compiled a real `std` Rust program to `wasm32-wasip1` with the installed toolchain and ran it against the exact configuration in `src/execution/wasi-preview1-worker.ts:43-90` (one `PreopenDirectory(".")`, empty-file stdin, two `ConsoleStdout` fds), and it worked completely — argv, environ, `current_dir`, relative/`./`/absolute path resolution into the preopen, `read_to_string`, `write`, `rename`, `copy`, `remove_file`, `create_dir`/`remove_dir_all`, append, seek + partial overwrite, truncate, `metadata`, `read_dir`, a 1 MiB file, realtime clock, separated stdout/stderr, and `exit(7)` propagated faithfully. Only `std::process::Command` failed ("operation not supported"), which is correct: WASI p1 has no process API. Implemented syscalls (from `@bjorn3/browser_wasi_shim@0.4.2` `dist/wasi.js` + `fs_mem.js`): args/environ, `clock_res_get`/`clock_time_get` (realtime+monotonic), the full `fd_*` set including `fd_readdir`, `fd_pread`/`fd_pwrite`, `fd_seek`/`fd_tell`, `fd_filestat_*`, `fd_renumber`, `path_open`/`path_create_directory`/`path_filestat_get`/`path_link`/`path_unlink_file`/`path_remove_directory`/`path_rename` (composed from unlink+link), `proc_exit`, `random_get`, `sched_yield`. Stubbed or hostile: `path_symlink`/`path_readlink` → `ERRNO_NOTSUP`; all four `sock_*` → `throw "sockets not supported"`; `proc_raise` throws a raw string; `poll_oneoff` accepts exactly one *clock* subscription and implements it as a **busy spin loop**, so `sleep` burns a core. So yes — precompiled `wasm32-wasip1` binaries genuinely run over the Airship workspace with args/env/stdout/stderr/exit-code and revision-checked writeback (the e2e gate at `e2e/browser-worker.spec.ts:81-175` proves the same with a `no_std` fixture). What is missing is not the runner: it is (a) any way to *get a binary in* other than the model emitting megabytes of base64 in a tool argument, and (b) stdin, which is hardcoded to an empty file. That makes a real capability practically inert. On the shell question: option (a) (WASIX/Wasmer) depends on a third-party runtime bug you cannot fix locally — though the recorded status `45` is exactly `ERRNO_NOEXEC`, which points at a failed nested-atom exec rather than mis-propagated Bash status and deserves one more 20-minute diagnostic before it is written off; option (d) (BrowserPod/CheerpX) is correctly rejected on licensing/keying. The winner is a **two-tier build on machinery you already own**: ship a real POSIX-sh interpreter in TypeScript that executes over `WorkspacePort` with real streaming pipes, redirection, globbing and exit codes as the universal tier (works on Safari/mobile, no cross-origin isolation, and can expose Airship's own Git/Python/WASI as commands), and then a Rust busybox-style multicall `airship-sh` compiled to `wasm32-wasip1` and shipped as a pinned same-origin asset — my probe proves the existing WASI runner already provides every syscall that shell needs, and an optimized `std` Rust binary was 91 KB, so the 4 MiB artifact budget is not the constraint. In-browser `rustc` is genuinely impossible and should stay `Unavailable`; "compile elsewhere, run here" is the honest ceiling and you already have the pipeline (`scripts/build-dcap-qvl-wasm.sh`, `scripts/pyodide-assets.ts`, digest list in `scripts/release-gate.mjs:125-129`). Python snapshot/writeback is real and byte-safe in both directions (`decodeWorkspaceBytes` in, `encodeWorkspaceBytes` out, `Uint8Array` across postMessage), but three things break it: the job timeout starts *before* the CPython cold boot with a 10 s hard ceiling, the egress path is missing the control-plane/excluded-segment guard that WASI and WASIX both have, and any over-budget generated file discards the entire result including a successful exit code. Cancellation is real, not cosmetic, in every runtime I checked: JS worker, WASI, and Pyodide all `worker.terminate()` a dedicated worker (a hard thread kill that stops synchronous wasm mid-execution — the WASI e2e cancel gate proves it against an infinite spin loop), WebContainer calls `process.kill()` and the terminal writes a real `\x03`, and the unpromoted WASIX pack terminates its tracked child-worker tree with a 1 s fail-closed ack timeout; the one honest exception is `execute_workspace_program`, where an already-dispatched declared tool call keeps running on the main thread after the worker dies, which the docs do disclose.

## 1. The real WASI runner has no usable artifact channel: base64-in-a-tool-argument only
`wasi-runner-unreachable` · kind **inert** · effort **medium**

**Evidence.** src/tools/execution-tools.ts:206-218 defines execute_code with `wasmBase64` as the only artifact input (maxLength 5,600,000 chars); src/execution/wasi-preview1-pack.ts:47 rejects any request without it; src/execution/wasi-preview1-worker.ts:44,92-99 decodes it with atob into a 4 MiB cap. There is no `wasmPath`, no transferred ArrayBuffer, and no pinned command catalog anywhere (grep for wasmBase64|wasmPath returns only these files plus tests). I verified the runner itself is excellent: a std Rust `wasm32-wasip1` binary compiled with the installed rustc 1.93.1 ran on the exact worker configuration and exercised args/env/cwd/read/write/rename/copy/remove/mkdir/remove_dir_all/append/seek/truncate/metadata/read_dir/1 MiB file/clock/exit(7) successfully.

**Impact.** The single genuinely working non-JS execution engine in the browser tier is unusable in practice. An agent cannot produce a wasm binary (there is no compiler), and inlining a 1.8 MB artifact as 2.4 M characters of base64 into a tool call is impossible for any model. The workspace can hold a .wasm (the binary envelope codec supports it) but execute_code cannot reference it. The capability is honestly described and genuinely real, yet nothing can ever invoke it.

**Fix.** (1) Workspace-path artifact — small and sufficient on its own. Add `wasmPath: { type: "string", minLength: 1, maxLength: 1_024 }` to the execute_code schema at src/tools/execution-tools.ts:208 and the mirrored proxy schema at src/tools/execution-tool-proxies.ts:88. In the executor (src/tools/execution-tools.ts:231-241) resolve it with normalizeWorkspacePath and require a bound workspace (the same guard as workspaceRoot at line 228). In validateExecuteCodeArguments extend all three branches: wasi-preview1 (1367-1377) requires exactly one of wasmBase64/wasmPath; javascript-worker (1360-1366) and python-pyodide (1378-1385) must reject wasmPath, otherwise the existing "accepts only code and timeoutMs" contract silently gains a hole.

(2) Plumbing. Add `wasmPath?: string` (or `wasm?: Uint8Array`) to ExecutionRequest at src/execution/runtime-registry.ts:42-57. In src/execution/wasi-preview1-pack.ts:46-56 replace the bare `if (!request.wasmBase64)` guard with "exactly one of", and for wasmPath do `workspace.read(normalizeWorkspacePath(path))` + `decodeWorkspaceBytes(file.content)` (both already imported at line 1) and run it through assertAllowedWorkspacePath/isWorkspaceControlPlanePath so .airship/.git/node_modules stay excluded. Important detail the original fix misses: read the artifact OUTSIDE captureWorkspace — captureWorkspace enforces WASI_PREVIEW1_MAX_FILE_BYTES (512 KiB per file) and WASI_PREVIEW1_MAX_WORKSPACE_BYTES (4 MiB total), so a >512 KiB .wasm inside the mounted root would make the mount itself throw before the run starts. Either exclude the artifact path from the snapshot or document that a mounted artifact is capped at 512 KiB; the artifact cap is the separate WASI_PREVIEW1_MAX_ARTIFACT_BYTES (4 MiB).

(3) Bytes instead of base64. Change runDisposableWasi (src/execution/wasi-preview1-pack.ts:82-90), the postMessage payload (149-158), and RunMessage (src/execution/wasi-preview1-worker.ts:21-27) to carry `wasm: Uint8Array`; delete decodeArtifact (worker:92-99) and move its WASI_PREVIEW1_MAX_ARTIFACT_BYTES check into validateInvocation (pack:256-269), which currently enforces the limit only as a base64 character count. Plain structured clone already works (the `files` array carries Uint8Array today); an explicit transfer list is optional. Blocking caveat the original fix omits: runDisposableWasi is re-exported at src/tools/execution-tools.ts:19 and consumed by the Chromium acceptance gate at e2e/browser-worker.spec.ts:60,95,109,127,155 with RUST_WASI_PREVIEW1_BASE64 — either keep a base64 entry point or update that spec and the fixture, or the gate cited in docs/MASTER_PROMPT_ACCEPTANCE.md:53 breaks.

(4) Pinned catalog — real but materially larger than "a Vite plugin plus five manifest lines". It needs, beyond scripts/pyodide-assets.ts-style serving and a vite.config.ts registration: required-path entries beside PYODIDE_ASSET_PATHS (scripts/release-gate.mjs:124-130); an isOptionalPythonPackPath-style classifier (scripts/release-gate.mjs:872-874) AND a new RELEASE_BUDGETS bucket, because eachWasm/allWasm (scripts/release-gate.mjs:105-106) cap every non-pyodide wasm at 1 MiB raw / 350 KiB gzip in aggregate, so any real tool pack fails the gate without its own optional bucket; a same-origin cache rule in public/sw.js:70; and an actual source of wasm32-wasip1 command binaries, which the repo does not have — crates/airship-runtime is a deliberately I/O-free library and crates/chutes-e2ee-wasm and crates/dcap-qvl-wasm are wasm-bindgen browser modules, not WASI commands. The lower-cost alternative is the existing remote-pin precedent at src/execution/wasix-contract.ts:18-21 (SHA-256 content-addressed images, digest-verified on the main thread; CSP already permits cdn.wasmer.io).

(5) Honesty upkeep: any new channel must be reflected in docs/BROWSER_EXECUTION_PACKS.md:14 and docs/CANON.md:531-533, which today describe the WASI tier purely as "precompiled command artifacts" with no statement about how an artifact is supplied.

Ship (1)+(2)+(3) first: they make the runner reachable from artifacts that git clone and WebContainer writeback can already place in the workspace, with no new dependency, no new asset, and no release-budget change.

## 2. No POSIX shell exists in any browser tier; the buildable winner is a TS sh now plus a Rust wasip1 multicall shell next
`no-posix-shell` · kind **absent** · effort **very-large**

**Evidence.** src/execution/runtime-registry.ts:26-40 types `shell` per adapter; every ready adapter reports `shell: "none"` (wasi-preview1-pack.ts:41, execution-tools.ts:566 for JS, 639 for Pyodide) except node-webcontainer which reports `webcontainer-jsh` (node-webcontainer-adapter.ts:43). The only `wasix-bash` adapter is fail-closed unavailable (runtime-registry.ts:101-114) and execution-tools.ts:476-477 throws wasixUnavailableDetail() for execute_wasix_shell. My empirical probe on the existing WASI worker shows the runner already supports every filesystem syscall a shell needs (rename/unlink/mkdir/rmdir/readdir/seek/truncate/append) and faithful exit codes; only std::process::Command fails, which WASI p1 never had.

**Impact.** The master prompt's core demand — a real multi-language shell — has no honest implementation. Users on Safari, Firefox, iOS, Android, or any page without cross-origin isolation get no shell at all, because the only interactive surface is StackBlitz jsh. Even on Chromium, jsh is not Bash and cannot reach Airship's own Git, Python, or WASI runtimes.

**Fix.** TIER 1 (universal, no toolchain, buildable today). Add src/shell/ with lexer.ts + parser.ts (POSIX sh grammar: quoting/escapes, |, &&/||/;, < > >> 2> 2>&1 <<here, ( ) subshells, $(...), $VAR/${VAR:-x}, and *?[] globs expanded against the VFS), fs-bridge.ts (VFS over WorkspacePort using list/read/readBounded/write/remove from src/workspace/contracts.ts:11-22, with a virtual cwd, a revision cache for CAS, and mkdir as a path-prefix because WorkspacePort has no directory objects), builtins/ (cd pwd echo printf cat ls mkdir rm mv cp head tail wc grep sort uniq cut tr find touch test export env which true false exit), pipeline.ts where every command is (ctx, argv, stdin: ReadableStream<Uint8Array>) => Promise<number> writing into a WritableStream so | is real streaming, and interpreter.ts owning $?, set -e, and an AbortSignal checked between chunks and builtins.

Wiring, with the corrections the original fix got wrong:
1. src/execution/runtime-registry.ts requires TWO union edits, not one: add "browser-sh" to ExecutionRuntimeId (lines 4-9) AND add "airship-sh" to the shell union at line 35 and "abort-interpreter" to the cancellation union at line 37. Also reuse the existing writeback vocabulary: workspaceAccess "bounded-snapshot-writeback", tier "web-baseline", isolation "disposable-worker", commandInterface "shell-script".
2. Register it next to createWasiPreview1Adapter() at src/tools/execution-tools.ts:589 and add execute_shell to src/tools/execution-tool-proxies.ts (existing tools are declared at lines 18-112).
3. Reuse reconcileWorkspace from src/execution/wasi-preview1-pack.ts:184-240 verbatim (dirty-set, per-path revision preflight, WorkspaceConflictError, nothing adopted unless exitCode===0), plus captureWorkspace at :162-183 for the mount, and honor assertAllowedWorkspacePath/isWorkspaceControlPlanePath so the shell cannot write .airship control-plane paths.
4. RELEASE BUDGET (missing from the original fix and a hard release-gate failure if ignored): scripts/release-gate.mjs:12-77 enforces per-chunk raw/gzip caps, including entryJavaScript 384 KiB raw / 110 KiB gzip. The shell must be a lazy chunk exported from src/deferred-capabilities.ts (or its own load-*.ts like src/load-execution-runtime.ts), and a new named budget entry (e.g. optionalShellPack) must be added alongside optionalExecutionPack / optionalWasiPreview1Worker.
5. Terminal wiring is a real refactor, not a line change: src/terminal/manager.ts is typed end-to-end on WebContainer (WebContainerProcess, WritableStreamDefaultWriter, mountTerminalWorkspace/syncTerminalWorkspace from src/terminal/workspace-sync.ts). Extract a TerminalEngine interface in src/terminal/contracts.ts first, then implement it for both engines.
6. Honesty artifacts: add a "POSIX sh subset — not Bash" row to docs/MASTER_PROMPT_ACCEPTANCE.md section 3 (next to the existing "Bash shell in the browser | Unavailable" row at line 56) enumerating job control, traps, arrays, process substitution, and signals as unsupported; add a candidate entry to PORTABLE_TERMINAL_CANDIDATES in src/execution/portable-terminal-contracts.ts with feature "bash" support:"unsupported"; and keep docs/ROADMAP.md:140 ("No arbitrary shell promise in the web tier") satisfiable by never claiming host access.

TIER 2 (Bash-grade) — the "run it on the existing wasi-preview1 worker, no new runtime" claim is wrong as written. src/execution/wasi-preview1-worker.ts:53 hard-wires stdin to `new OpenFile(new File([]))`, so stdin is instant EOF and no interactive prompt is possible without worker changes; the worker accepts exactly one run message and is disposed; WASI_PREVIEW1_MAX_ARTIFACT_BYTES in src/execution/wasi-preview1-contract.ts:2 caps artifacts at 4 MiB (enforced twice, at worker decodeArtifact and at validateInvocation's MAX_WASM_BASE64_CHARS = 5_600_000), which a brush + uutils/coreutils multicall binary will exceed; and the 64 MiB memory check plus the 256-file / 4 MiB / 512 KiB-per-file workspace caps apply. So Tier 2 must explicitly raise those pinned constants and add a stdin channel, and that change needs its own live probe. The build path itself is precedented: model crates/airship-sh on crates/dcap-qvl-wasm with scripts/build-airship-sh-wasm.sh after scripts/build-dcap-qvl-wasm.sh, emit via a Vite plugin modeled on scripts/pyodide-assets.ts, and pin the artifact the way e2e/fixtures/rust-wasi-preview1.ts already pins a wasm32-wasip1 binary with an inline SHA-256. Note the release-gate citation was wrong: scripts/release-gate.mjs:124-130 is PYODIDE_ASSET_PATHS, a required-asset path list, not a hash list — add the shell asset path there and pin its digest where the pack itself is loaded. Evaluating vendored MIT/Apache brush + uutils/coreutils under the existing pinning policy remains the right call before hand-writing a grammar for Tier 2. Both tiers should share one command table behind a single execute_shell contract.

## 3. WASI stdin is hardcoded to an empty file and ExecutionRequest has no stdin field
`wasi-no-stdin` · kind **absent** · effort **medium**

**Evidence.** src/execution/wasi-preview1-worker.ts:53-58 constructs the WASI with `new OpenFile(new File([]))` as fd 0, and RunMessage (lines 21-27) has no stdin member; src/execution/runtime-registry.ts:42-57 (ExecutionRequest) has code/wasmBase64/args/env/command/sourcePath but no stdin. My std Rust probe confirmed `stdin().read_to_string` returns 0 bytes.

**Impact.** No WASI command can consume input. That kills heredocs, `prog < data`, any filter used as the tail of a pipeline, and every interactive program. It is also the single hardest blocker for running a real shell binary interactively rather than as a one-shot batch.

**Fix.** Scope: this is a WASI-runtime input gap, not a shell gap. The shell dimension already has streaming stdin via jsh (src/terminal/manager.ts:190-229, 221-229, 244). Fix the WASI batch case; treat streaming as a conditional upgrade.

Batch stdin (small, fully buildable):
1. src/execution/runtime-registry.ts:42-57 — add `stdin?: string` to ExecutionRequest.
2. src/execution/wasi-preview1-contract.ts — add `WASI_PREVIEW1_MAX_STDIN_BYTES` (e.g. 512 KiB); every other input in this pack is explicitly budgeted, so an unbounded stdin would break the pattern.
3. src/execution/wasi-preview1-pack.ts — thread it through: add a `stdin` param to `runDisposableWasi` (signature at lines 82-90), pass `request.stdin` at the call site (lines 62-70), enforce the new ceiling inside `validateInvocation` (lines 256-269), and add `stdin: decodeWorkspaceBytes(stdin ?? "")` to the postMessage at lines 149-158. `decodeWorkspaceBytes` (src/workspace/content-codec.ts:24-26) is the right helper: plain text is UTF-8 encoded and the `airship-binary:` envelope also yields binary stdin.
4. src/execution/wasi-preview1-worker.ts — add `stdin?: Uint8Array` to RunMessage (lines 21-27) and change line 54 to `new OpenFile(new File(message.stdin ?? new Uint8Array()))`.
5. Tool surface is required, not optional: src/tools/execution-tools.ts:206-217 has `additionalProperties: false`, so a `stdin` property must be added to the execute_code inputSchema and to the ExecutionRequest construction ~lines 230-240, or a model can never supply it.
6. Update docs/BROWSER_EXECUTION_PACKS.md:14, whose capability row currently reads "printable-ASCII argv, env, stdout/stderr, clock/random".

Streaming stdin (medium, buildable but with corrected caveats):
- A new src/execution/wasi-stdin-fd.ts subclassing the exported `Fd` with a SharedArrayBuffer ring buffer and `Atomics.wait` in `fd_read` does work — `Fd.fd_read(size)` is synchronous and Atomics.wait is legal in a dedicated worker. It must also implement `fd_fdstat_get` returning a character-device filetype, or guests that stat fd 0 get ERRNO_NOTSUP.
- Gate it on `globalThis.crossOriginIsolated && typeof SharedArrayBuffer !== "undefined"`, NOT on the WebContainer precondition. WASI is the web-baseline tier and today asserts only Worker+WebAssembly (wasi-preview1-pack.ts:271-275); vite.config.ts:94-101 sets COOP/COEP only for the dev/preview server, so streaming can never be assumed.
- Drop the poll_oneoff claim from the rationale. Curing the busy-spin requires wrapping `wasi.wasiImport.poll_oneoff` in the worker before instantiation (the shim rejects fd subscriptions with ERRNO_NOTSUP and spins on clock ones), which is independent of any Fd implementation. Note this separately: a guest that polls stdin instead of blocking on read will still fail even with a streaming Fd.
- The honest capability field (`stdin: "batch" | "streaming" | "none"`) belongs on ExecutionCapability in runtime-registry.ts:26-40, alongside the existing shell/workspaceAccess/output/cancellation fields, and each of the five capability entries plus the three OPTIONAL_CAPABILITIES literals must declare it.

## 4. Python job timeout starts before CPython boots and is capped at 10 s, so real jobs time out spuriously
`pyodide-timeout-includes-cold-boot` · kind **bug** · effort **medium**

**Evidence.** src/tools/execution-tools.ts:1031 arms `setTimeout(..., timeoutMs)` immediately, while the job is only posted at line 1072 and the worker's onmessage at 1269-1277 then does `import(pyodide.mjs)` + `loadPyodide()` before a single line of user Python runs. Every job gets a fresh Worker and a fresh interpreter (line 1011-1018; the comment at 643 confirms 'fresh in-browser CPython interpreter per job'). DEFAULT_TIMEOUT_MS is 5,000 (line 23) and the execute_code schema caps timeoutMs at 10,000 (line 214, mirrored in execution-tool-proxies.ts:94).

**Impact.** A user's Python job is charged several seconds of interpreter cold start against its own 5 s default / 10 s maximum budget. On a cold cache or a slow device the job fails with 'Python execution exceeded 5000 ms' before the user's first statement executes, which reads as 'Python is broken' rather than 'the pack is still booting'. Repeated calls pay the boot cost every time.

**Fix.** Ship the timer split; do NOT ship the warm pool as described.

1) src/tools/execution-tools.ts:1273 (inside pyodideWorkerSource): immediately after `pyodide = await module.loadPyodide(...)` resolves, `__post({ type:"ready" })`. Keep boot inside `self.onmessage` rather than at module top level: the main thread posts the job at line 1072 with no handshake, so a top-level-await boot would need the early message buffered, and booting inside onmessage avoids that race entirely.

2) src/tools/execution-tools.ts:1019-1082 (runDisposablePyodide): arm a boot timer of DEFAULT_INSTALL_TIMEOUT_MS (line 24, 30_000) at Promise construction with a distinct message such as `Pyodide boot exceeded ${bootMs} ms.`; on the `ready` message clear it and only then arm `setTimeout(..., timeoutMs)` for execution. The `ready` branch must be inserted in the worker.onmessage handler ALONGSIDE the existing `message.type === "output"` branch at lines 1041-1045, i.e. BEFORE the `if (message.ok !== true)` check at line 1046 — otherwise `{type:"ready"}` has no `ok:true` and is swallowed as "Disposable Pyodide initialization failed." Leave the abort listener registration at 1032-1033 untouched so cancellation still terminates during boot.

3) Honesty follow-through, non-optional: total wall clock now exceeds the advertised budget, so update docs/BROWSER_EXECUTION_PACKS.md:15 ("10 s job") and surface both budgets (bootMs and timeoutMs, or an observed bootMs) in the ExecutionResult metadata returned at execution-tools.ts:246-261, rather than silently redefining what timeoutMs bounds.

4) Ceiling raise: the 10_000 max at execution-tools.ts:214 and execution-tool-proxies.ts:94 is one schema shared by all three runtimes, and the proxy schema is validated before the pack loads. Raising it for Python alone means raising the schema maximum in BOTH files and enforcing the lower per-runtime ceilings in the existing per-runtime branches of validateExecuteCodeArguments (execution-tools.ts:1361-1385, python branch at 1378).

5) Drop or separately gate the pooled warm interpreter. As written it breaks the honesty contract in four pinned places: execution-tools.ts:636-643 declares isolation "disposable-worker", persistence "ephemeral", cancellation "terminate-worker" and detail "Fresh in-browser CPython interpreter per job"; src/execution/runtime-registry.ts:91-98 declares the same pre-install ("fresh interpreter per job"); docs/BROWSER_EXECUTION_PACKS.md:115-116 states "Every job gets a new Worker and interpreter. Worker termination is the hard cancellation and timeout boundary."; and e2e/browser-worker.spec.ts:507-511 asserts isolation "disposable-worker" and persistence "ephemeral". "Reset FS state between jobs" is not sufficient isolation — sys.modules, module globals, monkeypatched builtins and pending asyncio tasks all survive a pool, so pooling is a genuine persistence/isolation downgrade that must be re-declared in all four places, not hidden. setInterruptBuffer is technically available (the app is cross-origin isolated via vite.config.ts:94-95 and public/_headers COOP same-origin + COEP credentialless), but an interrupt buffer only interrupts Python bytecode, not a blocking C/WASM call, so worker termination stays the only hard boundary and one wedged job poisons the pool. The cold-boot charge is fully fixed by steps 1-4 alone.

## 5. Python writeback can adopt files into .git/.airship/node_modules; WASI and WASIX both block this and the docs claim it is blocked
`pyodide-writeback-missing-control-plane-guard` · kind **bug** · effort **small**

**Evidence.** src/tools/execution-tools.ts:896-933 builds `changed`/`deleted` straight from the worker's returned paths and calls workspace.write/remove with no path validation. Compare src/execution/wasi-preview1-pack.ts:200 and 306-310 (assertAllowedWorkspacePath rejects isWorkspaceControlPlanePath and the .airship/.git/node_modules segments on egress) and src/execution/wasix-pack.ts:333,418-422 which do the same. The ingress filter exists for Python (execution-tools.ts:961-962) but has no egress twin. docs/BROWSER_EXECUTION_PACKS.md:127 states 'Control-plane paths are excluded.' src/workspace/contracts.ts:57-69 shows isWorkspaceControlPlanePath covers any `.git` segment plus .airship/memory, context and terminal state.

**Impact.** A Python job run with writeBack:true that does `os.makedirs('/workspace/.git'); open('/workspace/.git/config','w')` — or writes into .airship/terminal — has those files adopted into the authoritative workspace, corrupting the browser Git control plane or terminal manifest that other subsystems parse and refuse to guess about (terminal/manager.ts:650-667 throws on malformed metadata). It also contradicts a published doc claim, which is the one thing this project cannot afford.

**Fix.** Extract the egress guard into a shared browser-safe helper (e.g. src/execution/workspace-egress.ts) exporting `assertAllowedWorkspaceEgressPath(path, root, label)` that (a) rejects isWorkspaceControlPlanePath and (b) rejects the ".airship"/".git"/"node_modules" relative segments — the same set defined three times today at src/execution/wasi-preview1-contract.ts:7, src/execution/wasix-contract.ts:16, and src/tools/execution-tools.ts:30 — then have wasi-preview1-pack.ts:306-310 and wasix-pack.ts:418-422 delegate to it while keeping their existing "WASI/WASIX workspace excludes control-plane path: <path>" messages via the label. In src/tools/execution-tools.ts, apply it while building the `returned` map at line 897, BEFORE `changed`/`deleted`/`changedPaths` are computed (lines 898-904), so it fires even when writeBack is false, since changedPaths is reported back to the model. At the same point add the normalization WASI already does in reconcileWorkspace (wasi-preview1-pack.ts:194-203): run each returned path through normalizeWorkspacePath, throw unless it starts with `${snapshot.root}/`, and throw on duplicate normalized paths. Note the root-prefix assert is defense against a tampered worker message, not the symlink case the auditor described: collectWorkspace (execution-tools.ts ~1243-1268) builds paths textually from FS.readdir so they cannot escape the root string; FS.stat/readFile do follow symlinks, so a symlinked directory pulls its target's bytes in under in-root paths and normally trips the existing 256-file/4 MiB budget error. Optionally also skip excluded segments inside the worker's collectWorkspace so the budget is not consumed by a guest-created .git, but the authoritative guard must stay host-side. Tests: there is no existing Python writeback unit test — the only Python writeback coverage is the real-Pyodide e2e at e2e/browser-worker.spec.ts:483-533. Add a unit test that stubs globalThis.Worker and URL.createObjectURL in the style of src/execution/wasix-pack.test.ts:91-114 (post `{ ok: true, workspaceFiles: [{ path: "/workspace/project/.git/config", bytes: Uint8Array }] }` and assert the execute rejects with /excludes control-plane path/ and that no workspace write occurred), or extend the e2e spec with a Python job doing os.makedirs('.git'); open('.git/config','w') and assert rejection. Also tighten docs/BROWSER_EXECUTION_PACKS.md:127 so the "Control-plane paths are excluded." sentence explicitly covers both mount and writeback once the guard lands.

## 6. WASI and Pyodide throw away a successful run's exit code and output when workspace collection exceeds budget
`result-discarded-on-workspace-budget-overflow` · kind **bug** · effort **small**

**Evidence.** src/execution/wasi-preview1-worker.ts:83-89 calls collectFiles inside the completed postMessage; collectFiles (lines 138-158) throws on any file over 512 KiB or a total over 4 MiB, so the throw is caught by the generic handler at lines 38-40 and posted as `{type:"failed"}`, which makes runDisposableWasi reject (wasi-preview1-pack.ts:123-125). Pyodide is identical: execution-tools.ts:1307-1311 wraps the terminal post in try/catch and replaces the whole result with `{ok:false, error:"Python workspace collection failed"}`, discarding the exitCode/stdout/stderr computed just above at lines 1287-1306.

**Impact.** A job that ran correctly and printed exactly what the user wanted is reported as a hard failure with no output, purely because it also wrote a 600 KiB artifact. The user cannot see the program's own diagnostics to understand why. This is the most likely first failure mode for any data-processing or build-like workload.

**Fix.** Preserve the run's own outcome and report collection failure as a bounded field, but do NOT post `files: []` as the auditor proposed - an empty list is indistinguishable from "the guest deleted everything" and would make the reconcilers falsely report every mounted path as deleted (wasi-preview1-pack.ts:208 computes `deleted` from every snapshot file missing in `returned`; execution-tools.ts:897-903 does the same, and `result.workspaceFiles ?? []` already collapses undefined into "all deleted"). Correct shape:

1. src/execution/wasi-preview1-worker.ts:83-89 - have the main thread include a `collectWorkspace: boolean` flag in the run message (posted from wasi-preview1-pack.ts:149-158, true only when a snapshot was mounted) and skip collectFiles entirely when false, so unmounted runs can never be killed by a scratch artifact. When true, wrap collectFiles in try/catch and post `{type:"completed", exitCode, stdout: stdout.value(), stderr: stderr.value(), workspaceError: message.slice(0, 512)}` with the `files` key ABSENT (not empty).

2. src/execution/wasi-preview1-pack.ts:127-146 - in the "completed" branch, read a bounded `message.workspaceError` string; when present, skip parseWorkerFiles and carry the flag on the completion. In executeWasiPreview1Request (58-76), when workspaceError is present do not call reconcileWorkspace; return `workspace: { root: snapshot.root, mountedFiles: snapshot.files.length, changedPaths: [], writtenPaths: [], deletedPaths: [], writeBackRequested: request.writeBack === true, adopted: false, writeBack: request.writeBack === true, workspaceError }`.

3. src/tools/execution-tools.ts:1308-1310 - change the catch to `__post({ ok:true, exitCode, stdout, stderr, valueJson:value, workspaceError:"Python workspace collection failed: " + String(...) })` with no workspaceFiles key. Carry `workspaceError` through the handler at 1046-1069, and in executePythonRequest (880-947) short-circuit the diff/writeback block when workspaceError is set, returning the same all-empty-paths, adopted:false workspace record.

4. src/execution/runtime-registry.ts:66-76 - add `workspaceError?: string` to ExecutionResult["workspace"].

5. Honesty guard: with workspaceError present, refuse writeback unconditionally (even when writeBack===true and exitCode===0) and make execute_code report the run as an error rather than a clean success - src/tools/execution-tools.ts:260 currently sets `isError: result.exitCode !== 0`, which would mark a run whose artifacts were silently dropped as a success; change it to `result.exitCode !== 0 || Boolean(result.workspace?.workspaceError)` and surface workspaceError in the metadata block so the model cannot mistake a partial run for a complete one.

## 7. The terminal shell cannot call Airship's own Git, Python, or WASI runtimes; Git lives in a separate text box beside the prompt
`terminal-cannot-reach-page-runtimes` · kind **clunky** · effort **large**

**Evidence.** src/terminal/manager.ts:190-199 spawns only `jsh` in the WebContainer; src/ui/terminal-view.tsx:139-142 renders a separate 'Shared Git' form with its own input and Run button that calls runTerminalGitCommand and then manager.recordBridgeCommand (terminal-view.tsx:66-76, manager.ts:249-259) to paste the output into the transcript. The page simultaneously owns a real Git client (src/git/client.ts), a real Pyodide runtime (execution-tools.ts:604-662) and a real WASI runner, none of which is reachable from the prompt.

**Impact.** Typing `git status` at the actual terminal prompt fails, while typing it in a box six inches away works. Python and WASI are invisible from the shell entirely. The shell therefore feels like a demo of jsh rather than the agent's workbench, and the user must learn which surface owns which capability.

**Fix.** Install a labeled, fail-closed command bridge into the WebContainer and route it to the page's existing runtimes.

1. Paths: the WebContainer FileSystemAPI is scoped to container.workdir, and TERMINAL_WORKSPACE_MOUNT is the workdir-relative "airship-workspace" (src/terminal/contracts.ts:26). Do NOT use `/home/.airship-bin`. In src/terminal/manager.ts ensureHost (302-336), right after `mountTerminalWorkspace` (line 325), `host.fs.mkdir(".airship-bin", { recursive: true })` and write the shim sources there; put the request/response control directory in a sibling `.airship-bridge/` that is OUTSIDE `airship-workspace` so syncTerminalWorkspace's export (src/terminal/workspace-sync.ts:60) never adopts control files into the encrypted workspace.

2. PATH: at manager.ts:190-194 use `env: { TERM, AIRSHIP_TERMINAL, PATH: `${host.workdir}/.airship-bin:${host.path}` }`. WebContainer.path is the documented default PATH; replacing rather than prepending it would break node/npm inside jsh.

3. Exec bit: FileSystemAPI has no chmod (see @webcontainer/api dist/index.d.ts FileSystemAPI: readdir/readFile/writeFile/mkdir/rm/rename/watch only). Set it inside the container — `host.spawn("chmod", ["+x", ...])` or `host.spawn("node", ["-e", "require('fs').chmodSync(...)"])` — or sidestep it by writing a tiny package with a `bin` map and letting npm create the executable link, then pointing PATH at that `.bin`. Gate the whole install behind a one-time probe (`command -v git`) and, if the probe fails, leave PATH untouched and keep the existing Shared Git form (terminal-view.tsx:139-143) as the only surface rather than shipping a broken `git`.

4. Transport: each shim serializes argv+cwd+stdin to `.airship-bridge/<id>.req`, then async-polls for `<id>.res` (async fs + setTimeout, never a synchronous spin) and exits with the returned code so `git rev-parse HEAD || echo no` composes. Page side watches with `host.fs.watch(".airship-bridge", ...)` (exists in 1.6.4) plus a polling fallback, and dispatches git to runTerminalGitCommand with the same `reviewGit` approval, python to runDisposablePyodide, wasi to runDisposableWasi (base64 the .wasm from the request or read it with host.fs.readFile, respecting the 4 MiB artifact cap).

5. Coherence (missing from the original fix, and required by CANON 12.2's "cannot silently diverge from Editor"): page-side runtimes read the encrypted workspace, not the container FS. Before dispatching git or python, push container edits with syncTerminalWorkspace (src/terminal/workspace-sync.ts:55) so `git status` sees the shell's own edits; after any dispatch that rewrites workspace files (git switch/clone, Pyodide writeback) either remount via reconcileTerminalWorkspace or mark the tab reconcile-required, because the live mount is now stale and its baseline revisions will otherwise fail closed with WorkspaceConflictError on the next sync.

6. Fail closed, honestly: shims must not silently trigger the deliberately explicit pack installs (installPyodideExecutionRuntime, src/tools/execution-tools.ts:604) — print the install instruction and exit nonzero. Reject a bare `python3` REPL, stdin piping, and unsupported git subcommands with a message that names the Airship bridge, since runDisposablePyodide is a one-shot bounded worker with no stdin and runTerminalGitCommand implements only the enumerated command set (terminal-commands.ts:63-97).

7. Honesty contract: `git --version`/`help` must announce "Airship shared Git bridge, not POSIX git", and the three places that currently assert the shell has no git/python must be updated in the same change — docs/TERMINAL_ENGINE_ARCHITECTURE.md:39 ("instead of pretending ... that a package named `git` exists"), docs/CANON.md 12.2, and the evidence table in src/execution/portable-terminal-contracts.ts (git: "artifact-dependent", python: "unsupported").

8. Confused deputy: any process in the container (an npm postinstall, a dependency script) can write a request file. Bind requests to the foreground session and render the requesting command line in the approval prompt, and keep read-only git commands from leaking page-side repo state to unattended container processes.

## 8. WASI/Python jobs are capped at 10 s and 256 KiB of output while WebContainer gets 120 s
`wasi-ceilings-too-small-for-real-work` · kind **clunky** · effort **small**

**Evidence.** src/tools/execution-tools.ts:214 and src/tools/execution-tool-proxies.ts:25,53,94 cap execute_code timeoutMs at 10,000 ms, versus 120,000 ms for execute_node_project (execution-tool-proxies.ts:122). Output is capped at WASI_PREVIEW1_MAX_OUTPUT_BYTES = 256 KiB (src/execution/wasi-preview1-contract.ts) and MAX_OUTPUT_CHARS = 256 KiB (execution-tools.ts:25), with the WASI worker silently dropping bytes past the limit (wasi-preview1-worker.ts:168-175).

**Impact.** Any realistic shell workload — running a test suite, grepping a repo, processing a dataset — exceeds 10 s or 256 KiB and is killed or truncated. This alone would make the proposed shell tiers feel like toys even after they are built, and it is why the WASI tier reads as 'probe-grade' rather than 'work-grade'.

**Fix.** Two independent changes, both buildable in the browser today.

(1) Raise the WASI/Pyodide job ceiling without a per-property schema hack. JSON Schema `maximum` sits on the shared `timeoutMs` property of a flat discriminated object, so it cannot vary by `runtime`. Instead: set `timeoutMs: { type: "integer", minimum: 50, maximum: 120_000 }` in BOTH copies of the execute_code schema — src/tools/execution-tools.ts:214 and src/tools/execution-tool-proxies.ts:94 (leave the separate execute_javascript and execute_workspace_program tools at 10_000, proxies:25,53 and execution-tools.ts:70,117) — and enforce the per-runtime ceiling in the existing discriminated validator `validateExecuteCodeArguments` (src/tools/execution-tools.ts:1355), which already runs on both entry points (lines 223 and 422): throw for `javascript-worker` when timeoutMs > 10_000, allow up to 120_000 for `wasi-preview1` and `python-pyodide`. No other plumbing is required: the timeout is a main-thread setTimeout + worker.terminate() (wasi-preview1-pack.ts:108, execution-tools.ts:1031), and src/core/agent.ts:350 has no competing deadline. Update docs/BROWSER_EXECUTION_PACKS.md:13-15, which currently state "10 s maximum", or the docs stop matching the code.

(2) Replace silent truncation with declared truncation rather than an overflow log file. Keep the 256 KiB per-stream in-memory budget — src/tools/registry.ts:14,136 hard-fails any tool result whose JSON content exceeds MAX_TOOL_OUTPUT_BYTES = 1 MiB, so two 256 KiB streams is already near the ceiling. At each drop site, count what was dropped: src/execution/wasi-preview1-worker.ts:160-181 (`captureOutput` already tracks `acceptedBytes`; add `droppedBytes` and include per-stream totals in the `completed` post at line 82), src/tools/execution-tools.ts:1222-1226 (`boundedAppend`), :1190-1199 and :1122-1131 (`__emit`), plus the host-side `.slice(0, MAX_OUTPUT_CHARS)` calls at src/execution/wasi-preview1-pack.ts:137-138 and src/tools/execution-tools.ts:1059-1060, 801-802. Add an optional `output?: { limitBytes: number; stdoutBytes: number; stderrBytes: number; stdoutTruncated: boolean; stderrTruncated: boolean }` to ExecutionResult (src/execution/runtime-registry.ts:59-77), mirror it into the execute_code metadata block (execution-tools.ts:246-261 and 445-460), and follow the precedent already set by src/execution/node-webcontainer-adapter.ts:236,94, which reports its own 256 KiB limit as a `limitReason` string. Render it in the live tool-output panel (src/ui/app.tsx:5796) the same way workspace-view.tsx:461 marks a bounded file preview. Do NOT write an overflow log into the job workspace: WASI's mount is optional and javascript-worker has none, and collectFiles (wasi-preview1-worker.ts:138-158) throws past 256 files / 4 MiB, so that path would turn truncation into a hard job failure and pollute revision-checked writeback with a file the guest never produced.

## 9. One preopen named '.' at the workspace root, no cwd control and no scratch directory
`wasi-single-preopen-no-cwd-no-tmp` · kind **clunky** · effort **small**

**Evidence.** src/execution/wasi-preview1-worker.ts:47-48 creates exactly one `new PreopenDirectory(".", root.contents)` from the whole snapshot; ExecutionRequest (src/execution/runtime-registry.ts:42-57) has workspaceRoot but no cwd and no scratch/tmp concept. My probe confirmed the guest sees cwd "/" and that relative, ./ and absolute paths all resolve into that single preopen, and that everything the guest writes anywhere lands in the writeback set (wasi-preview1-pack.ts:184-240).

**Impact.** A command cannot be run in a subdirectory without re-snapshotting a different root, and there is nowhere to put scratch files that should not be adopted — a shell writing a temp file would try to write it back into the user's workspace. It also blocks the common pattern of mounting a read-only input tree next to a writable output tree.

**Fix.** Scratch mount (proven; do this part first). In src/execution/wasi-preview1-worker.ts, keep the workspace preopen FIRST in the fds array (lines 53-58) and append `new PreopenDirectory("/tmp", new Map())` after it. Order is load-bearing: I ran the repo's own no_std fixture (e2e/fixtures/rust-wasi-preview1.rs hardcodes fd 3) and putting scratch first made it exit 41. No change is needed to collectFiles (line 88 already walks only `preopen.dir`) and none to reconcileWorkspace (src/execution/wasi-preview1-pack.ts:184-240) — scratch is excluded for free. Inject `TMPDIR=/tmp` into the guest env, because `std::env::temp_dir()` unconditionally panics ("no filesystem on wasm") on wasm32-wasip1, so guests cannot discover it.

cwd: the proposed mechanism is wrong. "Set the guest cwd by passing the requested relative path as the preopen name" does not work — with the sole preopen renamed to "sub", the std probe still reported cwd "/" and every relative, ./ and absolute open failed with "failed to find a pre-opened file descriptor through which \"input.txt\" could be opened"; only paths already prefixed "sub/" resolved. The prestat name is a wasi-libc path prefix, not a cwd ("." strips to the empty catch-all prefix, which is why everything currently resolves), and no_std guests that use fd 3 directly ignore the name entirely. `PWD` in env also has no effect (verified). Buildable equivalent: add `cwd?: string` to ExecutionRequest (src/execution/runtime-registry.ts:42-57), thread it through the tool schema and validateExecuteCodeArguments (src/tools/execution-tools.ts:211 and ~1355-1375), the postMessage payload (wasi-preview1-pack.ts:149-158) and RunMessage (wasi-preview1-worker.ts:21-27); validate it normalizes inside workspaceRoot; then mount the requested subtree as the first `PreopenDirectory(".", subtree.contents)` so relative paths land there, and expose the wider tree as a second explicitly named absolute mount such as `new PreopenDirectory("/workspace", root.contents)`. getcwd still reports "/", so the capability text must say "relative paths resolve under <cwd>", not "working directory", or it becomes a false claim. Also fix the adoption join: reconcileWorkspace builds paths as `${snapshot.root}/${file.path}` (line 199), so when the collected mount is a subtree the join must add the cwd-relative prefix or writeback lands at the wrong workspace path.

Read-only mount: PreopenDirectory in shim 0.4.2 takes no rights argument, so a second mount is not read-only — guest writes succeed into the in-memory copy and are then silently dropped because collectFiles never visits it. Either subclass Directory to return ERRNO_ROFS from path_open/path_create_directory/path_unlink_file, or name it a discard mount; do not advertise "read-only" for a mount that accepts writes.

Whatever ships must also update the capability detail (wasi-preview1-pack.ts:44), docs/BROWSER_EXECUTION_PACKS.md:46-55, and the Chromium gate in e2e/browser-worker.spec.ts so the new mounts are receipted rather than asserted.

## 10. The WASI shim implements clock waits as a spin loop, so any guest sleep burns the worker at 100%
`poll-oneoff-busy-spin` · kind **bug** · effort **small**

**Evidence.** src/execution/wasi-preview1-worker.ts:53-58 wires wasi.wasiImport directly as the guest's syscall table. In that shim (node_modules/@bjorn3/browser_wasi_shim/dist/wasi.js) poll_oneoff rejects more than one subscription and any non-clock eventtype with ERRNO_NOTSUP, and implements the clock case as `while (endTime > getNow()) {}` — a busy wait. There is no override or wrapper in the Airship worker.

**Impact.** `sleep`, any retry/backoff loop, and any timed poll inside a WASI guest consume a full core for the duration and count against the 10 s job budget. For the proposed Rust shell tier this is a sharp edge users will hit immediately (`sleep 1` in a script), and on mobile it drains battery and can trigger the browser's background throttling.

**Fix.** Override poll_oneoff at the import-table wiring in src/execution/wasi-preview1-worker.ts:70-73 (NOT 53-58, which is the `new WASI(...)` construction). Build the table as `const imports = { ...wasi.wasiImport, poll_oneoff: sleepingPollOneoff }` and pass `imports` for both `wasi_snapshot_preview1` and `wasi_unstable`; spreading is safe because the shim's methods close over `const self = this`, not `this`.

Implement sleepingPollOneoff using the shim's public `wasi` namespace re-export (`import { wasi } from "@bjorn3/browser_wasi_shim"` - index.js does `export * as wasi from "./wasi_defs.js"`), which exposes Subscription.read_bytes, Event.write_bytes, EVENTTYPE_CLOCK, CLOCKID_MONOTONIC/REALTIME and SUBCLOCKFLAGS_SUBSCRIPTION_CLOCK_ABSTIME - so no hand-rolled struct offsets are needed. Preserve the upstream error surface exactly (ERRNO_INVAL for nsubscriptions===0, ERRNO_NOTSUP for >1 or non-clock, ERRNO_INVAL for an unknown clockid) and replace only the `while (endTime > getNow()) {}` body:
- Allocate `new Int32Array(new SharedArrayBuffer(4))` once, BEFORE the globalThis lockdown loop at lines 62-67, and block with `Atomics.wait(cell, 0, 0, remainingMs)` in a loop until the deadline. Atomics.wait is legal here because this is a dedicated worker thread, and SharedArrayBuffer is available because vite.config.ts:94-95/100-101 already serve COOP same-origin + COEP credentialless.
- When SharedArrayBuffer is absent (the adapter registers on any WebAssembly host, including non-isolated ones), do not silently spin for the full duration: cap the spin at a small budget (~50 ms) and return ERRNO_NOTSUP past it so the guest traps loudly instead of melting a core. Note the consequence in the code comment: Rust's std::thread::sleep panics on a failed poll_oneoff, which surfaces as the worker's existing "failed" message - that is the intended fail-closed behaviour.

Also update provenance, which the original fix omitted: src/execution/wasi-preview1-pack.ts:142 emits `engine: browser-wasi-shim-${BROWSER_WASI_SHIM_VERSION}-worker`, and docs/BROWSER_EXECUTION_PACKS.md:57-58 states the pinned shim is the unmodified upstream implementation. A patched syscall table makes both quietly untrue. Change the engine string to mark the deviation (e.g. `browser-wasi-shim-0.4.2-worker+poll_oneoff`) and record the override next to the existing 0.4.2 argv-sizing note at docs/BROWSER_EXECUTION_PACKS.md:59-60, extending the capability table row at docs/BROWSER_EXECUTION_PACKS.md:14 (which today claims only "clock/random") to state what sleep/poll actually does under each isolation posture. Add a unit test asserting the wrapper preserves the upstream ERRNO_INVAL/ERRNO_NOTSUP cases and that a 200 ms clock subscription returns ERRNO_SUCCESS without spinning.
