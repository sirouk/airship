# Are detected browser accelerators actually LEVERAGED, or merely reported?

> **Archived:** moved under `docs/archive/` during the provider-neutral simplification. This file is historical context only and is not normative. See [`../../SIMPLIFICATION.md`](../../SIMPLIFICATION.md) and the living docs in `docs/` for the current contract.

**Verdict.** Detection is genuinely excellent and genuinely honest — but leverage is thin, and the one place leverage matters most is broken by a boot-order race. Three accelerator paths are real: (1) WebGPU actually reaches the ONNX/Transformers.js semantic pack and the UI reports the worker's *actual* active backend, not the probe (src/indexing/semantic-transformers-loader.ts:48, src/ui/context-view.tsx:364); (2) OPFS is really used by the ciphertext cache with a real sync-access-handle worker path, though it selects itself via its own independent probe and never reads the policy (src/storage/client-ciphertext-cache.ts:408-465, wired by src/vault/coordinator.ts:467-472); (3) a real service worker exists, is registered in production, and caches app assets, Pyodide, and semantic-pack bytes (public/sw.js:68-87, src/main.tsx:11-18). The indexing triple (embeddingBatchSize / maxIndexingConcurrency / yieldEveryMs) is genuinely consumed all the way into IncrementalWorkspaceIndexer and has a test that proves constrained vs performance produce materially different work. Everything else is decorative: preferredWorkspaceStorage has literally zero consumers (not even UI), preferredWasmTier and heavyPackLoading are string-rendered in one UI row and read by nothing, maxWorkerConcurrency sizes no worker pool at all yet the UI prints "N workers", powerPreference is computed and never applied to the real GPU adapter or ORT, and WebNN/WebCodecs/WebTransport are probed, promoted into the model's prompt, and used by nothing. Worst of all, nothing kicks the probe off at boot: `BrowserCapabilityRegistry.start()` binds lifecycle listeners but issues no probe, so at the moment the semantic worker latches its backend forever, `snapshot()` is `undefined` and the page silently falls back to WASM on a WebGPU machine.

## 1. The capability probe is never kicked off at boot, so the semantic worker latches WASM on WebGPU machines
`probe-never-runs-before-first-use` · kind **bug** · effort **small**

**Evidence.** src/capabilities/browser-runtime.ts:377-394 — `start()` only binds pageshow/online/offline/visibilitychange/battery listeners; it issues no probe. :354 `snapshot()` returns `this.report`, which stays `undefined` until someone calls `refresh()`. The only non-test callers of `refresh()` are src/ui/app.tsx:2540-2541 (user opens the Capabilities screen) and :4848 (session-manifest creation, which happens when a conversation starts). Meanwhile src/tools/tool-bundle.ts:37 fires `void contextRuntime.scheduleRefresh()` during boot-time tool-registry construction (src/ui/app.tsx:1500), i.e. a full indexing generation begins ~120 ms later, before any manifest exists. src/indexing/semantic-browser-provider.ts:53-57 passes `() => capabilities()?.scheduling.preferredSemanticBackend === "webgpu"` which evaluates to `false` on an undefined snapshot; src/indexing/semantic-worker-provider.ts:167 turns that into `preferredBackend: "wasm"`, and :250 `const attempts = message.preferredBackend === "webgpu" ? ["webgpu","wasm"] : ["wasm"]` means WebGPU is then never even attempted. `ensureReady()` (:152-173) caches `this.ready` forever, so the WASM latch survives for the page lifetime; `setEmbeddingMode` (src/retrieval/client-context-runtime.ts:71-79) does not dispose the semantic provider. Semantic mode is persisted in localStorage (src/indexing/semantic-browser-provider.ts:18-27), so this fires on every reload for any user who has ever enabled it. The same race also forces the first generation onto the constrained fallback `{embeddingBatchSize: 4, maxIndexingConcurrency: 1, yieldEveryMs: 8}` at src/retrieval/client-context-runtime.ts:247-252 even on a 16-core desktop.

**Impact.** On a WebGPU-capable machine with semantic embeddings enabled, the model loads the q8 WASM ONNX weights instead of q4f16 WebGPU, and the UI truthfully reports "WASM semantic model ready" — so the user sees an honest label for a wrongly-chosen backend, with no way to recover short of a hard reload timed differently. The headline accelerator of the whole product is silently unused most of the time.

**Fix.** Restated: this is a boot-order race, not a missing probe -- the capability refresh does run at boot (src/ui/app.tsx:4848, reached from the mount effect at src/ui/app.tsx:1527), but it is gated behind two deferred chunk imports while src/tools/tool-bundle.ts:37 starts a wall-clock 120 ms indexing debounce, so at >=150 ms RTT the first embed latches the semantic worker to WASM on a WebGPU-preferring host (measured on dist/: "wasm" at t=1968 ms with the probe starting only at t=2167 ms).

Fix so the decision no longer depends on wall-clock ordering:
1. src/indexing/semantic-browser-provider.ts:41 -- change BrowserSemanticProviderOptions.capabilities to `() => Promise<Pick<BrowserRuntimeCapabilityReport, "scheduling"> | undefined>`, and at :53 default it to `() => getBrowserCapabilityRegistry().refresh().catch(() => undefined)` instead of `.snapshot()`. At :56 the predicate becomes `async () => (await capabilities())?.scheduling.preferredSemanticBackend === "webgpu"`.
2. src/indexing/semantic-worker-provider.ts:104 -- widen `webgpuAvailable` to `() => boolean | Promise<boolean>` (keep defaultWebgpuAvailable at :320 as the fallback) and in ensureReady() (:152-173) await it before the initialize postMessage: resolve the flag first, wrapped so a rejection falls back to defaultWebgpuAvailable(), then post `preferredBackend: resolved ? "webgpu" : "wasm"`. ensureReady is already async and the probe is deadline-bounded at 3 s per sub-probe, so this adds bounded first-embed latency only.
3. Optional latency hiding only (NOT sufficient alone, because the registry is first touched from inside webgpuAvailable() itself): kick the probe early, e.g. `void getBrowserCapabilityRegistry().refresh().catch(() => undefined)` next to the service-worker registration in src/main.tsx, or `void this.refresh().catch(() => undefined)` at the end of start() (browser-runtime.ts:377-394).
4. Optionally allow recovery from an already-latched worker: have ClientContextRuntime.setEmbeddingMode (src/retrieval/client-context-runtime.ts:71-79) dispose the semantic provider when switching back to semantic, since ensureReady caches this.ready for the page lifetime.
Do NOT include the scheduling-fallback item from the original finding (client-context-runtime.ts:247-252): client-context-engine.ts:460 re-reads the scheduling closure per generation, so that fallback is deliberate and self-correcting. Regression test: the existing e2e harness pattern in e2e/live-semantic-embedding.spec.ts can assert the initialize message carries "webgpu" under CDP Network.emulateNetworkConditions latency, which is exactly what fails today.

## 2. powerPreference is computed from battery/save-data and never applied to the real GPU adapter or ORT
`power-preference-never-applied` · kind **inert** · effort **small**

**Evidence.** src/capabilities/browser-runtime.ts:665-672 derives `low-power` / `high-performance` / `default` from battery level, charging state, save-data, cores and memory, and :278 puts it on the policy. It is applied only to the *probe's* throwaway adapter (:525) and the WebNN probe context (:564). The real workload requests its adapter with no options at all: src/indexing/semantic-transformers-loader.ts:19-20 `if (!gpu || !await gpu.requestAdapter()) throw ...`, and the actual device is then requested internally by onnxruntime-web, which is configured at :36-37 with `onnx.wasm = { ...onnx.wasm, wasmPaths: RUNTIME_ROOT }` and nothing else. Outside the UI string at src/ui/capabilities-view.tsx:92, `scheduling.powerPreference` has no consumers.

**Impact.** A laptop at 15 % battery, unplugged, gets the discrete high-power GPU for embedding work anyway; the Capabilities screen shows "low-power preference" while the page does the opposite. The signal is measured, displayed, and disregarded.

**Fix.** Thread the policy's powerPreference to the worker and use it to OVERRIDE the pack's hard-coded high-performance default. (1) src/indexing/semantic-worker-provider.ts:38 — add `powerPreference?: "high-performance" | "low-power" | "default"` to the `initialize` request; :65-70 — add the same optional field to `SemanticModelLoader.load` args; :102-104 — the constructor currently takes only `(workerFactory, webgpuAvailable: () => boolean)`, so add a third injected accessor (or replace webgpuAvailable with a scheduling-snapshot getter) and post it at :164-168 alongside preferredBackend; :255-259 — pass `powerPreference: message.powerPreference` into `loader.load({...})`. (2) src/indexing/semantic-browser-provider.ts:53-57 — `createBrowserSemanticProvider` already closes over `capabilities()` returning `Pick<BrowserRuntimeCapabilityReport,"scheduling">`, so supply `() => capabilities()?.scheduling.powerPreference` there; no new probe is needed. (3) src/indexing/semantic-transformers-loader.ts — map the policy to ORT's accepted set first: `const ortPower = powerPreference === "low-power" || powerPreference === "high-performance" ? powerPreference : undefined` (ORT throws `Invalid powerPreference setting: "default"` at wasm-core-impl.ts:117-119, so "default" must never be forwarded). Pass it to the pre-flight at :20 (`gpu.requestAdapter(ortPower ? { powerPreference: ortPower } : {})`, and widen the inline `gpu` type which currently declares `requestAdapter()` with no parameters). Then next to :36 widen the cast to `{ wasm?: Record<string, unknown>; webgpu?: Record<string, unknown> }` and mutate in place rather than spread-replacing: `if (backend === "webgpu") { onnx.webgpu ??= {}; if (ortPower) onnx.webgpu.powerPreference = ortPower; else delete onnx.webgpu.powerPreference; }` — in-place is safer because onnxruntime-web later installs `device`/`adapter` accessors on that same object (onnxruntime-web/lib/wasm/jsep/backend-webgpu.ts:277-283). Flag explicitly in review that the `delete` branch is a deliberate behavior change: hosts the policy classes "default" currently run high-performance because Transformers.js sets it, and after the fix they fall back to the browser's default adapter. If that regression is unwanted, leave "default" untouched and apply only the "low-power"/"high-performance" cases. Tests to update: src/indexing/semantic-worker-provider.test.ts:37 and src/indexing/semantic-browser-provider.test.ts:58,66 assert the initialize message shape.

## 3. preferredWasmTier selects no differently-compiled module anywhere in the repo
`wasm-tier-decorative` · kind **inert** · effort **medium**

**Evidence.** src/capabilities/browser-runtime.ts:254-260 derives `simd-threads | threads | simd | baseline` from real module-validation probes. Grep for the identifier across the whole repo returns only the type declaration, the derivation, the UI string at src/ui/capabilities-view.tsx:105, and two test fixtures. No consumer. The Rust crates ship exactly one artifact each with no target-feature flags: crates/chutes-e2ee-wasm/Cargo.toml and crates/dcap-qvl-wasm/Cargo.toml set only opt-level/lto/panic, and there is no `.cargo/config.toml` or `RUSTFLAGS` with `+simd128`/`+atomics` anywhere (verified by grep over scripts/ and crates/). The semantic pack ships one ORT build per backend (src/indexing/semantic-transformers-loader.ts:94-95 pins `ort-wasm-simd-threaded.jsep.wasm` or `ort-wasm-simd-threaded.wasm`), and `onnx.wasm.numThreads` / `simd` are never set (:36-37), so ORT falls back to its own internal heuristic — which ignores Airship's policy class entirely, meaning a 'constrained, low-battery' device still gets ORT's default thread count.

**Impact.** The page truthfully reports 'simd-threads WASM' and then runs the same single baseline artifact it would run on a 2015 browser. Cross-origin isolation is correctly configured (public/_headers COEP credentialless + COOP same-origin), so threads are genuinely available and genuinely unexploited by Airship's own code.

**Fix.** Three parts, in cost order.

(1) Honour the policy class in ORT thread count — drop the simd flag. In src/indexing/semantic-transformers-loader.ts:36-37 set `onnx.wasm = { ...onnx.wasm, wasmPaths: RUNTIME_ROOT, numThreads: maxWorkerConcurrency }`, threading the number through the existing initialize message: widen the union member at src/indexing/semantic-worker-provider.ts:38 (which already carries `preferredBackend`), populate it at :167, and widen the `() => boolean` webgpu predicate passed by createBrowserSemanticProvider (src/indexing/semantic-browser-provider.ts:44-57) to hand over `scheduling.maxWorkerConcurrency` as well. Do NOT set `onnx.wasm.simd`: per node_modules/onnxruntime-common/lib/env.ts:47-63 it only gates feature *checking* and never selects a runtime, and ORT 1.25 ships no non-SIMD artifact, so `simd:false` on a baseline browser replaces a clear error with an opaque instantiation failure.

(2) Real tiering for the E2EE crate only (this is where simd128 actually changes generated code). crates/chutes-e2ee-wasm/Cargo.lock pins sha2 0.11.0, whose src/sha256.rs:46-48 selects a `wasm32_simd128` compress under `target_feature = "simd128"` — the HKDF/SHA-256 path genuinely switches; chacha20 0.10.1 and ml-kem 0.3.2 gain only LLVM autovectorization, so state the win as SHA-256 + autovectorization, not 'ChaCha20-Poly1305/ML-KEM'. Extend scripts/build-e2ee.mjs to run wasm-pack twice, the second with RUSTFLAGS="-C target-feature=+simd128", emitting a second binary (e.g. src/inference/chutes/wasm/chutes_e2ee_wasm_simd128_bg.wasm) and asserting the two generated JS glue files are byte-identical (the wasm-bindgen ABI is unchanged by target features — make that an explicit build assertion, not an assumption). Select at load time by passing the chosen URL into the constructor parameter that already exists: src/inference/chutes/crypto.ts:31 `moduleOrPath`, consumed at :43 by `initWasm(this.moduleOrPath)` — no dynamic-import restructuring needed. Gate the choice on the same probe that feeds the tier (getBrowserCapabilityRegistry().snapshot()?.scheduling.preferredWasmTier), with a synchronous WebAssembly.validate fallback using the SIMD probe bytes already present at src/capabilities/browser-runtime.ts:142 for the pre-snapshot case. This fits the release gate unchanged: scripts/release-gate.mjs:105-106 budget eachWasm/allWasm at 1024 KiB raw / 350 KiB gzip against a current single 268 KB e2ee artifact, and both digests land in release-manifest.json automatically via the artifact map at :618-623.

(3) Do not blindly duplicate the DCAP QVL artifact as originally proposed. scripts/release-gate.mjs:401-404 throws unless there is *exactly one* optional DCAP QVL WASM pack, and :587-588 budget that single 1031 KB file against RELEASE_BUDGETS.optionalDcapQvlWasm (1536 KiB raw / 512 KiB gzip), which a second copy blows. Since crates/dcap-qvl-wasm/Cargo.lock pins sha2 0.10.9 (no wasm32_simd128 module), the QVL crate gains only autovectorization, so either skip it or land it separately with the invariant raised to 2 and the budget re-derived from a measured build.

(4) Honesty follow-through: once only the e2ee crate is tiered, the 'Adaptive policy' row at src/ui/capabilities-view.tsx:105 must say what the tier actually selects (e.g. the crypto artifact and the ORT thread count) rather than implying a global tier, matching the header's own promise at :82 that 'Probes select preferences; each workload reports its active backend.'

## 4. maxWorkerConcurrency sizes no worker pool, but the UI prints it as "N workers"
`max-worker-concurrency-sizes-nothing` · kind **dishonest-claim** · effort **medium**

**Evidence.** src/capabilities/browser-runtime.ts:243-244 computes a 1-8 ceiling. Its only uses are internal (:271, clamping maxIndexingConcurrency) and the UI string at src/ui/capabilities-view.tsx:105 which renders `{report.scheduling.maxWorkerConcurrency} workers`. Every `new Worker(...)` in the codebase is a fixed singleton or per-invocation instance, none sized by the policy: src/tools/execution-tools.ts:715, :826, :1014; src/storage/client-ciphertext-cache.ts:344; src/execution/wasi-preview1-pack.ts:93; src/execution/wasix-pack.ts:203; src/indexing/semantic-browser-provider.ts:47. There is exactly one semantic embedding worker regardless of whether the policy says 1 or 8.

**Impact.** A user on a 12-core machine reads "8 workers" on the Capabilities screen. Airship never runs 8 of anything. This is the one place in an otherwise scrupulous capability panel where the UI states a number that no code honours.

**Fix.** Make the number precise rather than building a pool. (1) In src/ui/capabilities-view.tsx:105 replace `{report.scheduling.maxWorkerConcurrency} workers` with `{report.scheduling.maxIndexingConcurrency} indexing lanes` — that value is the one actually consumed by concurrentMap at src/indexing/incremental-indexer.ts:99 via src/retrieval/client-context-runtime.ts:255 and src/indexing/client-context-engine.ts:470, and the codebase already uses the word "lanes" in the comment at client-context-runtime.ts:251-253. (2) In the same row, drop or qualify `{humanize(report.scheduling.heavyPackLoading)}`: heavyPackLoading is computed at src/capabilities/browser-runtime.ts:274 and has no consumer anywhere outside that file and this UI line, so it is the same defect the finding names and must be fixed with it or the panel stays inaccurate. (3) Because src/tools/browser-capabilities.ts serializes the entire report to the model, a UI-only edit is insufficient: either rename the field on AdaptiveSchedulingPolicy (src/capabilities/browser-runtime.ts:67) to something like workerConcurrencyCeiling with a doc comment stating it is only a derivation input for maxIndexingConcurrency and sizes no pool, or delete it and inline the ceiling into the :271 expression. Update the fixtures at browser-runtime.test.ts:73,165, semantic-browser-provider.test.ts:106, and e2e/edge-portability.spec.ts:31,110 accordingly. Do NOT take the auditor's worker-pool option: each additional semantic worker re-fetches and SHA-256-verifies the pinned mxbai-embed-xsmall-v1 pack against semantic-artifact-manifest.json and holds its own model plus WebGPU device (docs/SEMANTIC_EMBEDDING_PACK.md), multiplying memory and startup cost for a workload that is already batched inside one worker.

## 5. preferredWorkspaceStorage has zero consumers anywhere — not even the UI
`preferred-workspace-storage-dead` · kind **inert** · effort **small**

**Evidence.** src/capabilities/browser-runtime.ts:277 derives `opfs | indexeddb-fallback` from the OPFS root probe. Repo-wide grep finds it only in the type (:74), the derivation (:277), and two test fixtures. It does not appear in src/ui/capabilities-view.tsx, in src/storage/, or in src/vault/. The actual selection is made independently by src/storage/client-ciphertext-cache.ts:147-166, which unconditionally attempts OPFS first, then IndexedDB, then memory, and probes `createSyncAccessHandle` itself inside the worker realm (:422-425).

**Impact.** The right backend does get chosen, but by a second, duplicated probe — so the policy field is pure dead weight, and there is one wasted OPFS worker spawn plus up to a 5 s `OPFS_START_TIMEOUT_MS` stall (client-ciphertext-cache.ts:12, :382) on engines where `navigator.storage.getDirectory` exists but the directory cannot be opened (e.g. some private-browsing modes).

**Fix.** Make the derived policy a skip-hint that can only avoid work, never assert a capability.

1. src/storage/client-ciphertext-cache.ts:64-68 — extend ClientCiphertextCacheOptions with an optional `preferredWorkspaceStorage?: "opfs" | "indexeddb-fallback"`.

2. Same file, :155-165 — in createClientCiphertextCache, skip the `openOpfs` attempt (fall straight through to openIndexedDb, then memory) when the option is exactly "indexeddb-fallback". Leave the ladder unchanged when the option is absent or "opfs", so the default path and all existing tests in client-ciphertext-cache.test.ts:12-38 keep passing. Do not touch OpfsWorkerCiphertextPageBackend's reporting: the worker's own createSyncAccessHandle probe (:422-424) stays the sole authority for the reported `backend` and `syncAccessHandle`, which preserves the docs/CLIENT_STORAGE_ACCELERATION.md rule that "OPFS is reported only after the worker opens its origin-private directory and performs a real sync-handle probe."

3. src/vault/coordinator.ts:467 — pass the hint alongside the existing partition. The coordinator currently imports nothing from src/capabilities, so either lazily import the registry there (`const { getBrowserCapabilityRegistry } = await import("../capabilities/browser-runtime")`) or add `getBrowserCapabilityRegistry` to the VaultRuntimeModules bundle (coordinator.ts:176-186, loaded at :735) and read `snapshot()?.scheduling.preferredWorkspaceStorage`. Use the same non-blocking `snapshot()` form already used at src/retrieval/client-context-runtime.ts:247 — never `refresh()`, so vault adoption never waits on a capability probe. When snapshot() is undefined, pass nothing and keep today's behavior.

Two corrections to the original write-up that must carry into the change:

a. The main benefit is narrower than "OPFS unavailable". openOpfsWorkerBackend already short-circuits when navigator.storage.getDirectory is missing, and navigator.storage is itself secure-context-only, so the hint only adds value in the `opfs.state === "failed"` case (getDirectory present but rejecting — private-browsing style engines). That is exactly the case that costs the full 5 s today.

b. probeOpfs (browser-runtime.ts:621) reports state "failed" for both a rejected getDirectory and a 3 s withDeadline timeout (host.timeoutMs, :455). So a slow-but-working OPFS can be skipped for the life of that adopted cache. This is an acceptable trade (the IndexedDB fallback is still `origin-private-persistent`, and the registry re-probes on lifecycle events so the next adoption re-tries OPFS), but it should be stated in the code comment rather than left implicit. If a false downgrade is judged unacceptable, tighten it first by having probeOpfs distinguish a DOMException TimeoutError from a real rejection and only emit "indexeddb-fallback" for the latter.

Add a unit test in client-ciphertext-cache.test.ts asserting that with `preferredWorkspaceStorage: "indexeddb-fallback"` the injected openOpfs spy is never called and the reported backend is "indexeddb", and that with the option omitted openOpfs is still attempted first.

## 6. heavyPackLoading is derived from offline/save-data signals and gates no download
`heavy-pack-loading-dead` · kind **inert** · effort **small**

**Evidence.** src/capabilities/browser-runtime.ts:274 sets `"manual"` when `signals.online === false` or the connection reports save-data/2g, else `"lazy-on-demand"`. Its only appearance outside the type and tests is the humanized UI string at src/ui/capabilities-view.tsx:105. The two heavy downloads in the product ignore it: the semantic pack is fetched asset-by-asset in src/indexing/semantic-transformers-loader.ts:99-109 with no policy check, and the Pyodide pack loads on first Python execution (src/tools/execution-tools.ts:1014) with no policy check.

**Impact.** A user on a metered 2G connection with data-saver on flips the 'Local semantic' toggle and Airship immediately pulls the full pinned model + ORT runtime, while the Capabilities screen displays 'Manual' heavy-pack loading. The signal is real, the promise implied by the label is not kept.

**Fix.** Consume the signal on the one path that actually fetches, and drop the Pyodide leg.

1) Export the byte total that the loader already computes privately. In src/indexing/semantic-transformers-loader.ts the asset list and `totalBytes` reduce live at lines 83-97; lift them into an exported pure helper `semanticPackBytes(backend: SemanticBackend): number` over `semantic-artifact-manifest.json` so the UI can name the number without duplicating the asset list. Today's totals: ~38.8 MB for the wasm path (24,448,010 model_quantized.onnx + 12,528,402 ort-wasm-simd-threaded.wasm + runtime/tokenizer files) and ~46.2 MB for the webgpu path (32,885,696 model_q4f16.onnx + 25,415,321 jsep.wasm ... recompute in code, do not hardcode).

2) Gate the explicit switch. In src/ui/context-view.tsx, inside `changeEmbeddingMode` (line 107, before `await runtime.setEmbeddingMode(mode)` at line 112), when `mode === "semantic"` and `getBrowserCapabilityRegistry().snapshot()?.scheduling.heavyPackLoading === "manual"`, render an in-card confirmation state (not window.confirm) that names the byte total for the policy's `preferredSemanticBackend` and the reason strings already in `scheduling.reasons`, and only call `setEmbeddingMode` after the user confirms.

3) Gate the silent path, which is the one that actually matters. When `readEmbeddingMode()` (src/indexing/semantic-browser-provider.ts:18) restores "semantic" from localStorage while `heavyPackLoading === "manual"`, keep `SwitchableEmbeddingProvider` on the bootstrap provider and surface the same confirmation, instead of letting the first `embed()` from ContextView mount or from a `tool-bundle.ts:18` context tool call pull ~38-46 MB on a metered connection with no gesture in that session.

4) Do NOT add a dialog in src/tools/execution-tool-proxies.ts. The Pyodide pack is already fail-closed and explicit (installPyodideExecutionRuntime at src/tools/execution-tools.ts:604, only reachable via install_execution_runtime, effect "network", which passes the approval broker). If anything is wanted there, add the pack's byte total to the existing approval-card summary for that tool - which first requires a byte/hash manifest for /execution-packs/pyodide/ (scripts/pyodide-assets.ts currently lists file names only).

5) Cover it: extend e2e/edge-portability.spec.ts's `chromium-constrained-2c-2gib` project, which today asserts only that the policy value is "manual", with a route-level assertion that no /semantic-pack/v1/ request is issued until the confirmation is accepted. That is what turns the label into a kept promise rather than a displayed string.

## 7. WebNN is probed with a real context creation and used by nothing
`webnn-probed-never-used` · kind **absent** · effort **large**

**Evidence.** src/capabilities/browser-runtime.ts:555-576 really creates and destroys a `navigator.ml` context and :296 promotes it into the model's session prompt as a probe-passed capability. `SemanticBackend` is `"webgpu" | "wasm"` only (src/indexing/semantic-worker-provider.ts:16), and the policy comment at browser-runtime.ts:261-263 states plainly that WebNN 'cannot be selected until a WebNN embedding adapter passes the same activation contract'. Grep confirms `navigator.ml` appears nowhere outside the probe. This is the project's honesty ledger working correctly — the gap is capability, not truthfulness.

**Impact.** On Windows/ChromeOS devices with an NPU, Airship detects the accelerator, tells the model it exists, and then runs embeddings on the GPU or CPU. The prompt entry may also lead the model to reason about an NPU it can never reach.

**Fix.** The gap stands; the fix must be restated.

(1) Type surface is wider than claimed. Add the backend to src/indexing/semantic-worker-provider.ts:16 AND to `preferredSemanticBackend` at src/capabilities/browser-runtime.ts:72 (computed at :264). The main-thread seam is a boolean, not a backend: semantic-worker-provider.ts:167 sends `preferredBackend: this.webgpuAvailable() ? "webgpu" : "wasm"`, fed by src/indexing/semantic-browser-provider.ts:56 (`preferredSemanticBackend === "webgpu"`). That predicate must become a backend selector before a three-rung ladder at :250 is meaningful.

(2) No new ONNX Runtime bundle is needed — this part of the original fix is simply wrong. The already-pinned runtime/ort.webgpu.bundle.min.mjs (sha256 11391ac5fd67…, byte-identical to installed onnxruntime-web 1.25.0-dev.20260327) is the *asyncify* build and already contains the whole WebNN backend (`backend-webnn.ts`, `webnnInit`, `webnnRegisterMLContext`, the WebNN tensor manager). What that bundle actually names as its wasm binary is `ort-wasm-simd-threaded.asyncify.mjs/.wasm` — it never names `ort-wasm-simd-threaded.jsep.*` or the plain `ort-wasm-simd-threaded.*` that semantic-artifact-manifest.json pins and semantic-transformers-loader.ts:83-96 verifies. So step 2 is: pin runtime/ort-wasm-simd-threaded.asyncify.{mjs,wasm} in scripts/prepare-semantic-pack.mjs + the manifest + the suffixes list. Worth a separate look: under this ORT pin the WebGPU and WASM rungs appear to verify wasm binaries the runtime does not load, which would 404 the real one.

(3) Device string: `device: "webnn"` maps to `{name:"webnn", deviceType:"cpu"}` (node_modules/@huggingface/transformers/dist/transformers.web.js:7623), i.e. WebNN CPU — it would never touch the NPU that motivates the finding. src/indexing/semantic-transformers-loader.ts:48 must pass `"webnn-npu"` (optionally webnn-gpu/webnn-cpu as separate rungs).

(4) dtype needs a new artifact, not just a new constant. WebNN cannot execute the pack's MatMulNBits q4f16 or int8-dynamic q8 graphs. Add onnx/model.onnx (fp32, 96,025,279 bytes) or onnx/model_fp16.onnx (48,142,045 bytes) at the pinned revision to semantic-artifact-manifest.json and the backend-conditional suffixes list at semantic-transformers-loader.ts:83-96, and extend dtypeFor() at :116 with a webnn dtype.

(5) Static shapes. The pinned config.json has no `transformers.js_config.device_config`, so transformers.js only warns (transformers.web.js:18264) and runs with dynamic shapes. A real WebNN rung must pass `session_options.freeDimensionOverrides` and pin tokenization to that fixed batch/sequence (padding "max_length" + truncation) — which conflicts with the policy-variable `embeddingBatchSize` (4/12/32) from browser-runtime.ts.

(6) Honesty guard — the original fix's central safety claim is false. "A WebNN failure degrades honestly and automatically" holds only at load time (transformers.js throws `Unsupported device: "webnn"` when navigator.ml is absent, which the :250 ladder catches). ORT's WebNN EP partitions the graph and silently falls unsupported nodes back to the CPU/WASM EP, so session creation can succeed while nothing runs on the NPU, and `ready: { backend: "webnn" }` would then assert an acceleration the runtime cannot verify — exactly what browser-runtime.ts:296 and browser-capabilities.ts:18 are written to avoid. The rung must therefore either verify WebNN op coverage before promoting the label, or report the requested EP distinctly from observed acceleration.

## 8. WebGPU is used for embeddings only; vector search is scalar main-thread JavaScript
`webgpu-only-inside-onnx` · kind **absent** · effort **large**

**Evidence.** The only application code path that reaches the GPU is the ONNX/Transformers.js pipeline (src/indexing/semantic-transformers-loader.ts:48 `device: backend`). Retrieval scoring is a plain scalar loop on the main thread: src/indexing/flat-index.ts:16-34 maps over every chunk in a `Map` and :49-60 computes cosine similarity element-by-element over 384 dimensions, recomputing both norms on every comparison for every chunk on every keystroke-driven search. No SIMD, no worker, no GPU, no precomputed norms. The only WGSL compute submission in the repo is a test-only assertion (e2e/edge-portability.spec.ts:276-303) that proves the *browser* can, not that Airship does.

**Impact.** A workspace with a few thousand chunks blocks the UI thread on every search, on the same page whose Capabilities screen advertises an acquired WebGPU adapter with its storage-buffer limits. The most obviously GPU-shaped workload in the product (dense similarity over a matrix) never touches the GPU.

**Fix.** Ordered by cost, all in this repository.

(1) Correctness-preserving CPU win, no accelerator. In src/indexing/flat-index.ts, cache each chunk's L2 norm at insert time (upsert(), line 7, is the single ingress -- IncrementalIndexer.importSnapshot at src/indexing/incremental-indexer.ts:123-136 also funnels through index.upsert, so there is exactly one build point and no IndexSnapshot format change is needed since contracts.ts:51-57 still serializes only vector: number[]). Compute the query norm once at the top of search() (line 16) instead of per chunk, and reduce the inner loop at :54-58 to a single multiply-accumulate. Do NOT simply replace cosine with a bare dot product on the strength of `normalize: true`: both shipped providers do L2-normalize (src/indexing/hash-embeddings.ts:36-41 for the bootstrap path as well as the semantic manifest at src/indexing/semantic-worker-provider.ts:13), but validateVectors in semantic-worker-provider.ts checks only dimension and finiteness, never unit norm, and ClientIndex is a public contract -- cached norms keep the result exactly cosine for any provider while still cutting multiplies ~3x.

(2) Move scoring off the main thread. Introduce a dedicated scoring worker sized by scheduling.maxWorkerConcurrency (src/capabilities/browser-runtime.ts:67, :244), following the existing worker pattern in src/indexing/semantic-browser-provider.ts:45-52 including the Trusted Types URL policy. Maintain the vectors as one packed Float32Array (dimensions * chunkCount) rebuilt on upsert and transferred once per generation; note tokens must go with it since lexical() at flat-index.ts:62 participates in the 0.72/0.28 blend, so ship the token sets to the worker too rather than round-tripping to the main thread. Keep FlatClientIndex's current implementation as the reference.

(3) Optional WebGPU scoring backend. One WGSL dot-product kernel over the packed storage buffer, gated on scheduling.preferredSemanticBackend === "webgpu" (browser-runtime.ts:264-266), sized against the already-observed maxStorageBufferBindingSize / maxStorageBuffersPerShaderStage limits (browser-runtime.ts:160-161) with chunked dispatches when the matrix exceeds them, falling back to the CPU path on device-lost or validation error. Report its own active backend to the UI the same way the semantic provider does, which satisfies the contract already stated at browser-runtime.ts:292 ("a consuming pack must still report WebGPU as its active backend") rather than straining it.

(4) There is currently no unit test file for flat-index.ts (src/indexing has only client-context-engine, incremental-indexer.scheduling, semantic-browser-provider, and semantic-worker-provider tests), so add src/indexing/flat-index.test.ts asserting the cached-norm path is bit-comparable to the existing cosine and diffing the CPU and GPU scorers within a float32 tolerance.

## 9. The service-worker and cache-storage observations report API presence, not the real registration or cache state
`service-worker-observation-is-api-presence-only` · kind **clunky** · effort **small**

**Evidence.** src/capabilities/browser-runtime.ts:178-187 derives both from `navigator.serviceWorker !== undefined` and `"caches" in globalThis`, labelled `api-exposed` — which is honest as far as it goes. But a real, well-built service worker exists (public/sw.js:16-35 precaches the release-manifest-pinned asset set; :68-87 caches /assets/, /execution-packs/pyodide/, and /semantic-pack/v1/ on first use) and is registered at src/main.tsx:11-18 — but only under `import.meta.env.PROD`. The probe never checks `navigator.serviceWorker.controller`, so the report cannot distinguish 'this browser has the API' from 'Airship is actually being served from a warm offline cache'. `report.serviceWorker` and `report.cacheStorage` have no consumers beyond the prompt entries (browser-runtime.ts:310-317) and the UI list (src/ui/capabilities-view.tsx:68-71).

**Impact.** The user gets no signal about the one accelerator that most directly affects perceived speed and offline capability. On a dev/preview build the panel says 'Service Worker: available' while nothing is registered at all — technically accurate about the API, uninformative about the page.

**Fix.** Promote both observations from API presence to page reality in src/capabilities/browser-runtime.ts, keeping everything injectable through the existing probe host so unit tests stay hermetic.

1. Extend BrowserNavigatorLike (browser-runtime.ts:116) so serviceWorker is narrowly typed rather than `unknown`: `serviceWorker?: Readonly<{ controller?: unknown; getRegistration?: () => Promise<unknown> }>`. Add an injectable async cache accessor to BrowserCapabilityProbeHost (browser-runtime.ts:121-133), e.g. `cacheKeys?: () => Promise<readonly string[]>`, defaulted in createProbeHost (browser-runtime.ts:426-435) to `"caches" in globalThis ? () => caches.keys() : undefined`. Keep hasCacheStorage as the cheap presence gate.

2. Replace the apiObservation call at browser-runtime.ts:178-182 with an async probeServiceWorker(host) that mirrors probeOpfs (browser-runtime.ts:608-621) and joins the existing Promise.all at line 171-175:
   - navigator.serviceWorker undefined -> unavailable("Service Worker API was not observed.")
   - controller != null -> { state: "available", evidence: "probe-passed", detail: "A service worker is controlling this page; assets may be served from the offline shell cache." }
   - registration found via `await withDeadline(Promise.resolve(nav.serviceWorker.getRegistration()), host.timeoutMs, "Service worker registration probe")` but controller null -> { state: "available", evidence: "api-exposed", detail: "A service worker is registered but is not yet controlling this page." }
   - no registration -> { state: "available", evidence: "api-exposed", detail: "Service Worker API is exposed; no worker is registered for this page." }
   - throw -> failed/probe-failed via the existing boundedFailure() helper, never leaking raw error text.

3. Replace browser-runtime.ts:183-187 with an async probeCacheStorage(host) that calls `await withDeadline(host.cacheKeys(), host.timeoutMs, "Cache Storage probe")` and matches /^airship-shell-v\d+$/ against the returned keys — do NOT hardcode "airship-shell-v6", because scripts/release-gate.mjs:996 pins only the /const CACHE_VERSION = "airship-shell-v\d+";/ pattern in public/sw.js:1 and the version bumps between releases. Match -> probe-passed with the matched key in the detail ("The Airship shell cache <key> is present in this origin."); no match -> api-exposed with "Cache Storage is usable; no Airship shell cache was found."; throw (Firefox private browsing raises SecurityError here) -> failed/probe-failed, which is a real honesty gain over today's unconditional "available".

4. Update the prompt-entry loop at browser-runtime.ts:310-317, which currently hardcodes `evidence: "api-exposed"` for service-worker/cache-storage: emit `observation.evidence` instead, otherwise a newly probe-passed observation is understated in the session prompt. The e2e contract at e2e/edge-portability.spec.ts:236-242 already accepts both evidence values and only forbids unearned promotion for webgpu/webnn/opfs, so no test loosening is required.

5. In src/ui/capabilities-view.tsx:105 the "Browser primitives" details list renders only probePresentation(observation)[1] ("API observed" / "Probe passed") and drops observation.detail, so the new "registered but not controlling" wording would be invisible; render the detail (or attach it as a title/second line) in that list so the distinction reaches the user.

6. Extend the existing fixture in src/capabilities/browser-runtime.test.ts (navigator.serviceWorker is `{}` at line 35) with cases for controlling / registered-not-controlling / no-registration and for a cacheKeys() that returns an airship-shell-v* key, one that returns none, and one that rejects.
