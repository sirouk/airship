## Phone-only, whole journey, driven with Playwright at three real viewports: iPhone 14 Pro Max (430x932, dpr2, touch), Android-class (360x800), and landscape (932x430). Cold arrival at #chat; #access → Chutes lane → API key tab → paste the live cpk_ key → Discover models → model sheet → Finish: verify & connect; a real connected turn (first attempt returned Chutes HTTP 429, second returned a real `list_files` tool call); the slash menu; then #workspace, #editor, #terminal, #memory, #context, #sessions, #proof, and the More sheet, each measured for chrome budget, horizontal overflow, sub-44px targets and truncated text. Keyboard behaviour was tested by instrumenting window.visualViewport (obscured = 336px) so the app's own `data-keyboard-open` path actually fired. 40+ screenshots in .aesthetic/tmp/phone/, all read as images, not inferred from source.

**Verdict.** This is a desktop app that has been told about phones. The tokens prove it: `--fs-micro`, `--fs-body` and `--fs-lead` are byte-identical at 360px and 1440px, and the only responsive typographic decision anyone made was to shrink the page title from 21.25px to 17.85px — so the phone ships a flatter hierarchy (1.12:1 title-to-body) than the desktop (1.54:1). Underneath that, three things a phone user does most are broken rather than dense: the keyboard rule that would keep the composer visible is dead code (`position: static` with `bottom: 336px`), so Send sits 217px under the keyboard; the terminal cannot be typed into at all on touch — 550px of black that accepts no focus while ^C and Restart work fine; and the composer's placeholder is measured against a 209px box the composer never uses, clipping 40% of it at 430px and 60% at 360px. The connect flow is 4402px — 5.3 phone screens — with the primary button buried at y1254. And in the one place Airship's own thesis is on the line, the phone tool card spends ~180px on the words "Tool step completed" (already said by a green tick and a COMPLETED pill) and renders the tool's name as `lis…`. Three of ten characters. That is not density; that is the interface choosing to keep its own chrome and throw away the fact.

**Worst moment.** #chat on iPhone 14 Pro Max, connected, tapping the composer to ask a question. The app correctly detects the keyboard — `data-keyboard-open="true"`, `--visual-viewport-bottom: 336px` — and then does nothing with it, because computed `.composer-wrap` is `position: static; bottom: 336px`. The composer stays at y791–876 and the send button at y813–857 while the keyboard top is at y596. On screen above the keyboard: the topbar, "General conversation", the "Workspace, editor, terminal and Git work right now" banner, one greeting bubble, and the top halves of two suggestion cards. Not on screen: the text field you are typing into, the words you are typing, and the Send button — 217 to 261 pixels below the keyboard. Meanwhile the tab bar has been set to `visibility: hidden` but keeps its 56px box, so you lose the navigation and gain no space.

### [blocker] The keyboard-aware rule is dead code: composer and Send sit 217px under the keyboard

**Observed.** iPhone 14 Pro Max, #chat, composer focused, visualViewport obscured = 336px. The app sets `data-keyboard-open="true"` and `--visual-viewport-bottom: 336px` correctly. Computed style on .composer-wrap is `position: static; bottom: 336px` — inert. Rect unchanged: composer y791–876, send button y813–857. Keyboard top is y596. Send is 217–261px below the keyboard line. `.mobile-nav` gets `visibility: hidden` but keeps its 56px layout box (y876–932), so hiding it frees zero pixels and only removes navigation. .transcript stays at h611 and never reflows, so scroll-to-bottom lands behind the keyboard too.

**Why bad.** On a phone the composer is the product. Someone wrote the iOS keyboard rule — they knew the problem — and it has never worked, because `bottom` does nothing on a static box. Worse, iOS Safari's `100dvh` (styles.css:3253, 5022) does not shrink for the keyboard, so this is broken specifically on the platform the rule was written for and accidentally fine on Android Chrome, which resizes the layout viewport. The user types blind and cannot reach Send.

**Replacement.** At `@media (max-width: 640px)`: `.composer-wrap { position: fixed; left: 0; right: 0; bottom: calc(var(--visual-viewport-bottom, 0px) + env(safe-area-inset-bottom)); z-index: 40; }` and `.transcript { padding-bottom: calc(var(--composer-block, 96px) + var(--visual-viewport-bottom, 0px)); }`. Change `:root[data-keyboard-open="true"] .fixed-mobile-nav` from `visibility: hidden` to `display: none` so the 56px is reclaimed. On the visualViewport resize event, re-run scroll-to-bottom. Add a keyboard-up affordance the desktop does not need: a 44px 'Done' text button in the composer's control row, label 'Done', which blurs the field.

**Information fate.** Nothing removed. The tab bar's four destinations remain reachable the instant the keyboard closes, and Chat/Workspace/Trust/More are all duplicated inside the More sheet, which stays reachable via the Command Center.

**Files.** src/ui/platform-shell.css, src/ui/styles.css, src/ui/platform-shell.tsx

### [blocker] The terminal cannot be typed into on a phone: 550px of black that accepts no focus

**Observed.** #terminal, iPhone 14 Pro Max. Tapping the terminal surface at (200,200) leaves `document.activeElement` as `MAIN.main route-layout` — focus never moves. The only text input in the route is `textarea.xterm-helper-textarea` at 9x23px, which is never focused. Typing 'ls -la' then Enter produced no change: the pane still shows `~/airship-node/airship-workspace` and a bare `❯`. The pane occupies y210–760 = 550px, 59% of the viewport. The three controls that do work are ^C, Restart and ✕ — you can kill the shell you cannot use. Meanwhile three runtime facts are rendered off the right edge and are unreachable: 'Processes stay hot while this tab is open' (right edge 449), 'Reload requires process restart' (663) and 'Thread 978705f…84e37' (833) on a 430px viewport.

**Why bad.** A route in the primary tab bar, advertised on the cold-start screen as 'Open a terminal — Real processes in this tab, no account', is non-functional on the device class the user is holding, and says nothing about it. Silent breakage is the one failure mode this product's whole posture forbids. It also fails honest labelling: the pane shows a live `❯` prompt, which is a claim that input is accepted.

**Replacement.** Pin a command bar directly under the pane: a full-width `<input inputmode="text" autocapitalize="off" autocorrect="off" spellcheck="false">` at 44px with placeholder 'Run a command in Terminal 1', a 44px 'Run' button, and above it a horizontally scrollable 44px key strip with scroll-snap: `Tab` `Ctrl` `Esc` `↑` `↓` `|` `~` `/` `-`. Route submissions into the same pty as the xterm. If touch focus genuinely cannot be delegated, degrade honestly with a caption above the pane: 'This browser will not open a keyboard for the terminal surface. Type commands below — output is live.'

**Information fate.** Nothing removed; ^C / Restart / ✕ and the 'Interactive jsh process running inside this page's WebContainer.' caption stay. The three off-screen runtime facts move into a 44px 'Runtime facts ⌄' disclosure under the pane, stacked verbatim: 'Processes stay hot while this tab is open.' / 'Reload requires process restart.' / 'Thread 978705f…84e37'.

**Files.** src/ui/terminal-view.tsx, src/ui/terminal-view.css

### [blocker] The composer input gets 48% of the screen width at rest, clipping 40–60% of its own placeholder

**Observed.** 430x932: `.composer textarea` is 209x58 — 48.6% of the viewport width — because `.composer-footer` (202px: attach, 'Ask First ⌄', Send) sits beside it in the same row. Placeholder 'Ask Airship or type / for tools and session commands…' needs scrollHeight 97 in clientHeight 58: 4 lines of 24px, 2 shown, the second sliced through its glyphs ('tools and session' cut horizontally at the box edge). 360x800: textarea 139x58, scrollHeight 145 — 6 lines needed, 2 shown, 60% clipped. The moment you type one character the textarea jumps to 410px wide and the footer reflows below it, proving the resting layout is measured against a box the composer never actually uses.

**Why bad.** This is the first sentence the product says about how to use it, and it is cut in half on every phone, in the empty state, permanently. A user who never learns about `/` never finds tools or session commands. It also produces a visible layout jump on first keystroke.

**Replacement.** At ≤640px make `.composer` a two-row grid, not a row: row 1 = textarea, full width (410px at 430), `rows=1`, min-height 44px, auto-growing to 5 lines; row 2 = a 44px control row `[＋] [/ Tools] [Ask First ⌄] ——— [Send]`. Resting placeholder becomes 'Message Airship'. The `/` affordance stops being prose and becomes a tappable 44px chip labelled '/ Tools' that opens the slash sheet.

**Information fate.** The full sentence is not deleted. It becomes (a) the textarea's `aria-label`: 'Message Airship, or type slash for tools and session commands', and (b) a one-line hint above the composer in the empty state only: 'Type / for tools and session commands.' The '/' route to tools is additionally made reachable by tap for the first time.

### [major] The phone tool card spends 180px on 'Tool step completed' and renders the tool name as `lis…`

**Observed.** 430x932, live Chutes turn. `.tool-call` 341x63 at y537 and `.tool-result` 341x63 at y607 — 133px for one invocation, 22% of the 612px transcript. Each card's three columns: 'Tool step completed' at 17px green (~180px), then an 11px mono kind label that wraps to two lines ('TOOL' / 'CALL') colliding with the tool name, which is truncated to `lis…` (3 of 10 chars) and `list_f…` (6 of 10), then a pill COMPLETED / SUCCESS. Four separate renderings of one status per card: green tick, 'Tool step completed', 'TOOL CALL', 'COMPLETED'. The assistant produced no prose after them, so the entire visible answer is two green boxes saying 'Tool step completed'.

**Why bad.** Airship's claim is that it never hides what it did. On a phone it does exactly that: the only irreducible fact — which tool ran — is the single thing thrown away, while a string already carried by an icon and a pill is given three times the space. `lis…` is not an abbreviation, it is an erasure; `list_files`, `list_sessions` and `list_models` are indistinguishable.

**Replacement.** One 44px row per invocation inside a bordered group headed 'Tool steps · 1': `✓ list_files · 12 files · 240 ms  ›`. Name first, 15px mono, `overflow-wrap: anywhere`, never ellipsized — truncate the summary, never the identity. Tap expands the row in place to today's full card verbatim: kind label, status pill, 'ARGUMENTS · BOUNDED DISPLAY', the code box, and the call id. Group header states: 'Tool steps · 1', 'Tool steps · 1 running', 'Tool steps · 2 · 1 failed'.

**Information fate.** Nothing removed. 'TOOL CALL' / 'TOOL RESULT', the COMPLETED / SUCCESS pills, the arguments box and the raw call id all live inside the expansion; the ✓/✗ glyph and the group header carry status at rest, and the failed-state header word 'failed' preserves the pill's meaning without opening the row.

### [major] The type scale is the desktop scale verbatim, and the phone's hierarchy is flatter than the desktop's

**Observed.** Computed `:root` at 360, 430 and 1440: `--fs-micro: calc(.6875rem * 1)`, `--fs-body: calc(.9375rem * 1)`, `--fs-lead: calc(1.0625rem * 1)`, root font-size 17px — byte-identical at all three. The only responsive typographic change is downward: conversation title is 21.25px on desktop and **17.85px on phone**, against 15.94px body — a **1.12:1** title-to-body ratio on phone versus **1.54:1** on desktop. `--fs-micro` resolves to **11.69px** and carries 'SESSION MODEL', 'airship/demo-v1', 'Ephemeral · this page only', the whole 'Workspace, editor, terminal and Git work right now' banner, the message author labels, 'Ask First', and the composer's trust caption. `.mobile-nav__tab` is **11px**. At 360px, body lines are 271px wide ≈ 34 characters.

**Why bad.** A phone is held further from the eye than a laptop, in worse light, in motion. Airship's response was to keep every desktop size and shrink the one element that should have grown. The result is that the page title, the section headings and the body text are all within 2px of each other, so the phone screen has no scannable hierarchy at all — and the trust vocabulary the product cares most about is set at 11.69px, below every platform legibility floor.

**Replacement.** A real phone ramp at ≤640px: `--fs-display: 24px/1.2` (serif page title), `--fs-lead: 19px`, `--fs-body: 16px/1.55`, `--fs-meta: 13px`, `--fs-micro: 12px` as an absolute floor, `.mobile-nav__tab: 12px`. That moves title:body from 1.12:1 to 1.5:1 and puts every label at or above 12px. At 360px, cap body measure at 38–42 characters by trimming bubble padding from 16px to 12px rather than shrinking type.

**Information fate.** No string changes at all. This is purely the size ramp; every label, caveat and provenance line renders identically, larger.

### [major] The slash menu hides half its items, wraps names to three lines, truncates every description, and pre-selects the destructive command

**Observed.** 430x932, connected, typing '/'. Popover y399 h360 — 39% of the screen, covering the conversation. 10 items; `scrollHeight` 505 vs `clientHeight` 358, so ~4.5 items are hidden with no scrollbar, fade or count. Names get a ~200px column and wrap to **three lines** ('/deactivate-' '/execution-' '/runtime'; also '/execute-workspace-program'), while every description is hard-truncated to one line: 'Terminate an optional runtime and release i…', 'Execute one strictly typed browser job in a …', 'Run bounded JavaScript in a disposable br…'.
