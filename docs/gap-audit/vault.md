# Vault, storage, encryption, streaming

**Verdict.** The cryptography and the object-store contract are genuinely real and unusually well built: `encrypted-segments.ts` is a true per-block AES-256-GCM extent format with an offset table and AAD binding, so partial reads without whole-object download are structurally supported; the Drive adapter issues real `Range: bytes=a-b` requests and refuses anything that is not a `206` with an exactly matching `Content-Range`; the resumable upload is a real Drive resumable session with 308 offset recovery; the Local Device vault is a complete, offline, encrypted, crash-safe authority with a real recovery ceremony, a real encrypted export, and a real verified atomic restore wired into the UI. Client-side-only encryption holds everywhere — no key ever reaches a provider. But "Google Drive is the DEFAULT fully-wired production vault" is currently the weakest claim in the whole dimension. Drive is the default *preference value* (`platform-shell.tsx:227-232`), and the shipped GitHub Pages build never supplies `VITE_GOOGLE_CLIENT_ID` (`.github/workflows/pages.yml:38-41`, no `.env` in the repo), so the default provider renders a developer-facing red notice and the runtime silently stays page-memory ephemeral. Even with a client ID, Drive forgets the workspace key and the folder descriptor on every reload (nothing is persisted; the non-extractable-CryptoKey IndexedDB store exists but is wired only to Local Device), the OAuth token dies every hour with no silent refresh, every single write does a full-index download + full-index re-upload (up to 24 MiB, unsharded), nothing is ever deleted or trashed so a Drive vault grows monotonically forever including permanent conformance-probe litter, and the "range coalescing" in the acceptance ledger is index-download coalescing, not byte-range merging — retrieval still issues one HTTP request per expert block. Key custody has no unlock ceremony at all: WebAuthn PRF is designed in detail and implemented nowhere (zero `navigator.credentials` references in the tree), and the docs say so honestly. Net: Local Device is the genuinely production-grade vault today and it is not the default; Drive is a real, careful, mostly-correct adapter that is not yet a usable default.

## 2. A Drive vault must be fully re-established (recovery key + Google consent) on every page reload
`drive-vault-forgets-key-and-folder-on-reload` · kind **absent** · effort **medium**

**Evidence.** src/vault/coordinator.ts holds `config`, `directStore`, `store`, `runtime`, and the workspace key only as instance fields; the only localStorage use in the whole app is preference overrides (src/ui/platform-shell.tsx:237,254) plus the semantic-embedding mode flag. src/storage/google-drive-auth.ts:25-57 is explicitly `MemoryOnlyGoogleAccessTokenProvider` with no refresh token and `getAccessToken` throwing `GoogleDriveAuthorizationRequiredError` within 30 s of expiry. src/ui/google-drive-setup.tsx:66-115 requires the user to either generate a new recovery key or paste an existing `airship-wrk-v1…` value into a textarea before `connect()` will run. Meanwhile src/storage/local-device-keyring.ts:237-284 already implements exactly the missing piece — an IndexedDB store of a structured-cloned non-extractable `CryptoKey` handle keyed by partition — but it is only invoked for the local-device backend (src/ui/app.tsx:1099-1110). docs/GOOGLE_DRIVE_VAULT.md:51-53 names this as future work: "A future same-origin IndexedDB cache may store a non-extractable CryptoKey for same-browser reloads".

**Impact.** The default durable provider is unusable as a daily driver: every refresh, every tab restore, and every ~1-hour token expiry drops the user back to pasting a 128-character recovery key. Reloading also re-runs `connectExisting()` folder discovery from scratch. This is the practical reason a user would abandon Drive, and it is the difference between "default vault" and "demo".

**Fix.** Scope correction first: mid-session ~1-hour token expiry is ALREADY solved in place by src/vault/coordinator.ts:333-339 (`reauthorizeGoogleDrive`) wired to the closure captured at src/ui/google-drive-setup.tsx:98 and exposed as a renew button at src/ui/vault-view.tsx:235 / src/ui/app.tsx:3111-3117. The gap is only page reload, new tab, and browser restart.

Fix: add a new provider-neutral module src/storage/workspace-key-handle-store.ts rather than mutating local-device-keyring.ts in place. Use a NEW IndexedDB database name (e.g. `airship-workspace-key-handles-v1`); do not bump `airship-local-device-keyring-v1` (src/storage/local-device-keyring.ts:8-10), which would force a migration of existing local-device enrollments for no benefit. Copy the IndexedDbLocalDeviceKeyHandleStore pattern (local-device-keyring.ts:237-284) verbatim, including the "structured cloning a CryptoKey is the custody boundary; raw bytes are never a fallback" rule at lines 274-277.

Partition keying must differ from the auditor's proposal. `google-drive:<workspaceFolderId>:<googleSubject>` is unusable as the primary key because neither component is known before the user authorizes, so nothing could be looked up to render the reconnect affordance. Instead key records by `google-drive:<googleSubject>` (valid under the existing partition regex at local-device-keyring.ts:373-382, which permits `:`), and (a) extend the record type with the non-secret `GoogleDriveWorkspace` descriptor from src/storage/google-drive-workspace.ts:9-16 ({workspaceFolderId, workspaceName, rootFolderId, segmentsFolderId, namespaceId}) plus the account email, and (b) add a `list()`/`getAll()` method so src/ui/google-drive-setup.tsx can render "Reconnect <email> → <folder>" before any click. Note that the existing `keyRecord()` validator (local-device-keyring.ts:332-353) silently drops unknown fields and would discard the descriptor — the new module needs its own validator that parses and bounds every descriptor field.

Write path: in src/ui/google-drive-setup.tsx after `manager.connectOrCreate/connectExisting` returns at lines 80-82 and before `onConfigure` at line 90, `putIfAbsent` the record with `workspaceKey.persistedHandle()` (encrypted-envelope.ts:63-65) plus the descriptor and `identity.email`.

Read path: on the single GIS click, `authorize({selectAccount:false})`, read `identity.subject` via `readGoogleAccountIdentity` (google-drive-auth.ts:209), load the record for `google-drive:<subject>`, rehydrate with `WorkspaceRootKey.fromPersistedHandle` (encrypted-envelope.ts:45-58), then fail closed by re-running `new GoogleDriveWorkspaceManager(provider, key).connectExisting()` (google-drive-workspace.ts:50-60) and asserting the rediscovered `workspaceFolderId` and `namespaceId` equal the stored ones before calling `onConfigure`. That live rediscovery is the correct adoption gate here and is stronger than trusting the cached descriptor. `equivalentWorkspaceKeys` (local-device-keyring.ts:310-321) is a private, non-exported function — it is also already duplicated at src/ui/local-device-vault-setup.tsx:849 — so reusing it means exporting it from the new shared module and having local-device-keyring.ts import it, not referencing it as-is.

## 3. Every Drive write downloads and re-uploads the entire encrypted object index
`drive-full-index-round-trip-per-write` · kind **bug** · effort **large**

**Evidence.** src/storage/google-drive-object-store.ts:150 and :172 call `this.loadIndex(signal, true)` (forceRefresh) inside `putIfAbsent` and `compareAndSwap`; lines 197-203 make forceRefresh bypass the 1.5 s cache and call `loadIndexFresh`, which re-lists the index files and downloads the whole `.airship-root-v1.enc` body (line 227, bounded by MAX_INDEX_BYTES = 24 MiB at line 30). `advanceIndex` (lines 286-302) then re-seals and PATCHes the *entire* index back. `MAX_OBJECTS = 100_000` (line 32) and each `IndexEntry` carries key + 33-char fileId + 50-char sha256 etag + size + ISO timestamp, so a busy workspace's index is measured in megabytes. This stacks with the same pattern one layer up: src/vault/encrypted-workspace.ts:127 puts the immutable file object and :204 CAS-advances a full workspace manifest (MAX_MANIFEST_BYTES = 32 MiB, line 27), so one `workspace.write()` costs roughly four full-index transfers plus two full-manifest transfers.

**Impact.** A Drive-backed workspace degrades quadratically. Cloning or checking out a repo through the browser Git path — which writes each object as a workspace file — turns N object writes into ~4N full-index downloads and ~4N full-index uploads. At only 10k objects (~1.6 MB index) that is already tens of gigabytes of traffic for one clone. This is the reason the default provider cannot survive a real workload, and it is the opposite of the master prompt's "only necessary encrypted shards move".

**Fix.** Two layers must change; the auditor's version fixes only one and misroutes the other.

(A) Shard the Drive index by KEY prefix, not by sha256. In src/storage/google-drive-object-store.ts keep `.airship-root-v1.enc` as a small CAS-fenced directory record `{version, generation, shards:[{lowKey, highKey, fileId, httpEtag, entryCount}]}` and route each logical key by lexicographic range. Do NOT use `sha256(logicalKey)` first-8-bits routing as proposed: `list(prefix)` has real callers — src/storage/encrypted-object-journal.ts:82 (`${prefix}/session-heads/`), src/vault/coordinator.ts:820, src/storage/conformance.ts:83 — and hash routing forces all 256 shards to be fetched on every prefix list, which is also why docs/GOOGLE_DRIVE_VAULT.md:132 says "route key prefixes". With lexicographic ranges, `putIfAbsent`/`compareAndSwap` load and PATCH only the owning shard with `If-Match`, `list(prefix)` touches only overlapping ranges, and the directory record is CAS-advanced only on split/create. Preserve the existing fail-closed properties: keep `locateOrCreateIndex`'s re-list-and-reject-ambiguous check (lines 239-261) on the directory record, keep the forced-fresh read before any conditional write, and add a shard-split race test next to the existing ambiguous-root test in src/storage/google-drive-object-store.test.ts.

(B) The dominant cost for the Git/editor path is the manifest, not the index, and `writeMany` is unreachable there. src/vault/encrypted-workspace.ts:196-206 re-downloads the whole manifest and :212-224 re-uploads it as a fresh immutable segment on every write()/remove(); that manifest lives under one logical key, so index sharding alone does not touch it. Adding `EncryptedObjectWorkspace.writeMany(files)` would never be called by a Git checkout, because isomorphic-git drives src/git/workspace-fs.ts:101-125 `writeFile` one file at a time through `PromiseFsClient` (and that method additionally does a read-before-write, costing a second full-manifest download per file). Instead: (1) add an explicit transactional write scope on the workspace port that buffers manifest mutations and flushes with a single CAS, and open/close it in src/git/workspace-adapter.ts around each `git.clone` / `git.checkout` / `git.commit` call so `WorkspaceGitFileSystem` writes accumulate into one manifest advance; and (2) drop the redundant `workspace.read` in workspace-fs.ts:112 in favour of manifest metadata already held by the scope. Optionally chunk the manifest itself the same way as (A) so a single-file write outside a scope stops paying O(total files).

(C) While touching this, note that the growth is unbounded independent of shard size: write() mints a new cloudKey per revision and no path ever removes the superseded object-index entry, so release gate 3 (GC) must land or MAX_OBJECTS = 100_000 becomes a hard wall after 100k cumulative writes.

## 4. Nothing is ever deleted: superseded revisions, lost-race orphans, and conformance-probe litter accumulate permanently in the user's Drive
`no-delete-vault-grows-forever` · kind **absent** · effort **large**

**Evidence.** src/storage/object-store.ts:49-61 — the `ObjectStore` interface has get/getRange/putIfAbsent/compareAndSwap/list and no delete. src/storage/google-drive-object-store.ts contains no DELETE request and no `trashed: true` update (the only occurrence of "trashed" is the `trashed = false` list filter at line 268). src/vault/encrypted-workspace.ts:125 derives each file's cloudKey from `fileLogicalId(path, revision)`, so every edit writes a brand-new segment file, and `remove(path)` at lines 160-169 only rewrites the manifest — the ciphertext object stays in Drive forever. src/storage/conformance.ts:18-22 states the contract has no delete and "callers must configure expiry or remove the returned keys out-of-band"; src/vault/coordinator.ts:443-448 surfaces that as `deletionAvailableInRuntime: false` and the warning "Probe objects are immutable. Configure provider lifecycle expiry or remove the listed keys out-of-band." One probe run writes at least the six keys enumerated at conformance.ts:38 plus the losing sides of two deliberate races plus the encrypted-composition probe objects, and vault-view.tsx:232-234 offers a repeatable "Verify again" button.

**Impact.** Google Drive has no lifecycle-expiry feature, so the cleanup instruction Airship prints is not actionable on the default provider. Each Drive connect leaves ~10+ permanent `.enc` files in the user's own Drive quota, and normal editing grows the vault without bound — a 100-edit session leaves 100 encrypted copies of the same file. docs/GOOGLE_DRIVE_VAULT.md:127-129 already names this ("Until then, losing uploads are retained ciphertext residue") but the residue from superseded revisions is the far larger volume and is not named.

**Fix.** Keep the optional-capability shape (`ReclaimableObjectStore.trash(keys)` in src/storage/object-store.ts, implemented only by GoogleDriveObjectStore via `PATCH /drive/v3/files/{id}` `{"trashed": true}`), and forward it through CiphertextCachingObjectStore (src/storage/caching-object-store.ts:22-33, which the runtime actually hands to every consumer at coordinator.ts:474-483) with a matching `cache.evict()` for the trashed keys. Three corrections:

(1) An index-only sweep is blind to most of the residue. `replaceEntry` (google-drive-object-store.ts:525-529) removes the superseded entry's fileId from the index on every CAS, and the segment is uploaded before `advanceIndex` (:145-160, :169-182) so every lost race leaves an untracked file too. "Resolving fileIds from the index" therefore cannot see the lost-race orphans or any superseded head. Reclamation must enumerate the Drive segments folder (`workspace.segmentsFolderId`, filtered by `appProperties airshipRole='encrypted-segment-v1'` + `airshipNamespace`, same query shape as google-drive-workspace.ts:90-108) and diff fileIds against the live index.

(2) Drop part (b) — do NOT trash the superseded revision inline after a manifest CAS. It is not safe: a reader that loaded manifest generation N and then calls `readEntry` (encrypted-workspace.ts:171-176) throws "Encrypted workspace file is missing." / "Google Drive encrypted segment is missing." (google-drive-object-store.ts:114) if the object vanished in between, and the Drive index cache TTL of 1500 ms (google-drive-object-store.ts:34) plus multi-context use widens that window. This is precisely why the project's own gate 3 mandates a safety age and a fresh-index recheck. Superseded cloudKeys should be enqueued as candidates for the aged job, not trashed inline.

(3) The referenced set in part (c) is incomplete and would delete live data. coordinator.ts:474-483 wires FOUR consumers onto the same store: EncryptedObjectJournalBackend (state/journal/v1), EncryptedObjectWorkspace (state/workspace/v1), EncryptedProfileCatalogStore (state/profiles/v1, src/profiles/persistence.ts:104) and VaultContextFabricPort (src/vault/context-fabric-port.ts:47). The auditor's set omits profiles. The referenced set must be derived from all four roots (and must fail closed if any root cannot be opened).

Also: order the two-system operation index-entry-first — CAS the entry out of the index, then PATCH `trashed:true` — because a crash after the CAS leaves a folder-visible untracked file that the next sweep recovers, whereas trashing first leaves an index entry whose `get()` hard-throws at google-drive-object-store.ts:114. No cross-system atomicity is achievable, so the "a crash can never orphan a live reference" claim should be restated as "a crash can only leak an untracked file, never break a live reference." Sweeping `evidence.createdKeys` after a successful probe (coordinator.ts:441-448) is fine, but only report keys whose PATCH returned 200 and whose absence a fresh list confirms; keep the existing warning verbatim for unconfirmed keys, for the failed-probe residue path (coordinator.ts:517-523), and for every adapter without trash. Update encrypted-workspace.test.ts:77-91, which currently asserts the retained orphan as intended behavior.

## 5. There is no unlock ceremony at all — the device key auto-opens; WebAuthn PRF is designed in detail and implemented nowhere
`no-unlock-ceremony-passkey-prf-absent` · kind **absent** · effort **large**

**Evidence.** src/ui/app.tsx:1085-1119 — as soon as the backend is "local-device", an effect imports the keyring and calls `openLocalDeviceWorkspaceKey({partition})` with no user gesture. src/storage/local-device-keyring.ts:70-79 simply loads the persisted record and returns `WorkspaceRootKey.fromPersistedHandle(record.handle)` — possession of the browser profile is the only authentication. A repo-wide grep for `navigator.credentials`, `PublicKeyCredential`, `webauthn`, or `prf` returns zero source hits; the only matches are prose in docs/. docs/KEY_CUSTODY_AND_DEVICE_ENROLLMENT.md:45-47 states plainly "Airship does not yet implement passkey PRF unlock, portable device wrappers, cross-device enrollment, wrapper rotation, device revocation…", and lines 135-152 specify the intended ceremony in full (userVerification required, verify UV flag + credential ID + `prf.enabled` + `prf.results.first`, fail closed on absent/ignored/cancelled/wrong-salt).

**Impact.** For the privacy-minded user this is the gap between "encrypted at rest" and "encrypted at rest against someone who has my laptop". Anyone who opens the browser profile — a shared machine, a borrowed laptop, a stolen unlocked device — gets the vault with no prompt. The honesty is intact (the doc says so), but the capability is absent, and it is one of the few security controls a browser genuinely can offer.

**Fix.** Build `src/storage/passkey-prf-wrapper.ts` and make the local-device record a discriminated union so a PRF-wrapped vault stops persisting the raw handle. Corrections to the proposed fix:

1) Wrong crypto primitive. WebCrypto `unwrapKey` cannot produce an HKDF key — `WorkspaceRootKey.import` (src/storage/encrypted-envelope.ts:29) only accepts raw bytes via `importKey("raw", ..., "HKDF", false, ["deriveKey"])`. So: HKDF-SHA-256 the 32-byte `prf.results.first` (with a stored random salt + a fixed info string, e.g. "airship/local-device-passkey-prf/v1") into an AES-GCM key, AES-GCM-decrypt the stored `wrappedSeed` to raw bytes, call `WorkspaceRootKey.import(bytes)`, then `bytes.fill(0)`. Bind `credentialId`, `rpId` and salt into the AES-GCM AAD.

2) There is no "stored seed" to wrap. The seed exists only transiently inside `WorkspaceRecoveryMaterial` (src/vault/recovery.ts:30-70), which exposes only `displayValue` and `workspaceKey`. The wrapper must therefore be minted inside `prepareLocalDeviceWorkspaceKeyEnrollment`'s commit path (src/storage/local-device-keyring.ts:95-183) or inside `importLocalDeviceWorkspaceRecoveryKey` (186-218) — add a scoped seed accessor rather than re-parsing `displayValue`. An already-enrolled vault cannot retrofit PRF silently: its live key is non-extractable (documented at docs/KEY_CUSTODY_AND_DEVICE_ENROLLMENT.md ~173), so opt-in for an existing vault must require re-entering the `airship-wrk-v1.` value. Verify the unwrapped key with the existing `equivalentWorkspaceKeys` / `KEY_EQUIVALENCE_CONTEXT` check (used at lines 154 and 214) before adopting it.

3) Record shape and store semantics. `PersistedWorkspaceKeyRecord` (local-device-keyring.ts:13-18) and its validator `keyRecord` (332+) must become a union: `{version, partition, createdAt, handle}` OR `{version, partition, createdAt, wrapper: {credentialId, salt, wrappedSeed, iv, rpId}}`. The IndexedDB store uses `keyPath: "partition"` and `putIfAbsent` (263-277) refuses overwrite, so enabling PRF must be an explicit replace path, not an add — and the "persisting raw key bytes is never a fallback" comment at 273-274 needs to say that wrapped (never raw) seed bytes are the one permitted alternative. Both `MemoryLocalDeviceKeyHandleStore` and the IndexedDB store need the new shape.

4) Unlock cannot live in the existing effect. Safari requires transient user activation for `navigator.credentials.get({publicKey})`, so src/ui/app.tsx:1083-1131 must, on seeing a wrapper-shaped record, stop auto-opening and instead surface an explicit "Unlock with your passkey" affordance (route through the existing `setVaultSetupOpen(true)` / `LocalDeviceVaultSetup` in src/ui/local-device-vault-setup.tsx, which already owns enrollment and recovery-import via its injected `beginEnrollment` / `importRecovery` seams at lines 38-92). Opt-in registration ("Require a passkey to unlock this Vault") belongs in that same component.

Keep the registration guard (`getClientExtensionResults().prf.enabled === true` or abort with no state written), verify the UV flag in `authenticatorData` and `rawId` equality on assertion, and fail closed on every case in docs/KEY_CUSTODY_AND_DEVICE_ENROLLMENT.md:147-152. Keep `airship-wrk-v1` recovery as the always-available fallback. Feature-detect via `PublicKeyCredential.getClientCapabilities?.()` / `isUserVerifyingPlatformAuthenticatorAvailable()` and report "passkey unlock unavailable on this browser" rather than degrading. Finally, the same change must edit docs/KEY_CUSTODY_AND_DEVICE_ENROLLMENT.md:45-47 and docs/CANON.md:788, which currently state PRF unlock is not implemented — leaving them stale would invert the honesty contract.

## 6. The OPFS ciphertext acceleration cache has no eviction and accumulates every superseded revision forever
`ciphertext-cache-never-evicts` · kind **bug** · effort **medium**

**Evidence.** src/storage/client-ciphertext-cache.ts defines only per-record size ceilings (MAX_HEADER_BYTES, MAX_CIPHERTEXT_BYTES 64 MiB, MAX_PERSISTED_RECORD_BYTES at lines 8-10); a grep for evict/quota/prune/estimate/LRU in that file returns nothing but those constants. src/storage/caching-object-store.ts:137-144 writes every classified object into the cache with `.catch(() => undefined)`, and `remove` is only called on a successful compareAndSwap (line 124). This is mandatory, not optional - without it a lost or corrupt index permanently strands OPFS files that no LRU can ever reclaim, because there is no delete-all path and OPFS entries outlive close(). Implement it as a new worker op in opfsWorkerSource() (line 408) using `for await (const [name, handle] of directory.entries())` plus `(await handle.getFile()).size`, filtering the `p-<43 base64url>.bin` filename shape from `filename()` (line 412); in IndexedDbCiphertextPageBackend (194) via getAllKeys plus stored byteLength; in the memory backend via its Map.

4. Serialize index mutation with navigator.locks keyed on the partition (the pattern already in src/vault/local-device.ts:262-303); two tabs on the same partition share one OPFS directory and the worker's `tail` chain only serializes within a tab. ## 7. Only the context-fabric path streams shards; workspace and Git file reads always move the whole encrypted object
`workspace-reads-never-use-ranges` · kind **inert** · effort **medium**

**Evidence.** A repo-wide grep for `getRange(` outside src/storage/ finds exactly one caller: src/storage/encrypted-segments.ts:138 (used by src/retrieval/context-driver.ts:149). src/vault/encrypted-workspace.ts:171-175 `readEntry` calls `this.store.get(entry.cloudKey)` — the full object — and `readBounded` at lines 73-89 does not range-read at all: when `entry.size > maxBytes` it returns committed metadata with `content: ""` and an explanatory comment that AES-GCM authenticates the complete immutable object. Workspace files may be up to MAX_FILE_BYTES = 16 MiB (line 25).

**Impact.** The master prompt's "only necessary encrypted shards move" is true only for retrieval. Opening a large file in the Editor, or any browser-Git object read, transfers and decrypts the entire object over Drive even for a preview or a header check. The segmented extent format that would make this cheap already exists and is simply not used outside retrieval — this is present-but-inert capability, not an absent one.

**Fix.** Scope the change to text workspace files and the Editor/agent-search preview path; leave Git object reads and binary envelopes alone (they need the whole object anyway).

1. Write path — src/vault/encrypted-workspace.ts write() (101-158): above a threshold (~256 KiB) and only when !isWorkspaceBinaryEnvelope(content), split the UTF-8 plaintext into ~512 KiB blocks cut on code-point boundaries (openFile at line 266-281 decodes with `new TextDecoder("utf-8", { fatal: true })`, so a block that splits a multi-byte sequence throws), seal them with sealSegmentedObject from src/storage/encrypted-segments.ts using namespace FILE_NAMESPACE and logicalId fileLogicalId(path, revision), and putIfAbsent the single concatenated ciphertext. Keep the existing sealFile/single-envelope path for small files and for binary envelopes so nothing regresses.
2. Manifest — store the returned SegmentedObjectDescriptor on the WorkspaceManifestEntry (type at line 29) and validate it in parseManifestEntry (line 316) as an optional field, so entries without it stay on the single-envelope read path. The manifest is the trust anchor: because it is sealed and advanced by CAS (advanceManifest, line 202), the block count/offsets/digests are authenticated and a provider cannot truncate the block list. Also update the putIfAbsent-collision re-verification branch (127-142), which currently re-reads and byte-compares the whole object, to compare the descriptor for the segmented shape.
3. Read path — add a private readSegmentedPrefix used by readBounded (74-89): resolve the blocks covering [0, maxBytes), fetch them with parallel store.getRange calls (the same pattern as src/retrieval/context-driver.ts:149; the Drive adapter already coalesces the index download across concurrent ranges), and verify each with openSegmentRecord (encrypted-segments.ts:152) against the descriptor from the manifest. Do NOT reuse openFile for this: line 273 asserts plaintext.byteLength === expectedSize and will reject any prefix. Return { content: prefix, size: entry.size } so the existing truncation signalling keeps working.
4. UI/docs honesty — src/ui/workspace-view.tsx:461 currently says "Encrypted file not downloaded ... full-object AES-GCM verification is never mislabeled as a range stream"; that copy must change to distinguish a genuinely authenticated segmented prefix from the whole-object case, and docs/COMPUTE_CONTINUUM.md:310-314 plus docs/VAULT_COMPOSITION.md:314 must be updated in the same commit, since they currently disclose the opposite. Do not claim "arbitrary partial-file workspace streaming" — the honest claim is authenticated block-aligned prefixes for text files.

Do not gate this on any "batched reader from the coalescing fix"; no such prerequisite is needed, per-block parallel getRange already works on every store adapter.

## 8. Local Device range reads decrypt the entire object before slicing
`local-device-range-reads-whole-record` · kind **clunky** · effort **medium**

**Evidence.** src/storage/local-device-object-store.ts:235-252 — `getRange` calls `this.get(key)` (which fetches the sealed record and runs a full AES-GCM `open`) and then returns `record.bytes.slice(start, endExclusive)`. The OPFS backend does support genuine partial file reads — src/storage/local-device-object-store.ts:1191-1216 already uses `file.slice(...)` to read the record prefix, header, and ciphertext separately — but each logical object is sealed as one AEAD blob, so partial decryption is impossible by construction. src/ui/vault-view.tsx:267 tells the user "Matching turns retrieve authenticated ranges from encrypted device shards without a network request."

**Impact.** An 8 KiB context block read from a 64 MiB segmented object reads and decrypts all 64 MiB from OPFS. The claim shown to the user is literally true (no network request) but the implied efficiency is not there, and offline retrieval latency on a large index is far worse than the equivalent Drive path. The capability descriptor is honest — `providerEvidence: "in-process"` in object-store.ts:34 makes no efficiency claim — so this is a performance gap, not a false claim.

**Fix.** Do NOT use the `<storageId>#<blockIndex>` per-block-record variant as written: record ids must pass validateOpaqueId (src/storage/local-device-object-store.ts:1282-1287, strict /^[A-Za-z0-9_-]{43}$/), and extra records would also enter list() (295-329, which fully decrypts every record and compares logical keys), the exportEncryptedBackup inventory digest and MAX_OBJECTS ceiling, and the replaceAll restore authentication — precisely the identity/inventory machinery the fix promises to leave untouched.

Build the envelope-framing variant instead:

1. Block-frame the local sealed record. In `seal` (src/storage/local-device-object-store.ts:423-448), instead of one AES-GCM blob over `encodePlainRecord(logicalKey, bytes)`, emit fixed-size frames of `NONCE(12) || ct || TAG(16)` over a constant BLOCK_BYTES (e.g. 1 MiB) of plaintext. Keep the layout fully derivable from already-AAD-covered fields so no new unauthenticated header field is introduced: block count and each block's file offset follow from `plaintextSize` plus the constant BLOCK_BYTES. Extend `recordAad` (currently {id, revision, etag, updatedAt, plaintextSize}) with `blockIndex` and `blockCount` so truncation, reordering, and cross-object splicing all fail closed; keep the logical key bound by putting its digest in the per-block AAD, since `encodePlainRecord`'s in-plaintext key check (473-475) is no longer observable from a partial read.

2. Add a range method to the `LocalDeviceRecordBackend` interface (declared around line 264): e.g. `getFrames(id, firstFrame, lastFrame): Promise<{ frames: Uint8Array; plaintextSize: number; revision: string; etag: string; updatedAt: string } | undefined>`. Implement it in the OPFS backend with `file.slice(OPFS_RECORD_PREFIX_BYTES + headerLength + firstFrame * FRAME_BYTES, ...)` reusing the existing prefix/header parse in readOpfsRecord (1185-1220). IndexedDB and memory backends can default to reading the record and slicing — they still skip the AES-GCM decrypt and both sha256 passes over untouched blocks.

3. Rewrite `getRange` (235-255) to resolve only the covering frames. Two invariants must be preserved without a full read: the bounds check at 244 and `totalSize` at 253 must come from the sealed header's `plaintextSize`, which is AAD-covered and therefore trustworthy, because `readEncryptedSegment` hard-fails when `range.totalSize !== descriptor.ciphertextLength` (src/storage/encrypted-segments.ts:140-142). Note the whole-record `ciphertextDigest` check (452) and whole-plaintext `etag` check (480) are structurally unavailable on a partial read; binding `etag` into every frame's AAD preserves version-binding, and this is the same authentication strength the cloud segmented path already ships.

4. Version the layout: bump the record `version` field (SealedLocalRecord.version is currently the literal 1) and DEVICE_SCHEMA_VERSION, keeping v1 records readable through the existing migration path so exportEncryptedBackup/restoreEncryptedBackup and the identity anchor (verifyOrInitialize, 185-218) stay untouched.

Cheaper interim mitigation worth pricing first: wire a CiphertextCachingObjectStore around the local-device facade in src/vault/local-device.ts:115 (its `classifyVaultImmutableCiphertext` already recognizes `context/segments/`), which removes repeat full decrypts even though the first read of each expert block still costs a whole-object pass.
