# Hermes-level context engine (compression, smart references, lineage, Memory+Context fusion, retrieval quality)

**Verdict.** The skeleton is real and unusually rigorous — this is not a mock. Compression is genuinely iterative (prior projection + new delta only, digest-chained, never a full re-summarization), the 80-85% band is enforced at the type level, every summary is verifiable against journal digests, and Memory really is fused into every turn at the agent seam (tool-bundle.ts:26 -> agent.ts:152-165), not stitched at the UI. Turn-path lineage is the most complete I have seen in a browser agent: source revision, content digest, extractor, chunker, embedding provider/dimensions/posture, index format, persistence, session/profile/workspace scope, query digest and selection digest, canonicalized and cryptographically verified before the model can see it. But four things keep it short of "Hermes-level" in practice. (1) The iterative summary has no second tier: deltas are appended into a 48 KB projection and, at ~4 compressions, the oldest deltas are silently dropped rather than re-compacted, so long sessions permanently lose their early context. (2) Compression runs exactly once per turn, before a 32-step tool loop, so the loop itself can overflow the window it was supposed to protect — and the trigger fires on a bytes/3.6 guess while real prompt_tokens are already sitting in the journal, unused. (3) The "smart reference" storage story is metadata deduplication only; there is no content-addressed chunk dedup, and every encrypted index publish uploads a whole new object and never deletes the old one, so vault index storage grows monotonically. The ledger is right that 60-78% is unproven — but today the honest measured number would be small, because the lever that produces a big number has not been built. (4) Retrieval quality is the weakest link: the default engine is a feature-hash bag-of-words whose "dense" score is really noisy lexical overlap, and the real semantic pack is served by a Vite dev/preview middleware only — it is not emitted into dist/, so on a deployed static build the visible "Local semantic" button 404s. WebGPU is detected and then used only to pick a quantization inside semantic mode; it never promotes semantic to default. Nothing here is dishonest — the docs and ledger are careful — but a normal user of a deployed Airship today gets lexical retrieval, weak profile-memory recall that degrades as their messages get longer, and no visible evidence that any of the fusion happened.

## 1. Iterative summary has no meta-compaction tier; oldest deltas are dropped at 48 KB
`summary-chain-drops-oldest-deltas` · kind **absent** · effort **large**

**Evidence.** src/core/context-summary-projection.ts:6 sets MAX_SUMMARY_PROJECTION_BYTES = 48*1024; src/core/context-policy.ts:9 sets DEFAULT_MAX_DELTA_BYTES = 12*1024. materializeContextSummary (context-summary-projection.ts:134-165) walks the digest chain and concatenates every delta via boundedSummaryChainProjection (:174-193), which, when the concatenation exceeds the budget, picks the longest SUFFIX of the chain that fits and replaces the omitted prefix with renderOmittedSummaryPrefix (:214-218): '[N earlier summary deltas omitted from the active projection...]'. planContextCompression (context-compressor.ts:200-231) only ever summarizes events in (coveredThrough, cutoff]; no code path re-summarizes or merges existing deltas.

**Impact.** After roughly four compressions (4 x 12 KB > 48 KB minus framing) the earliest summarized conversation stops being sent to the model. The user sees a session that 'remembers' and then quietly forgets its own beginning. The journal still has it, and the marker is honest, but the model cannot use it. This is precisely the property Hermes-style iterative compression exists to avoid: it rewrites the running summary rather than appending and truncating.

**Fix.** Add a second, append-only compaction tier. Touchpoints verified against HEAD:

1. src/core/context-summary-projection.ts:20-45 — extend CanonicalContextSummary with optional `compactionLevel: number` and `compactedSummaryDigests: readonly string[]`, and validate both in canonicalContextSummary (:55-108) alongside the existing bounds (the 64 KB summaryDelta ceiling at :71 already covers the compacted body).
2. src/core/context-summary-projection.ts:138-152 — the chain walk currently follows previousSummaryDigest strictly and requires chain[0].sourceStartSequence === 1. Build a lookup from each compaction node's LAST covered digest to that node; when the backward walk reaches a summary whose digest is subsumed, substitute the compaction node and stop. Keep the sourceStart=1 invariant: a level-n node inherits sourceStartSequence from the summaries it subsumes, so its anchors are still real journal sequences and verifyContextSummary's event lookup (context-compressor.ts:297-300) keeps working unchanged.
3. src/core/context-compressor.ts — add planSummaryCompaction() next to planContextCompression (:177-287). Trigger it when materializeContextSummary reports bytes at/near the 48 KB bound, feed the summarizer the concatenated deltas + digests of chain[0..k] (reuse ContextSummaryRequest, with maximumOutputBytes = options.maxSummaryDeltaBytes), and commit sourceStartSequence = chain[0].sourceStartSequence, sourceEndSequence = chain[k].sourceEndSequence, compactedSummaryDigests = [chain[0..k].summaryDigest], compactionLevel = max(level of subsumed)+1. Critically, planContextCompression's `prior = canonicalSummaries(events).at(-1)` (:204) must keep resolving to the newest LEVEL-0 summary so coveredThrough and the (coveredThrough, cutoff] range stay correct once compaction events are interleaved.
4. src/core/context-compressor.ts:289-307 — verifyContextSummary needs a compaction branch: assert compactedSummaryDigests is exactly the contiguous prefix run present in the journal, that its endpoints match sourceStart/EndSequence, and relax the terminal `previousSummaryDigest === undefined && sourceStartSequence === 1` rule to also accept a level-n node.
5. src/core/session-audit.ts:35-56 — a new `context.summary.compacted` type MUST be added to KNOWN_EVENT_TYPES or it trips the unknown-type finding at :629; add a sibling branch to the context.summary.updated handler at :663-706. summaryMatchesContextPolicy (:1221-1256) cannot be reused as-is for a compaction: its `estimatedTokensBefore/contextWindowTokens >= threshold` check and its `turn.completed after sourceEndSequence === preserveRecentTurns` check are both meaningless for a node whose range is old — give compaction its own predicate.
6. src/core/agent.ts:203-209 — add the emission path (the existing site only appends context.summary.updated).

Cheaper variant worth considering: instead of a new event type, keep `context.summary.updated` and add the optional compactionLevel/compactedSummaryDigests fields to the existing payload. That avoids steps 5's KNOWN_EVENT_TYPES/new-branch work entirely, at the cost of branching inside the one existing audit handler.

Also fix the independent scaling bug the finding exposes: MAX_SUMMARY_PROJECTION_BYTES (context-summary-projection.ts:6) is a fixed 48 KB regardless of the session's pinned contextWindowTokens, so a 200K- or 1M-token window still gets 48 KB of summary. Derive the projection budget from contextWindowTokens (it is already threaded through CanonicalContextSummary.contextWindowTokens) with 48 KB as the floor.

## 2. Compression runs once per turn, before a 32-step tool loop that can overflow the window
`no-compression-inside-tool-loop` · kind **bug** · effort **medium**

**Evidence.** src/core/agent.ts:178-209 calls planContextCompression once, then src/core/agent.ts:211 opens `for (let step = 0; step < maxSteps; step += 1)`. Inside the loop, agent.ts:213-217 re-reads the whole journal and re-materializes messages every step, but never re-evaluates the threshold. maxSteps defaults to 8 (agent.ts:78) and the production app passes 32 (src/ui/app.tsx:2232). Tool results are appended as full-content events (agent.ts:351-364) with no per-turn output ceiling other than the per-result tool limits.

**Impact.** A single agent turn that reads a few large files or runs a verbose command can add hundreds of KB of tool output to the message array after the only compression check has already passed. The turn then fails at the provider with a context-length error instead of compressing, and the user loses the whole turn. The 80-85% guarantee is a guarantee about turn boundaries, not about the context actually sent.

**Fix.** Do NOT hoist src/core/agent.ts:178-209 into the step loop. Blockers: (a) src/core/session-audit.ts:663-690 only permits context.summary.updated outside a turn or as pre-inference turn preprocessing (active.step === -1, no inference, no tool events), so a mid-loop append is audited as CONTEXT_SUMMARY_INVALID and src/ui/app.tsx:2795-2798 refuses to resume the session; (b) src/core/context-compressor.ts:206-214 can only summarize a prefix ending at a turn.completed cutoff, so the current turn's tool.resulted bytes are never compressible and the cited failure is untouched.

Buildable in-browser remedy, in priority order:
1. In-loop budget guard (small, no protocol change): in src/core/agent.ts, immediately after materializeMessages at line 214, call the already-exported estimateInferenceTokens (src/core/context-compressor.ts:159) with session.manifest.systemPrompt and session.manifest.tools, and compare against pinnedContextCompression.contextWindowTokens. If the projected request exceeds the pinned window, fail closed locally before transport.stream() with a specific message (e.g. 'This turn's tool output exceeded the session's pinned N-token context window'). The turn already fails today; this makes it a deterministic, auditable turn.failed with an actionable reason instead of a provider-dependent context-length error, and it costs one estimate per step.
2. Per-turn tool-output budget (fixes the actual loss): track cumulative tool.resulted bytes for the turn in src/core/agent.ts alongside the existing per-result 1 MiB cap in src/tools/registry.ts:14,136-137. When appending a result would push the projected estimate past the window, store the result truncated with an explicit marker and a metadata flag — the same honesty pattern already used by src/tools/network-tools.ts (`truncated: true` in content and metadata) — so the turn survives and the transcript never silently misrepresents what the model saw.
3. Only if compressing the prior prefix mid-turn is also wanted, treat it as a protocol-v2 amendment, not a hoist: add a third accepted position to the context.summary.updated branch in src/core/session-audit.ts (mid-turn, event.turnId === active.id, no operationId, summary.sourceEndSequence strictly below the current turn's turn.requested sequence), and fix the bookkeeping at session-audit.ts:~697 (`active.request.messageIndex = messages.length - 1`), which assumes the summary message lands immediately after the user request — mid-turn the last materialized message is a tool message, so that index would be wrong. Ship it with an agent-compression.test.ts case proving the resulting journal still audits as verified.

Also correct the impact framing: docs/CONTEXT_FABRIC.md:61-71 already states compression 'summarizes only boundaries ending at turn.completed' and preserves recent complete turns, so the turn-boundary scope is documented and is not itself a broken promise. The undocumented, real defect is that there is no in-loop context budget guard at all before the provider call.

## 3. Compression trigger uses a bytes/3.6 guess while real prompt_tokens sit unused in the journal
`token-estimate-never-calibrated` · kind **inert** · effort **medium**

**Evidence.** src/core/context-compressor.ts:43 defines BYTES_PER_ESTIMATED_TOKEN = 3.6 and estimateInferenceTokens (:159-170) divides the stableStringify byte length of systemPrompt+messages+tools by it. Meanwhile agent.ts:269-271 journals every provider usage event; src/core/contracts.ts:194 types it as `{ type: "usage"; inputTokens?: number; outputTokens?: number }`; src/inference/chutes/openai.ts:51 maps the real `usage.prompt_tokens` into it. grep shows the only consumers of inputTokens are src/billing/client.ts:343-348 and src/ui/billing-view.tsx:158-159 — the compression path never reads it.

**Impact.** Byte-per-token ratios vary from ~2.5 (minified JSON tool output, CJK) to ~4.5 (English prose). A fixed 3.6 can be off by 25-40%, which is larger than the entire 80-85% trigger band the policy so carefully constrains. Compression therefore fires early (wasting a summarizer call and discarding recent detail) or late (overflowing). Ground truth for this exact session, model and tokenizer is already durably recorded one event away.

**Fix.** Calibrate the byte-per-token ratio from provider-reported usage already in the journal, but build it as follows (the auditor's placement and reconstruction are not workable as written):

1. Calibrate in src/core/agent.ts, not in the compressor. `materializeMessages` is exported from src/core/agent.ts:667 and src/core/agent.ts:31 already imports `planContextCompression` from context-compressor.ts, so putting the calibrator in context-compressor.ts creates an agent<->compressor import cycle. Add `calibrateBytesPerToken(events, { systemPrompt, tools, materialize })` to context-compressor.ts as a pure function that takes the materializer as an argument, and call it from agent.ts:179 where `existingEvents` (agent.ts:96, the full journal) is already in scope.

2. Reconstruct the sample, do not read it from the event. src/core/agent.ts:229-245 records only `{ step, providerId, model, posture, requestDigest, idempotencyKey }` in `inference.started` — the messages are NOT in the payload, only inside the sha256 `requestDigest`. To get the byte length actually sent at that step you must re-materialize the prefix: find the most recent `inference.usage` event with a numeric `inputTokens`, find the `inference.started` event sharing its `operationId` (agent.ts:270 sets it to the same `requestId`), then call `materializeMessages(events.filter(e => e.sequence < started.sequence), { allowEmbeddedContext: manifest.turnContext === undefined, allowSelectedContext: manifest.turnContext !== "disabled" })` — matching the options at agent.ts:214-218 exactly (note the step loop leaves `injectLatestContext` at its default, unlike the pre-turn call at agent.ts:181-185).

3. Use the estimator's own basis. `bytesPerToken = byteLength(stableStringify({ systemPrompt, messages, tools })) / inputTokens`, i.e. the identical object shape built in estimateInferenceTokens (context-compressor.ts:164-168), using the manifest's immutable `systemPrompt` and `tools`. Dividing messages-only bytes by full `prompt_tokens` (as proposed) is systematically biased low and would make the estimator over-count and fire early.

4. Keep the bounded EMA and the [2.0, 6.0] clamp, defaulting to 3.6 when no usage has been observed. The clamp is load-bearing for a reason the finding does not state: `prompt_tokens` is adversary-controlled input flowing into a client-side control decision, so an unclamped ratio would let a hostile provider either suppress compression until every turn overflows or force a summarizer call on every turn.

5. Thread it through as `bytesPerToken?: number` on `planContextCompression` (context-compressor.ts:177-187) and use it in all three call sites of the constant (:169, :256, :432) so `estimatedTokensBefore` and `estimatedTokensAfter` share one basis.

6. If you record the value used inside the commitment, you must also extend the canonicalizer or verification breaks: `canonicalContextSummary` (src/core/context-summary-projection.ts:54-108) rebuilds the object field-by-field and silently drops unknown keys, so a `bytesPerToken` field included in the sha256 at context-compressor.ts:285 would fail the digest re-check in `verifyContextSummary` (context-compressor.ts:293-296) once the summary is read back through `canonicalSummaries`. Add it as an optional field to the `CanonicalContextSummary` type (projection.ts:20-45), to the validation block, and to the returned object so pre-existing journals without it still verify; leave `algorithm: "airship-reference-delta-v1"` intact since the field is optional. No change is needed in src/core/session-audit.ts:1234, which only checks `estimatedTokensBefore / contextWindowTokens >= threshold` against the recorded values.

## 5. Profile-memory recall collapses as the user's message gets longer
`memory-recall-normalized-by-query-length` · kind **bug** · effort **medium**

**Evidence.** src/retrieval/federated-turn-context.ts:148-164 rankMemories scores each record as `min(1, 0.75 * max(lexical, phrase) + 0.25 * ((index+1)/records.length))` where `lexical = overlap / queryTokens.size` (:156) and `phrase` requires the ENTIRE lowercased query to appear as a substring (:157). Candidates are then filtered by `score > 0.25` (:162) and capped at MAX_PROFILE_MEMORY_HITS = 3 (:17, used at :56).

**Impact.** Recall is divided by the length of the user's turn, not by the memory's length, and there is no IDF. A 25-token question that shares one distinctive token with a stored memory scores 0.75*(1/25) = 0.03 plus a recency term; only the single newest record (recency 0.25) clears the 0.25 gate. A memory sitting in the middle of the list needs roughly 5 of 25 query tokens to match. In practice the user writes a normal multi-sentence message and their remembered facts are simply not retrieved, while the same facts would be found by a one-word query. This is the difference between a memory system that works and one that appears to work in demos.

**Fix.** Replace rankMemories in /Users/chrisk/chutes-jumpmaster/airship/src/retrieval/federated-turn-context.ts:148-164 with BM25 (k1=1.2, b=0.75) over the already-scoped records from scopedMemories (:135-146): tokenize `${record.content}\n${record.source}` once per record with the existing tokenize() (:186-188), build df over that bounded set (<=512 per src/tools/memory-tools.ts:8), and score sum-over-query-terms of idf(t)*(tf*(k1+1))/(tf + k1*(1 - b + b*len/avgLen)). Drop the whole-query substring `phrase` term (:157) in favour of a query-bigram overlap bonus. Two corrections to the proposal as written: (a) "normalize by the best achievable score for that query" must mean the THEORETICAL ideal-document score (every query term present at saturating tf and average document length), NOT the observed maximum over the corpus — normalizing by the observed max pins the best candidate at 1.0 on every turn, so the `> 0.25` gate could never return empty and an irrelevant memory would be injected as context on every single turn, converting a recall bug into a precision/honesty bug; (b) keep the recency prior strictly below the threshold (as today, 0.25 max against a strict `>` gate) so a genuinely no-match turn still injects nothing. Keep lineage shape untouched and change only indexFormat at :181 from "bounded-lexical-recent-v1" to "bounded-bm25-recent-v1"; that field is a free string validated only by boundedString(...,256) at src/core/context-selection.ts:352, nothing asserts the old literal, and verifyContextSelection does not re-derive scores, so no sealed-record contract breaks. Also update the now-stale docs/MEMORY_CONTEXT_SCOPE.md:17 ("does not yet automatically inject explicit profile memories"), which the code at federated-turn-context.ts:49-71 already contradicts. Existing tests in src/retrieval/federated-turn-context.test.ts use short queries ("turbine pressure", "quartz") and keep passing; add a regression test asserting that a multi-sentence question containing the memory's distinctive terms still yields a profile-memory hit.

## 6. The same profile-memory corpus is searched three different ways with three different results

## 7. Full lineage exists on the turn seam but is stripped from all three agent-facing retrieval tools
`lineage-dropped-on-agent-tool-retrieval` · kind **bug** · effort **medium**

**Evidence.** The turn path is complete: FederatedTurnContextProvider seals retriever, scope (sessionId, profileId, profileRevision, memoryScope, workspaceId) and per-generation sourceRevision/sourceDigest/extractor/chunker/embedding{provider,dimensions,posture}/indexFormat/persistence (src/retrieval/federated-turn-context.ts:94-131), verified in src/core/agent.ts:480-490 before it can reach the model. 2) src/core/context-selection.ts:41 and :304-306 — if tool payloads are to reuse CanonicalContextLineage, add a distinct retriever id (e.g. "airship-workspace-tool-search-v1") to both the type union and canonicalLineage's check; reusing "airship-workspace-turn-context-v1" for a tool call would misdescribe the retriever. This enum is referenced nowhere else outside the three providers, so the change is local.

3) src/tools/federated-memory.ts:160-167 — same lineage block for the workspace group (note limitPerGroup max is 12 at :59, likewise above MAX_HITS=8, so the same clamp-or-label choice applies).

4) src/tools/federated-memory.ts:153-159 — export `memoryLineage` from src/retrieval/federated-turn-context.ts:166 (or lift it into a shared module) and call it with the already-read `file` from :100 to attach the profile-memory generation (sourceRevision = file.revision, sourceDigest = sha256(file.content), extractor "airship-explicit-memory-v2", chunker "record-boundary-v1", indexFormat "bounded-lexical-recent-v1", persistence "memory-only"). ## 8. "Smart references" dedupe metadata only; chunk payloads and vault index objects are never deduplicated
`no-content-addressed-payload-dedup` · kind **absent** · effort **very-large**

**Evidence.** Two real reference mechanisms exist: the summary chain stores only the new delta plus previousSummaryDigest (src/core/context-compressor.ts:263-286), and v2 selection hits point at one shared generation record via lineageRef instead of repeating metadata per hit (src/core/context-selection.ts:18-22, 289-300). Neither avoids restoring a payload. Chunk identity is `sha256(path\0revision\0chunkIndex\0text)` (src/indexing/incremental-indexer.ts:162), so the same paragraph in two files, or an unchanged paragraph in a new file revision, produces two distinct chunks with two full copies of the text and two full vectors; indexFile removes and re-embeds the whole file on any edit (:172-174). publishContextGeneration seals one whole new segmented object per generation and writes it with putIfAbsent under `context/segments/<objectId>` (src/retrieval/publisher.ts:60-76) with no cross-generation block reuse, and grep shows no delete of any prior context segment anywhere in src/retrieval/publisher.ts or src/vault/context-fabric-port.ts.

**Impact.** This is the missing lever behind the unproven 60-78% claim. Today a one-line edit to one file re-embeds that entire file, and a republish of the encrypted index re-uploads and re-stores the entire index while the previous generation stays in the vault forever. For the encrypted-vault path storage does not fall by 60-78% — it rises monotonically with every publish. Any honest benchmark run against the current code would produce a small number, which is exactly why the ledger cannot yet substantiate a large one.

**Fix.** Two independently shippable pieces; (b) needs more than the auditor stated.

(a) Chunk-level content addressing -- as proposed, buildable in-browser today.
- src/indexing/incremental-indexer.ts:162: change `id` to sha256 of the chunk text alone; add path/revision/chunkIndex as separate occurrence fields on EmbeddedChunk (src/indexing/contracts.ts:15-24).
- src/indexing/flat-index.ts: store one {text, tokens, vector} record per content id plus an occurrence list; removeByPath drops occurrences and only evicts the payload when its last occurrence goes. search() (flat-index.ts:16-33) must emit one SearchHit per occurrence, not per payload, so ranking behavior is unchanged.
- src/indexing/incremental-indexer.ts:149-157: skip the embed() call for any chunk whose content id is already present, which makes re-indexing an edited file near-free for untouched paragraphs.
- src/indexing/client-context-engine.ts validateChunks (~line 610): change the duplicate check from `chunk.id` to the tuple (contentId, path, chunkIndex).
- src/retrieval/publisher.ts:43-47 still requires each chunk.id to match /^sha256:.../ and to carry path/revision/chunkIndex, so a content-id scheme satisfies it unchanged.
- Note the auditor omitted: (a) alone saves embedding compute and local memory but NOT published bytes, because src/retrieval/codec.ts:23-39 emits one full record per chunk. To convert (a) into stored-byte savings, StoredExpertBlock must gain a payload table plus an occurrence list, with decodeExpertBlock (codec.ts:41-48) rehydrating occurrences.

(b) Vault block reuse -- proposal is right in outline but blocked by two things it does not mention.
- Give publishContextGeneration a `previous?: ContextRoutingMirror` arg, hash each encodeExpertBlock output, and for a matching hash carry the PREVIOUS mirror's { cloudKey, descriptor } entry forward into the new mirror's `objects` map, pointing the new ContextExpert at the old objectId/blockId. The mirror shape already supports this: `objects` is a map and each expert carries objectId + blockId (src/retrieval/publisher.ts:100-104, src/retrieval/context-driver.ts:145-147).
- BLOCKER 1 (missed): cross-generation reuse currently fails closed at read time. src/retrieval/context-driver.ts:156 passes expectedLogicalId = `${mirror.workspaceId}/${mirror.generation}`, and validateDescriptor at src/storage/encrypted-segments.ts:190-196 recomputes opaqueObjectId(`${namespace}\0${expectedLogicalId}`) and throws "Encrypted segment object identifier does not match." for any descriptor from an earlier generation. The fix must record a per-object logicalId (or generation) on each entry of ContextRoutingMirror.objects (src/retrieval/contracts.ts) and have fetchExpert verify each descriptor against ITS OWN recorded logicalId, while still asserting that logicalId's workspace prefix equals mirror.workspaceId so the workspace binding survives. Decryption itself is fine: openSegmentRecord derives the content key from descriptor.objectId/descriptor.revision (src/storage/encrypted-segments.ts:164), so a carried-forward descriptor opens correctly. Because this loosens the "generation-fenced reads" property credited at docs/MASTER_PROMPT_ACCEPTANCE.md:78, add explicit negative tests in src/retrieval/context-driver.test.ts and src/vault/context-fabric-port.test.ts proving a foreign-workspace or unlisted objectId is still rejected.
- BLOCKER 2 (missed): there is no delete to build retention on. src/storage/object-store.ts:47-58 defines only get/getRange/putIfAbsent/compareAndSwap/list, and no adapter implements delete (the only delete( hits under src/storage are IndexedDB cache eviction in client-ciphertext-cache.ts:186,219). Retention therefore requires adding `delete(key, signal)` to the ObjectStore interface and to every adapter -- memory, direct, s3, google-drive (files.delete), and local-device (OPFS/IndexedDB removal) -- plus a capabilities flag, before a "delete segments no mirror references" sweep can exist. Also note src/vault/context-fabric-port.ts keeps exactly one mirror at CONTEXT_ROUTING_MIRROR_PATH, so the sweep has only the current mirror as its liveness root; it must run after the new mirror write commits, or a crash between publish and mirror write will orphan the new segment instead of the old one.

Finally, whatever benchmark backs the 60-78% number must be added as a real fixture; grepping src/, tests/ and e2e/ for reduction|savings currently returns nothing, so docs/MASTER_PROMPT_ACCEPTANCE.md:74's "a deterministic fixture proves a substantial reduction" has no locatable storage-reduction fixture behind it.

## 10. The memory relationship graph is a real engine that no retrieval path consults
`memory-graph-never-influences-retrieval` · kind **inert** · effort **large**

**Evidence.** src/memory-graph/derive.ts is 1023 lines that build session/message/workspace-file/profile/skill/term nodes with contains/follows/uses-profile/uses-skill/references-file/mentions/co-occurs edges, plus searchNodes (:660) and selectNeighborhood (:704), bounded at 5000 nodes / 20000 edges (:21-35). grep for 'memory-graph' outside src/memory-graph/ returns only src/deferred-capabilities.ts:14, src/ui/memory-controls.tsx:2, src/ui/memory-view.tsx:8 and src/ui/memory-relationships.ts:1 — all rendering. **Fix.** Same idea, three corrections that the proposed version gets wrong.

(1) THE LINEAGE FIELD AS PROPOSED BREAKS EVERY TURN. Adding `reranker: 'memory-graph-affinity-v1'` to a workspace generation is silently stripped by the whitelist in `canonicalGeneration` (src/core/context-selection.ts:347-377), so `canonicalContextSelection` returns an object that no longer matches the sealed `selectionDigest`; src/core/agent.ts:480-483 then throws "The turn-context provider returned a selection whose commitments did not verify" on every turn, and replay would raise TURN_CONTEXT_DIGEST_MISMATCH (src/core/session-audit.ts:832-834). The disclosure must be schema-first: extend `CanonicalContextGeneration` (src/core/context-selection.ts:24-38) or `CanonicalContextLineage` (:40-50) with an optional bounded `reranker` string, accept and re-emit it in `canonicalGeneration`/`canonicalLineage` (:302-377), and keep it optional so historical v2 events still canonicalize. If a new retriever id is preferred instead, note the id is an enum in two places (:41 and :304-306) and both must be widened.

(2) RE-RANKING AT federated-turn-context.ts:72-92 CAN ONLY PERMUTE ~8 ITEMS. The inner workspace provider is invoked with the same `maxHits` (:36-40) and clamps to 8 (src/retrieval/client-context-runtime.ts:127; canonical MAX_HITS = 8 at src/core/context-selection.ts:5), so by the time the federated provider sees hits the tail is already discarded and a graph prior cannot surface "the file referenced by this thread". To get the claimed effect, over-fetch where the engine allows it: `ClientContextEngine.search` accepts a limit up to 50 (src/indexing/client-context-engine.ts:322), so widen the seam so `ClientContextRuntime.selectForTurn` (src/retrieval/client-context-runtime.ts:129) requests e.g. `min(50, maxHits * 4)` candidates, applies the bounded prior, then cuts to `maxHits`. Because `ClientContextRuntime` holds no `EventJournal`, the prior must be injected — pass an optional `rerank?: (hits) => hits` / affinity map through `ClientContextRuntimeOptions` or `TurnContextRequest`, computed by `FederatedTurnContextProvider`, which does hold the journal.

(3) IMPORT PATH AND DERIVATION COST. Import `graphAffinity` from `../memory-graph/derive` directly, never the `../memory-graph` barrel — src/memory-graph/index.ts:3 re-exports `MemoryGraphRenderer`, which drags preact + the dynamically-loaded sigma/graphology WebGL renderer into the per-turn path. Derive the turn-time graph with a cheap option set (`deriveTerms: false` or a small `maxTermDocuments`, small `maxTextScanChars`, `maxFiles` bounded) rather than DEFAULT_OPTIONS, since the UI itself treats full derivation as heavy enough to defer behind a route; the existing DERIVE_CACHE (derive.ts:100-119) is keyed on a stableStringify of the whole input, so pass a stable minimal input or the cache will miss every turn.

Everything else in the proposal stands: bound the multiplier (<= 1.25x), apply it only to `corpus === "workspace"` hits, never let it introduce a path the index did not return, and update docs/MEMORY_RELATIONSHIP_GRAPH.md ("optional visual surface") plus the CANON entry so they stop describing the graph as view-only once it participates in retrieval.
