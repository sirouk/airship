# Claude Code / Codex-level tool power

**Verdict.** The registered tool surface is real, well-typed, and unusually disciplined — 30 tools, every one backed by a browser executor, all schemas compiled by a fail-closed JSON-Schema dialect (src/tools/schema.ts) and shipped to the model both as an `[Airship installed tool manifest]` prompt section (src/core/operating-charter.ts:134-139) and as genuine function-calling `parameters`/`input_schema` (src/inference/providers/browser-cloud.ts:697,714; src/inference/chutes/openai.ts:246). Against Claude Code the coverage is: read yes, write yes, edit yes, multi-edit yes (text_editor, 32 files/call), todo yes (list_tasks/update_tasks), web-fetch yes (CORS-bounded), bash no, glob no, grep partial (literal-only, hard 512-file cap with no continuation), task/sub-agent no, web-search no, patch/diff-apply no. The headline problem is not honesty — the ledger is accurate — it is that the strongest claims are the thinnest. "Programmatic text_editor calls from executed code" is Implemented but the bridge only lets code choose whether and in what order to fire calls whose arguments were frozen in the approval manifest (`airship.call(id)` takes an id and nothing else, src/tools/execution-tools.ts:1141-1151), so read-compute-edit still cannot collapse into one turn. Meanwhile a genuine POSIX-ish shell (WebContainer `jsh`) is already spawned in this very codebase for the human terminal (src/terminal/manager.ts:190) and is reachable through `execute_node_project` today, yet that tool's own description tells the model "No shell string or host Bash is involved" — a real capability that is inert and actively discouraged. Approvals are correct but brutal for agentic work: the only affirmative button is "Allow once" and tool calls execute serially, so a 20-step run in ask-first mode is literally 20 modals with no session- or tool-scoped grant. Several fully-implemented Git operations (push, worktree create/remove) are exposed to the human UI but withheld from the model with no declaration that they exist.

## 1. A real WebContainer `jsh` shell already runs in-page for the human but no model tool exposes it, and execute_node_project's description denies it exists
`no-shell-tool-while-jsh-runs` · kind **inert** · effort **medium**

**Evidence.** src/terminal/manager.ts:190 spawns `host.spawn("jsh", [], ...)` for the interactive human Terminal with a mounted workspace (src/terminal/workspace-sync.ts). src/execution/node-webcontainer-adapter.ts:62-80 validates only the *command name* against COMMAND_PATTERN `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$` (line 14) and then passes `args` verbatim to `container.spawn(command, args, {cwd: jobRoot, env, terminal})` — so `command:"jsh", args:["-c","cd src && grep -rn foo . | head"]` is already legal and would run a real shell pipeline over the mounted workspace snapshot with writeBack. Yet src/tools/execution-tool-proxies.ts:113 tells the model the tool is "No shell string or host Bash is involved", and the capability record at src/execution/node-webcontainer-adapter.ts:42-43 honestly says `commandInterface: "direct-process", shell: "webcontainer-jsh"` — a field the model only sees via inspect_execution_runtimes. docs/MASTER_PROMPT_ACCEPTANCE.md:56 correctly marks WASIX Bash Unavailable, but nothing marks jsh as reachable.

**Impact.** The single largest Claude-Code parity gap — multi-command shell workflows (chained greps, find, test-and-inspect loops, `&&` sequencing) — is unavailable to the agent even though the runtime to serve it is already activated, mounted, and cancellable in the same tab. The model is additionally told a false negative, so it will never even try.

**Fix.** Gate first, then ship. (1) Probe before advertising: add an opt-in case to e2e/live-webcontainer.spec.ts (guarded by AIRSHIP_LIVE_WEBCONTAINER=1, alongside the existing "opt-in live WebContainer executes Node entirely in the browser tab" test) proving `jsh -c 'exit 7'` returns exitCode 7, `jsh -c 'cd sub && printf x > out.txt'` produces an adopted writeBack change at exitCode 0 and adopts nothing at nonzero, and that AbortSignal kills the process. Do NOT put this in e2e/browser-worker.spec.ts — line 336 of that file asserts node-webcontainer is not `ready` there. Optionally mirror the terminal-level proof in e2e/master-browser-acceptance.spec.ts:175. (2) Only if the probe passes, add `execute_shell_command` in src/tools/execution-tools.ts (registered form) plus a byte-identical frozen definition in src/tools/execution-tool-proxies.ts EXECUTION_TOOL_DEFINITIONS and a matching `case "execute_shell_command"` in the executeExecutionTool dispatch in src/tools/execution-tools.ts (~line 476-506) so proxy and pack stay in sync. Schema { workspaceRoot, script (string, maxLength 16k), env, timeoutMs (1_000-120_000), writeBack }, effect "network", requiring workspaceRoot+script. Description must say: "Run one WebContainer jsh script (BusyBox-class builtins, pipes, && sequencing) over a bounded workspace snapshot. This is not host Bash: no sudo/apt, no host filesystem, no host processes." (3) Widen ExecutionRequest in src/execution/runtime-registry.ts:42-57 with `shellScript?: string`, and in src/execution/node-webcontainer-adapter.ts:60-70 handle it explicitly (force command "jsh", args ["-c", script]) while KEEPING the existing COMMAND_PATTERN rejection for the `command` field so the "never routes a shell expression through a hidden shell" invariant (src/execution/node-webcontainer-adapter.test.ts:68) still holds; add a unit test that shellScript and command are mutually exclusive. (4) Stop the two tools contradicting each other: either reject `command: "jsh"` in execute_node_project (pointing at the new tool), or stop hardcoding `shell: "none"` at src/tools/execution-tools.ts:338 and :505 and report the adapter's capability value instead — as written those receipts contradict src/execution/node-webcontainer-adapter.ts:43. Keep `commandInterface: "direct-process"` for execute_node_project and emit `shell: "webcontainer-jsh"`, `output: "combined"` (WebContainer does not separate stdout/stderr) for the new tool. (5) Reuse the existing gates verbatim: workspace binding required, assertPinnedExecutionTier against the node-webcontainer capability, adapter registered only after activation. (6) Docs: add a docs/MASTER_PROMPT_ACCEPTANCE.md section-3 row "jsh shell command execution — Conditional" citing the new live-webcontainer case, leaving the existing "Bash shell in the browser — Unavailable" row untouched; update the execute_node_project paragraph in docs/BROWSER_EXECUTION_PACKS.md (~line 281, "directly spawns one command without an intermediary shell") to name the new explicit-jsh sibling. Do not touch src/core/operating-charter.ts — it already names jsh correctly and any edit rotates every system-prompt digest.

## 2. search_text silently scans only the alphabetically first 512 files and offers no continuation cursor, so it cannot grep a real repository
`grep-caps-at-512-files` · kind **bug** · effort **medium**

**Evidence.** src/tools/workspace-tools.ts:11 `MAX_SEARCH_FILES = 512`; line 198-199 `const allEntries = await workspace.list(path); const entries = allEntries.slice(0, MAX_SEARCH_FILES);`. src/workspace/memory.ts:28-34 shows `list()` is recursive and sorted by `path.localeCompare`, so the slice keeps the lexicographically first 512 paths. Additional caps: MAX_SEARCH_TOTAL_BYTES 8 MiB (line 13), MAX_SEARCH_FILE_BYTES 512 KiB (line 12), MAX_SEARCH_RESULTS 200 (line 15). The only signal is `metadata.truncated` (line 232-236). The schema (line 174-183) has `path`, `query`, `caseSensitive`, `maxResults` — no offset, no cursor, no include/exclude glob, and `collectLiteralMatches` (line 493-515) does `indexOf` only, so there is no regex.

**Impact.** On any imported repository of realistic size — including Airship's own thousands of files — a search from /workspace scans `.github/`, `docs/`, `e2e/` and never reaches `src/`, returning "No matches" plus a `truncated:true` flag the model has no way to act on. The agent's primary discovery primitive gives confidently wrong negatives, and there is no paging parameter to recover.

**Fix.** All changes in /Users/chrisk/chutes-jumpmaster/airship/src/tools/workspace-tools.ts (searchText, lines 168-251) plus tests; no new platform API, so fully browser-feasible.

(1) Add `include`/`exclude` (bounded arrays of bounded-length glob strings compiled to RegExp) and apply them to `allEntries` BEFORE the MAX_SEARCH_FILES slice at line 199 — ordering is load-bearing; filtering after the slice fixes nothing.

(2) Add `cursor` (string): after filtering, drop entries whose path <= cursor. Both backends return localeCompare-sorted lists (src/workspace/memory.ts:33, src/workspace/indexeddb.ts:59), so this pages deterministically. Return `nextCursor` = path of the last scanned entry whenever the file/byte/result budget is exhausted.

(3) CRITICAL correction the auditor missed: metadata is invisible to the model. src/core/agent.ts:750 and src/core/session-audit.ts:1123,1151 forward only `payload.content` into the inference transcript, so improving `metadata.truncated` alone changes nothing. The truncation disclosure and nextCursor MUST be embedded in `content` on BOTH branches at line 238 — e.g. `No matches in files 1-512 of 601 under /workspace (bounded scan); continue with cursor="/workspace/docs/file-0511.ts"` and, for the match branch, a trailing note that the scan was partial. Optionally also fold `metadata.truncated` into the model-visible path in agent.ts, but the content-level fix is the one that must ship.

(4) Regex: reject the auditor's item (3) as written. A step counter inside collectLiteralMatches cannot bound a JS RegExp — a single `exec()` call runs to completion in the engine and catastrophic backtracking freezes the tab (and the whole browser agent, since this runs on the main thread) no matter what the caller counts. Either drop regex entirely, or gate it fail-closed: validate the pattern against a safe subset (reject nested/adjacent quantifiers and backreferences), cap pattern length and per-line length, use a sticky/global regex with a wall-clock budget checked BETWEEN exec calls, or run the scan in the existing worker with a hard terminate timeout.

(5) Tests in /Users/chrisk/chutes-jumpmaster/airship/src/tools/workspace-tools.test.ts: a >512-file fixture asserting (a) the unscoped call states the bound in `content`, not just metadata, (b) following the returned cursor reaches the last file, (c) `include:["**/*.ts"]` surfaces a match the unfiltered call misses, (d) a hostile regex pattern is refused rather than executed (if regex is added).

## 3. No sub-agent / task-spawning primitive exists; the runtime is strictly one linear turn loop
`no-subagent-task-tool` · kind **absent** · effort **large**

**Evidence.** No tool in any of the 11 registration sites (src/tools/tool-bundle.ts:23-36) spawns a nested agent. src/core/agent.ts:77-458 `runTurn` is a single linear loop with `maxSteps` (default 8, line 78; UI passes 32 at src/ui/app.tsx:2232) and a hard `MAX_TOOL_CALLS_PER_STEP = 64` (line 70). The only nested inference in the codebase is the safety reviewer (src/approvals/model-reviewer.ts:30-42) which is explicitly forbidden to call tools (line 40-41). `list_tasks`/`update_tasks` (src/tools/task-tools.ts) track a plan but nothing executes it. docs/MASTER_PROMPT_ACCEPTANCE.md contains no sub-agent row at all.

**Impact.** Broad exploration tasks ("find every call site of X across this repo and summarize") must burn the parent context window step by step, and there is no way to isolate a noisy search into a disposable context. This is a first-class Claude Code primitive with no analogue here — and, unlike Bash, nothing about the browser prevents it.

**Fix.** Add a `run_subagent` tool (`effect: "execute"`) with `{ instructions, allowedTools: string[], maxSteps (<=8) }`, but wire it through the seams the codebase already uses rather than the ones proposed:

1. Do NOT register it inside src/tools/tool-bundle.ts. `AirshipToolRegistryOptions` (src/tools/airship-tools.ts:17-31) carries no InferenceTransport, and the transport is a per-runtime, user-switchable field (`turnTransport = turnRuntime.transport`, src/ui/app.tsx:2077). Construct the tool in the UI where the transport lives and inject it via the existing `additionalTools` seam (src/tools/airship-tools.ts:31; consumed at src/tools/tool-bundle.ts:33; already used for `providerAvailabilityTool` at src/ui/app.tsx:1504/2752/2910/2993).

2. Drop "register the tool only when a nested transport is available." That contradicts the codebase's manifest-stability convention — `registerLazyExecutionTools` (src/tools/execution-tool-proxies.ts:11-14) deliberately "register[s] stable schemas while leaving the Worker/WASI implementation cold", and `execute_wasix_shell`/`install_execution_runtime` stay registered even though runtime-registry.ts is fail-closed at `unavailable`. Conditional registration would make `toolManifestDigest` connectivity-dependent and trip agent.ts:93-95 ("The tool manifest changed. Fork the session...") on every reconnect. Register unconditionally with a live transport accessor and fail closed inside `execute`.

3. Import runTurn lazily via the existing src/load-agent-runtime.ts, not directly from src/core/agent.ts. src/core/session-manifest.ts:5-9 states the pin is deliberately built "without loading the turn executor"; a static tool-bundle -> agent.ts import would pull the whole turn loop into the tool chunk.

4. Child session construction must satisfy three hard checks in runTurn or it throws: read the parent via `journal.getSession(context.sessionId)` and inherit `providerId`/`model`/`systemPrompt` (agent.ts:85-89 rejects a transport whose `id` differs from the pinned `providerId`); build the child manifest from the SUBSET registry's `definitions()` (agent.ts:90-95 compares `sha256(stableStringify(tools.definitions()))` against `toolManifestDigest`); and leave `turnContext` at the `createSessionManifest` default of "disabled" (src/core/session-manifest.ts:47) unless `ToolRegistry.subset()` also forwards the attached ClientContextRuntime and TurnContextProvider, because agent.ts:467-473 throws "This session requires turn-context retrieval, but no provider is attached." Create it with `journal.createSession(title, manifest)` and set `lineage` to the parent session/turn so the child is auditable.

5. `ToolRegistry.subset(names)` in src/tools/registry.ts should build a fresh ToolRegistry and re-`register()` the selected `RegisteredTool.tool` values (register() at line 59-66 recompiles the schema and re-freezes), and optionally re-attach the same contextRuntime/turnContextProvider instances — attaching the same instance is allowed; only a *different* instance throws (lines 40, 49).

6. Journal `subagent.started`/`subagent.completed` on the PARENT session with the parent `turnId`. `EventDraft.type` is a free-form string (src/core/journal.ts:5-10), and EventJournal.append re-reads the head each call (src/core/journal.ts:107), so tool-side appends interleave safely with the suspended parent turn; they will simply be absent from runTurn's `emitted` array and ignored by materializeMessages.

7. Propagate `context.signal` into the nested runTurn. Note the parent's terminal-event reconciliation already appends with `useTurnSignal = false` (agent.ts:432-438), so child cancellation still leaves a durable terminal record.

8. Return only the child's final `content` plus a bounded transcript digest. Output is already hard-bounded by `MAX_TOOL_OUTPUT_BYTES = 1_048_576` in `executeApproved` (src/tools/registry.ts:14, 136-138).

9. Approvals: pass the parent's ApprovalPolicy instance through unchanged so every child tool call is still individually reviewed. Do NOT couple this to a "one approval, not N" turn-scoped-grant scheme as a precondition — that is a separate change to the permission model and CANON.md 23's "grant every capability explicitly" sentence, and collapsing N child approvals into one must be argued on its own merits.

10. Add a MASTER_PROMPT_ACCEPTANCE.md row under section 3 once shipped, and correct the finding's evidence: the safety reviewer is not the only nested inference — createInferenceTransportContextSummarizer (src/core/context-compressor.ts:85+) is a second in-turn nested `transport.stream()` call, which is additional proof the browser does not prevent this.

## 4. git push, worktree create/remove, and snapshot import are implemented and human-reachable but are not exposed to the model, with no declaration that they exist

**Evidence.** src/git/client.ts implements `createWorktree` (137), `removeWorktree` (142), `importSnapshot` (152), `fetch` (156), `push` (161). src/tools/git-tools.ts exposes only: `git_inspect` actions `[capabilities, repositories, status, diff]` (line 14), `git_change` actions `[stage, unstage, commit, create_branch, switch_branch]` (line 49), and `git_remote` actions `[clone, fetch]` (line 122). Schema {repositoryId, worktreeId, remote, branch, expectedWorktreeVersion} with force omitted entirely, delegating to client.push. Do not claim it "always hits the approval broker": src/approvals/modes.ts auto-allows every non-read effect in full-access mode (exactly as terminal push already is), so say instead that it always carries an identity-effect / change-remote approval descriptor. Catch GitDomainError in the tool and return {ok:false, code, message} — src/git/errors.ts keeps `code` off the message and src/core/agent.ts:323 journals only error.message, so `push-outcome-unknown` would otherwise be lost. (2) WORKTREES — add create_worktree/remove_worktree to git_change (correct effect: operations.ts maps both to "write"/"change-local"), but note the schema change: GitCreateWorktreeRequest/GitRemoveWorktreeRequest (src/git/types.ts ~246-262) take `expectedRepositoryVersion`, while git_change currently requires `expectedWorktreeVersion` for every action (git-tools.ts:61), so the `required` list must become per-action and `path`/`expectedRepositoryVersion` must be added to properties. (3) LOG/SHOW is not a tool-layer-only edit — it needs a new method on BrowserGitAdapter (src/git/types.ts:288-310), implementations in MemoryGitAdapter (src/git/memory-adapter.ts), WorkspaceGitAdapter (src/git/workspace-adapter.ts, via isomorphic-git `log`/`readBlob`), a delegate in src/git/encrypted-workspace-adapter.ts, a client wrapper in src/git/client.ts, and a new entry in GIT_CAPABILITIES (src/git/types.ts:3) — note validateCapabilities (client.ts:224-234) forces every adapter to declare the new capability with a reason when unavailable. All of that is browser-feasible. (4) HONESTY — the manifest (src/core/operating-charter.ts installedToolSection) stays positive-only, so put any genuinely withheld capability as an explicit negative in the tool description (e.g. "force push is not offered from tools; use Source Control"), and reconcile with git_inspect {action:"capabilities"}, which already reports features.push/features.worktree availability and today contradicts the absent tool surface. (5) Update src/tools/airship-tools.test.ts:17-24, which asserts the exact tool-name set and per-tool effects.

## 5. read_file has no offset/limit and hard-fails on any file over the 1 MiB tool-output cap instead of returning a bounded window
`read-file-hard-fails-over-1mib` · kind **bug** · effort **small**

**Evidence.** src/tools/workspace-tools.ts:74-99: `read_file`'s schema is `{path}` only; it calls `workspace.read(path)` and returns the entire content. src/tools/registry.ts:14 `MAX_TOOL_OUTPUT_BYTES = 1_048_576` and lines 136-138 `throw new Error("Tool output exceeded ...")` — a throw, after execution, so the model gets a `tool.failed` event (src/core/agent.ts:365-374) with no partial content and no guidance. Meanwhile `WorkspacePort.readBounded(path, maxBytes)` exists (src/workspace/contracts.ts:14), is implemented in the Git-synchronized wrapper (src/tools/git-synchronized-workspace.ts:18-20), and is already used by search_text (workspace-tools.ts:212-213) and the UI (src/ui/app.tsx:5340) — read_file simply never calls it. Binary files are refused outright (workspace-tools.ts:90-96).

**Impact.** Any file over ~1 MB — a lockfile, a bundled asset, a long log, a large dataset the agent itself just generated — is completely unreadable, and the failure message points at an output budget rather than at a fix. Claude Code's Read takes offset/limit for exactly this reason; a 102k-LOC-class agent runtime cannot leave its most-used read primitive all-or-nothing.

**Fix.** In /Users/chrisk/chutes-jumpmaster/airship/src/tools/workspace-tools.ts (read_file, lines 74-99):

1. Extend the schema to {path, offsetBytes: {type:"integer", minimum:0}, maxBytes: {type:"integer", minimum:1, maximum:262144, default:262144}} (keep additionalProperties:false; the compiler at src/tools/schema.ts already handles integer/minimum/maximum/default). Optional startLine/lineCount can layer on top, but bytes must be the primitive the paging contract is built on so nextOffsetBytes is exact.

2. Do NOT gate the clamp on `workspace.readBounded`. That call is a trap on the production path: IndexedDbWorkspace (src/workspace/indexeddb.ts:33-95) implements no readBounded at all, and GitSynchronizedWorkspace.readBounded (src/tools/git-synchronized-workspace.ts:18-21) delegates to `this.workspace.read` when the inner port lacks it — so the method is *present* on the wired workspace (tool-bundle.ts:22) yet returns the entire file. read_file must always clamp the bytes it is about to return, using readBounded only as an optional read-side optimization for the offset 0 case.

3. Reuse the existing helper shape from src/ui/app.tsx:5335-5349 (encode to bytes, slice, decode) rather than reinventing it — better still, extract it into src/workspace/content-codec.ts and have app.tsx, MemoryWorkspace.readBounded and read_file share one implementation. Slice on a UTF-8 boundary and trim any trailing partial sequence instead of accepting the U+FFFD that MemoryWorkspace.readBounded currently produces at split points (src/workspace/memory.ts:24), then report the *post-trim* byte count so nextOffsetBytes = offsetBytes + returnedBytes resumes exactly.

4. Always return metadata {path, revision, size, offsetBytes, returnedBytes, truncated, nextOffsetBytes} so paging is mechanical, and mention the window in the tool description so the model knows the window exists. Leave the binary refusal at lines 90-96 as is.

5. Optionally add a real readBounded to IndexedDbWorkspace so large-file reads do not have to materialize the whole string first — a memory win, not a correctness one, since step 2 makes read_file safe either way.

On src/tools/registry.ts:136-138, do NOT blanket-convert the throw into a truncated success. list_files, stat_path and search_text all emit JSON as content; silently clamping their bytes would hand the model malformed JSON that looks authoritative. Keep the throw as a backstop for tools that overrun, and instead (a) make the message actionable ("read_file returns a window; re-call with offsetBytes/maxBytes") and (b) have each potentially-large producer clamp and declare its own truncation, which is what the search_text truncated-metadata pattern already does.

## 6. The prompt manifest is a positive list only — the model gets no declaration of what is deliberately absent, and no schemas in-prompt
`no-negative-capability-declaration` · kind **clunky** · effort **small**

**Evidence.** src/core/operating-charter.ts:134-139 `installedToolSection` emits `- <name> [<effect>]: <description truncated to 512>` and nothing else — no input schemas (those travel separately as function-calling `parameters`, src/inference/providers/browser-cloud.ts:697/714, so this is a defensible split). The manifest is pinned once at session creation from `runtime.tools.definitions()` (src/ui/app.tsx:4854, 4876) and is immutable thereafter (src/core/agent.ts:90-95 rejects any drift). The "exists but not installed" distinction is real only for execution runtimes: src/execution/runtime-registry.ts:11 defines states ready/installable/activating/failed/unavailable, OPTIONAL_CAPABILITIES (line 84-128) ships python-pyodide `installable`, node-webcontainer `installable`, wasix `unavailable` with a detailed NO-GO reason (line 113), and the charter (line 15) teaches the model exactly how to read those three words. There is no equivalent for tool-level absences.

**Impact.** For runtimes the design is genuinely excellent. For tools it is silence: the model cannot tell that git push exists but is human-only (finding 6), that no web search exists at all (finding 11), or that sub-agents were never built (finding 5) — it just sees absence and must guess. The charter's instruction to "check the current tool manifest" cannot resolve a distinction the manifest does not encode.

**Fix.** Narrow the section to the bounded, code-derivable set: Airship capabilities that another surface in this same build demonstrably has but the agent tool set withholds. Concretely that set is exactly {push, worktree-create, worktree-remove} — src/git/workspace-adapter.ts:1082-1085 reports push and worktree as available and src/ui/sources-view.tsx:238,244,249 plus src/git/terminal-commands.ts:264 exercise them, while src/tools/git-tools.ts:49,120 exposes no such action. Add an `[Airship declared capability boundary]` section built in src/core/operating-charter.ts the same byte-stable way as installedToolSection (line 134), composed from a new exported constant of `{ id, reason }` entries, e.g. `- git-push: the Git adapter reports push and worktree as available, but no installed tool exposes them in this build; they are reserved to the human Source Control and terminal surfaces`. Do NOT add a host-bash entry: charter line 15 already says "WebContainer exposes conditional Node and jsh, not host Bash" and "Never claim host processes, native files, Docker, SSH, or a language toolchain", and runtime-registry.ts:113 repeats it in the runtime report. For web-search, phrase it manifest-relative rather than as a claim about the world ("no search tool is present in the manifest above; use fetch_url against a known URL, or import_github_repository for public repos"), so a host-registered additionalTool cannot turn the line into a lie. Because the composer only receives {name, description, effect}, the anti-rot guarantee must be a test, not runtime derivation: add a case in src/core/operating-charter.test.ts (and/or src/tools/git-tools tests) that reads the git_change/git_remote action enums and fails if a boundary entry names an action that has become reachable, or if an available GitAdapterCapabilities feature has no tool and no boundary entry. Bump AIRSHIP_CORE_CHARTER_VERSION 6->7 (line 8) only if you also add the one charter sentence teaching the model to read the new section — that change requires updating the pinned digest assertion at src/core/operating-charter.test.ts:11-15 ("sha256:WziI7-LpWZnLkG-yzwS-K0SQQiy3G1LyfKG1a3tMc7E"); existing session pins stay byte-identical either way.
