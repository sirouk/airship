# Real Git and the virtual workspace

**Verdict.** The Git core is genuinely real, not simulated: `src/git/workspace-adapter.ts` drives stock `isomorphic-git@1.38.10` over a Node-shaped FS projection (`src/git/workspace-fs.ts`) onto the one authoritative `WorkspacePort`, and I verified in a live run that `/workspace/.git/HEAD`, `/workspace/.git/refs/heads/main`, zlib loose objects under `.git/objects/`, and a real binary `DIRC` index exist as bytes, with 40-hex SHA-1 commit oids. Linked worktrees are conventional (`.git` pointer file, `.git/worktrees/<adminId>/{HEAD,index,commondir,gitdir}`, shared object/ref namespace). The only simulated Git in the repo is `src/git/memory-adapter.ts` (Map-based commit graph, sha256 pseudo-oids) — it is never instantiated by the app, but it is still exported into the shipped capability pack via `src/deferred-capabilities.ts:13`. Where the dimension breaks down is everything around that core. (a) The verb set is roughly `git status/diff/add/reset/commit/branch/switch/clone/fetch/push` and nothing else — there is no `log`, `show`, `blame`, `tag`, `stash`, `merge`, `rebase`, `cherry-pick`, `revert`, `reset --hard`/discard, or `remote add` anywhere in the adapter, terminal bridge, UI, or agent tools, even though isomorphic-git ships `log`, `merge`, `cherryPick`, `stash`, `tag`, `listTags`, `fastForward`, `abortMerge`, `addRemote`, and `isIgnored` today. (b) The deployed Content-Security-Policy `connect-src` (index.html:13, public/_headers:2) allowlists `api.github.com` and `raw.githubusercontent.com` but no Git host at all — so clone/fetch/push against github.com/gitlab.com are blocked by Airship's own page policy before CORS is ever consulted, while `capabilities.features.clone/fetch/push` all report `available: true` and the failure message blames the remote's CORS policy. That is the one place in this dimension where the app states something untrue. (c) I found and root-caused a live correctness bug: `WorkspaceFsStat` reports `ino/dev/uid/gid = 0` and `ctimeMs = mtimeMs`, and isomorphic-git's `compareStats` only compares *whole-second* mtime, so any same-byte-length edit inside the same wall-clock second is completely invisible to `git status`/`diff`/`stage`/`commit` — I reproduced it and proved a ~6-line fix. (d) Performance is the deepest problem: a single `status()` on a 2,400-file repo took 2.5 s with 205 `list()` and 5,429 `read()` calls against the *fastest possible* backend (in-page memory); on the durable path every one of those calls re-downloads, AES-GCM-decrypts and SHA-256-verifies the entire workspace manifest (`src/vault/encrypted-workspace.ts:193-201`), and every write re-encrypts and CAS-uploads the whole manifest. There is no OPFS tier for the workspace FS and no directory index. 10k files is not slow, it is unusable. `.gitignore` is correctly honored (I verified it empirically), but it has zero tests and the error text for adding an ignored file is wrong.

## 1. Clone/fetch/push are advertised available but the app's own CSP forbids reaching any Git host, and the error blames the remote
`csp-blocks-every-git-remote` · kind **dishonest-claim** · effort **medium**

**Evidence.** index.html:13 and public/_headers:2 set `connect-src 'self' https://api.chutes.ai https://llm.chutes.ai https://api.openai.com https://api.anthropic.com https://api.x.ai http://localhost:11434 ... https://api.github.com https://raw.githubusercontent.com ...` — there is no `https://github.com`, no `https://gitlab.com`, no wildcard. Git Smart HTTP needs `https://github.com/<o>/<r>.git/info/refs`, a different origin from `api.github.com`. Meanwhile src/git/workspace-adapter.ts:1081-1086 hardcodes `clone/fetch/push: { available: true }`, and src/git/workspace-adapter.ts:1162-1168 `directHttpError()` renders 'The remote must grant this Airship browser origin CORS for Git Smart HTTP.' A CSP block surfaces as the same opaque `TypeError: Failed to fetch`, so the user is told the remote refused CORS when in fact the request never left the page. src/git/workspace-adapter.test.ts:327-335 asserts exactly that CORS wording, and the only 'successful push' evidence (line 342) is `vi.spyOn(git, 'push').mockImplementation` — no real remote has ever been contacted. No doc connects CSP to Git: grep for 'connect-src' across docs/ returns only S3/Vault docs; docs/BROWSER_GIT.md:124-148 'Remote contract' attributes failure solely to the remote. src/ui/sources-view.tsx:353-359 also has no clone form at all — the empty state says 'install an adapter with a real browser-safe clone path' while the installed adapter already claims clone availability.

**Impact.** A user who pastes a GitHub URL into the terminal (`git clone https://github.com/...`) gets a confident, specific, and false diagnosis: that GitHub refused CORS to their browser. They will go configure CORS on a server they don't control, or conclude Airship is broken. The honest snapshot importer is the only working path, and the UI never routes them to it from the clone failure. Push has never been proven against a real remote at all.

**Fix.** (1) src/git/validation.ts: add `GIT_REMOTE_CONNECT_ORIGINS` (exact origins, no wildcards) and `assertRemoteOriginPermitted(url)`; leave validateRemoteUrl (line 117) intact so parseRegistry's existing records are not retroactively invalidated. Pin the constant to the shipped policy by extending scripts/check-static-security.mjs (it already extracts connect-src from index.html:13 and public/_headers:2 at lines 6-26) to assert GIT_REMOTE_CONNECT_ORIGINS is a subset of that list — one gate, no drift.

(2) src/git/workspace-adapter.ts: call the gate at the top of clone() (line 491, before git.clone at 501), fetch() (530, before 536), and push() (545, before 557), throwing a new GitDomainError("remote-origin-not-permitted", ...) that names Airship's own Content-Security-Policy, lists the permitted origins, and points at the snapshot importer. Do NOT make capabilities() (1064) return available:false per-remote — it receives no URL and is a frozen snapshot built at adapter open. Instead add `permittedOrigins: readonly string[]` to the remote capability block in src/git/types.ts:37-42, populate it at workspace-adapter.ts:1075-1080, and rewrite the detail string (currently "The remote must grant this browser origin CORS; Airship never inserts a proxy.") to state that this build's CSP permits Git Smart HTTP only to those origins and that github.com/gitlab.com are not among them.

(3) src/git/workspace-adapter.ts:1162 directHttpError(): because (2) runs first, any surviving "TypeError: Failed to fetch" is genuinely remote-side, so the existing CORS wording becomes true by construction — keep it and add the permitted-origin fact. Drop the auditor's `fetch(url,{mode:'no-cors'})` sentinel: it rejects identically on DNS/offline failure so it cannot distinguish, and it emits an unwanted cross-origin request. A `securitypolicyviolation` listener is available (adapter is on the main thread per src/ui/app.tsx:1487) but is only a belt-and-braces secondary signal. Update src/git/workspace-adapter.test.ts:327-335 to cover the new blocked-origin error alongside the CORS case.

(4) Surfaces: src/git/terminal-commands.ts clone() (279-296) has no capability pre-flight, unlike pushRemote() at 256 — add the origin gate there so the user is told before the approval prompt, and extend the help text at 389. src/ui/sources-view.tsx:353-359 should render capabilities.remote.permittedOrigins and route the user up to the snapshot importer that already works.

(5) docs/BROWSER_GIT.md "Remote contract" (~124-148): add a CSP subsection stating plainly that this build's connect-src cannot reach github.com Smart HTTP, that GitHub grants no CORS on git endpoints regardless, and that the snapshot importer (api.github.com + raw.githubusercontent.com, both already in the CSP) is the supported public-GitHub path. Mirror the existing operator-facing pattern in docs/VAULT_COMPOSITION.md:268-278.

(6) The corsProxy piece is optional and contract-sensitive, not required to close the dishonesty. isomorphic-git does expose it (node_modules/isomorphic-git/index.d.ts:1121,1163) and vite.config.ts applyLocalDevelopmentPolicy is the natural build-time injection point, but shipping it means rewriting four standing "Airship never inserts a proxy" claims (src/git/workspace-adapter.ts:1079 and 1166, src/tools/git-tools.ts:115, src/ui/sources-view.tsx:356) plus the receipts and docs. Ship (1)-(5) first; treat the proxy as a separate reviewed decision.

## 2. git status silently misses any same-size edit made within the same wall-clock second
`stat-cache-hides-same-second-edits` · kind **bug** · effort **small**

**Evidence.** src/git/workspace-fs.ts:235-260 `WorkspaceFsStat` hardcodes `uid = 0; gid = 0; dev = 0; ino = 0` and sets `ctimeMs = mtimeMs = Date.parse(file.updatedAt)`. isomorphic-git's `compareStats` (node_modules/isomorphic-git/index.js:942-955) declares a file stale only if `mode`, `mtimeSeconds`, `ctimeSeconds`, `uid`, `gid`, `ino`, or `size` differ — nanoseconds are computed by `normalizeStats` but never compared. `GitWalkerFs.oid()` (index.js:4720-4735) therefore reuses the staged oid without hashing content. I reproduced this: a repo seeded with `a.txt = "tracked1\n"` then rewritten to `"MUTATED1\n"` (same 9 bytes) produced `status == []` both immediately and after a 40 ms delay, while `workspace.read()` confirmed the new content was committed to the workspace. I then patched `stat()` to pass `ino = fnv1a(file.revision)` (the workspace revision is a fresh randomUuid per write, src/workspace/memory.ts:48) and the same test produced `[{path:"a.txt", worktree:{kind:"modified"}}]`; all 47 existing tests in src/git, src/workspace and src/tools/git-synchronized-workspace.test.ts still passed. No existing test covers this case.

**Impact.** Silent data loss in the core loop. An agent or editor rewrites a file to a same-length value (a version bump, a boolean flip, a renamed identifier of equal length, a rewritten line) and Airship reports 'working tree clean'. The change cannot be staged (`stage()` at src/git/workspace-adapter.ts:306 throws 'has no unstaged change'), cannot be diffed, and is never committed — while the file on disk is different from HEAD. Sub-second writes are the norm for agent tool loops and editor autosave.

**Fix.** In src/git/workspace-fs.ts:

1. Make `ino` a constructor parameter with a 0 default so the directory branch at line 177 (`new WorkspaceFsStat("directory", 0, 0)`) is untouched:
   - line 245: `readonly ino = 0;` -> `readonly ino: number;`
   - line 247: `constructor(private readonly kind: "file" | "directory", size: number, modified: number, ino = 0)` and assign `this.ino = ino;` in the body.
2. line 176: `if (file) return new WorkspaceFsStat("file", decodeWorkspaceBytes(file.content).byteLength, Date.parse(file.updatedAt), revisionInode(file.revision));`
3. Add a module-level helper near `fsPath` (must stay <= 2^32-1 because GitIndex._entryToBuffer writes ino with writeUInt32BE):

function revisionInode(revision: string): number {
  let hash = 0x811c9dc5;
  for (let index = 0; index < revision.length; index += 1) {
    hash ^= revision.charCodeAt(index);
    hash = Math.imul(hash, 0x01000193);
  }
  return hash >>> 0;
}

Why the workspace revision is the right identity: MemoryWorkspace.write (src/workspace/memory.ts:48), IndexedDbWorkspace (src/workspace/indexeddb.ts:78) and EncryptedObjectWorkspace.write (src/vault/encrypted-workspace.ts:120) each mint a fresh revision on every write, and WorkspaceGitFileSystem.writeFile short-circuits identical content at line 113, so the ino changes exactly when bytes may have changed. A no-op rewrite by another writer costs one re-hash, never a wrong answer.

Regression test to add in src/git/workspace-adapter.test.ts: open a WorkspaceGitAdapter seeded with { "a.txt": "tracked1\n" }, assert status is [], then `await workspace.write("<root>/a.txt", "MUTATED1\n", { expectedRevision })` with no delay, and assert status is [{ path: "a.txt", index: null, worktree: { kind: "modified" } }]. Add the same assertion through `client.writeWorkingFile({ path: "a.txt", content: "MUTATED1\n", ... })`, and (because the miss is permanent, not merely sub-second) re-read status after an awaited tick to prove it stays "modified". A durable-side case in src/git/encrypted-workspace-adapter.test.ts is worth adding too, since the encrypted port has the same hole.

Bonus the fix also closes: the same ino now disambiguates `.git/index` itself in GitIndexManager's isIndexStale cache (node_modules/isomorphic-git/index.js:1041), which had the identical same-second/same-size reuse hole.

## 3. The documented import→review→stage→commit workflow is impossible for any repo over 512 files
`stage-all-impossible-above-512-paths` · kind **bug** · effort **small**

**Evidence.** src/git/validation.ts:12 sets `maxPathsPerOperation: 512` and `validatePathList` (lines 62-70) throws `Select between 1 and 512 paths.` Every stage/unstage passes through it via src/git/operations.ts:31-37. src/git/terminal-commands.ts:133-141 builds the path list from the full status for `git add -A`/`git add .` with no chunking; src/ui/sources-view.tsx:200-206 does the same for 'Stage selected'. src/tools/repository-import.ts:3 defaults `maxFiles` to 2000, and src/git/workspace-adapter.ts:631-653 `initializeEmptyRepository()` deliberately commits an *empty* tree so every imported file is untracked — so a freshly imported repo has up to 2000 unstaged paths on day one. docs/BROWSER_GIT.md:82-90 tells the operator to 'review, stage, and commit them'. I proved the failure: a 600-change worktree + `git add -A` rejects with `Select between 1 and 512 paths.` Separately, src/tools/git-tools.ts:53 advertises `paths: { maxItems: 2048 }` to the model, so the agent is schema-invited to send four times the runtime limit.

**Impact.** Import any real repository (React, a monorepo package, anything over 512 files) and you can never commit it. Both the UI button and the terminal command hard-fail with a validation error that reads like a user mistake. The agent hits the same wall with a tool schema that promised 2048.

**Fix.** Keep 512 as the per-adapter-call bound and add a larger request-level bound plus chunking; the throw must be relaxed at the approval boundary, not just in the client.

1. src/git/validation.ts — keep GIT_LIMITS.maxPathsPerOperation = 512 and add e.g. maxPathsPerRequest = 4_096 (>= the importer's 2,000-file default). Give validatePathList an optional limit parameter defaulting to maxPathsPerOperation.

2. src/git/operations.ts:35 — validate stage/unstage request paths against maxPathsPerRequest. This is mandatory: describeGitOperation (operations.ts:100-101) re-runs normalizeGitOperation, and it is called before any client call from terminal-commands.ts:310 (approve) and sources-view.tsx:152 (runMutation), so the current failure happens at approval time. Chunking only in client.ts, as originally proposed, would change nothing.

3. src/git/client.ts:112-120 — in stage()/unstage(), split the normalized paths into <=512-path chunks and execute them sequentially inside a single this.mutate("stage", ...) scope (worktreeMutation currently takes a one-shot executor; widen it or inline the mutate call). Chain each chunk's expectedWorktreeVersion from the previous chunk's result.worktree.version, which the returned GitMutationResult already carries, so an interleaved foreign write still fails the fence (fail-closed). Return the final GitMutationResult with the union of changedPaths. If a later chunk throws, rethrow an error that states how many paths were actually staged — partial staging is a durable outcome and must not be reported as a rollback.

4. src/git/workspace-adapter.ts:303,318 and src/git/memory-adapter.ts:224,237 — leave these on the 512 default so the per-call safety bound is still enforced at the adapter.

5. src/tools/git-tools.ts:53 — set maxItems to the new request cap (or 512 if you keep the per-call cap as the contract) so the model-facing schema matches runtime.

6. Do NOT add the git.add({ filepath: '.' }) stageAll fast path: isomorphic-git addToIndex throws NotFoundError on deleted paths and only walks existing worktree entries, so it would not stage deletions (wrong for `git add -A`) and would stage paths outside the reviewed set, bypassing the adapter's per-path `status.get(path)?.worktree` review check.

7. Optional: surface the chunk count in the approval summary at operations.ts:107-110; the path count itself is already accurate. Add a regression test alongside src/git/terminal-commands.test.ts asserting that `git add -A` over a 600-change worktree stages all 600 paths.

## 4. The workspace FS has no directory index and no OPFS tier; one status on 2.4k files costs 5,600 workspace round trips, each a full manifest decrypt on the durable path
`workspace-fs-collapses-at-scale` · kind **clunky** · effort **very-large**

**Evidence.** Measured (in-memory backend, Node, M-series): 100 files → status 18 ms; 400 → 62 ms; 1,200 → 412 ms; 2,400 → 2,479 ms with 205 `list()` calls scanning 1,026,640 entries and 5,429 `read()` calls. Cause chain: `WorkspaceGitFileSystem.readdir` (src/git/workspace-fs.ts:133-154) has no directory index and calls `workspace.list(prefix)`; `stat` (line 173-179) calls `workspace.read` and decodes the whole file just to get `byteLength`; `WorkspaceGitAdapter.repositoryRevisions` (line 786-796) lists every worktree on every `issueVersion`. Every `WorkspacePort.list` is O(total files): src/workspace/memory.ts:28-34 filters all values, src/workspace/indexeddb.ts:49-60 does `getAll()` of the entire store *including content* then filters in JS. The durable production path is worse: src/vault/encrypted-workspace.ts `read` (63-70), `list` (90-98), `write` (100-157) and `remove` (159-168) each call `loadManifest()` → `store.get(rootCloudKey)` → full AES-GCM decrypt + SHA-256 verify of a manifest holding up to `MAX_FILES = 100_000` entries, and every write re-seals and CAS-uploads that whole manifest. src/storage/caching-object-store.ts:19-20 documents that mutable heads are deliberately never cached, so each of those is a provider round trip. No OPFS anywhere in src/workspace or src/git — grep for OPFS in src/ hits only src/storage/client-ciphertext-cache.ts and src/vault/local-device.ts. docs/BROWSER_GIT.md:120-122 acknowledges 'a future worker/OPFS tier' but only for cross-tab locking, not performance.

**Impact.** At 10k files a single `git status` extrapolates to tens of seconds in page memory and to thousands of network round trips against a Google Drive vault, each re-downloading and decrypting a ~1.4 MB manifest. Cloning or importing anything the size of a real project makes Source Control, the editor tree, and every agent turn that touches Git unresponsive. The 2,000-file import default is already past the comfortable edge (a 600-file seed took 21 s in my run).

**Fix.** Three layers, corrected for what the code actually permits.

(1) Directory + metadata index in WorkspaceGitFileSystem (src/git/workspace-fs.ts). Build a revision-fenced Map<dir, Set<child>> plus Map<path, {revision, size, updatedAt}> from one workspace.list(root) on first touch, invalidate per-path in writeFile/unlink/removeTree, and serve readdir/hasDirectory/exists from it. Caveat the auditor missed: WorkspaceEntry.size is the byte length of the *encoded* content string, not the decoded file size — binary files cross the boundary as the base64 "airship-git-binary-v1:" envelope (src/workspace/content-codec.ts:10-22), so entry.size is ~4/3 too large for them and cannot be handed to isomorphic-git's stat as-is (it silently defeats the index stat fast path). This half is now done: WorkspaceEntry carries an optional decoded `contentByteLength` beside `size`, written by all three ports and read through `workspaceEntryByteLength` (src/workspace/contracts.ts), and the encrypted manifest keeps it optional so pre-existing manifests still parse. Stat must read it through that accessor — entries sealed before the field existed still fall back to the envelope length, so a stat fast path that must not be wrong for legacy binaries has to fall back to a read for envelope-encoded entries.

(2) Manifest handling in EncryptedObjectWorkspace (src/vault/encrypted-workspace.ts). Two separable wins, only the first of which is free: (a) memoize the decrypted manifest keyed by the head record's ETag while still performing the provider GET — this preserves the "provider reads remain authoritative for mutable heads" invariant documented at src/storage/caching-object-store.ts:18-21 verbatim and still removes the dominant local cost (my 200-file durable run spent 4.6 s with zero network, i.e. it is AES-GCM + SHA-256 + JSON parse + per-entry validation, not I/O); (b) to remove the round trips themselves, note that ObjectStore (src/storage/object-store.ts:49-61) has no conditional GET — there is no ifNoneMatch parameter on get() — so "revalidate with a conditional get" is not implementable without extending that interface across the memory/direct/s3/google-drive/local-device adapters. The honest alternative that needs no interface change is a single manifest snapshot per adapter operation: WorkspaceGitAdapter already reads the head 525 times inside one status with no transaction spanning them, so one snapshot per operation gives up no consistency guarantee that exists today, and writes still fail closed through compareAndSwap. Add the write-coalescing window on top so a commit that writes N loose objects performs one manifest CAS instead of N.

(3) The OPFS tier must NOT be wired as the auditor proposed. A plaintext OpfsWorkspace implementing WorkspacePort cannot be the ephemeral backend — Ephemeral is user-facing-advertised as "page memory only; nothing synced" (src/ui/platform-shell.tsx:305, src/ui/vault-view.tsx:87/97, src/ui/durability-indicator.tsx:10) and the ephemeral runtime is deliberately MemoryWorkspace (src/ui/app.tsx:1459, :2978); persisting it to disk would falsify that label. Nor can it be the local-device backend — that tier is advertised as "Encrypted Local Device", is constructed as EncryptedObjectWorkspace over the OPFS store at src/vault/local-device.ts:116, and WorkspaceGitAdapter derives its durable capability from the ClientEncryptedWorkspacePort marker (src/git/workspace-adapter.ts:167-169), so a plaintext port would both leak plaintext to disk and silently downgrade the reported backend. Also note OPFS is already in use for local-device ciphertext (src/storage/local-device-object-store.ts, OpfsLocalDeviceBackend with createSyncAccessHandle), so the local-device path already gets OPFS and still pays the 525-manifest-loads-per-status cost — layers (1) and (2) are what fix it. If an OPFS workspace tier is still wanted, build it as either an explicitly labelled new durability option with its own honest UI string ("OPFS - this device, unencrypted") or as a client-encrypted OPFS-backed port that keeps the encryptionBoundary marker; the dedicated-worker + FileSystemSyncAccessHandle pattern to copy is src/storage/client-ciphertext-cache.ts:337-460. The unused GitStorageBackend "opfs" value (src/git/types.ts:18) may then be declared, and src/ui/sources-view.tsx:631 already has its label.

## 5. There is no git log, show, or blame — the commit graph is written but never readable
`no-history-anywhere` · kind **absent** · effort **medium**

**Evidence.** grep for `git.log|readCommit|readTree|listTags` across src/ (excluding tests) returns zero production hits; the only `git.log` call in the repo is an assertion in src/git/workspace-adapter.test.ts:58. `src/git/types.ts:3-14 GIT_CAPABILITIES` has no history capability. src/git/terminal-commands.ts:63-97 dispatches only status/diff/add/reset/restore/commit/branch/switch/checkout/fetch/push/remote/rev-parse, and `help()` at 378-393 lists exactly that set. src/tools/git-tools.ts:14 gives the agent `action: ["capabilities","repositories","status","diff"]` only. src/ui/sources-view.tsx has no history panel (grep for 'history' returns only the import contract copy at line 330). isomorphic-git already exports `log`, `readCommit`, `readTree`, `readBlob`, `findMergeBase`, `listTags` and `walk`.

**Impact.** A developer cannot answer 'what changed and why' inside Airship. No commit list, no per-commit diff, no file history, no blame, no way to find the commit that introduced a line. The agent literally cannot read the repository's history to reason about a change, which guts the 'Claude Code-level tool power' claim for any task that starts with 'why is this code like this'.

**Fix.** Same shape, three corrections. (a) Path history needs no git.walk: isomorphic-git 1.38.10 (node_modules/isomorphic-git/index.d.ts:2196) already accepts `filepath` plus `follow`, `since`, `depth` on `git.log`, so src/git/workspace-adapter.ts should call `git.log({fs: this.fs.client, dir, gitdir, ref, depth, filepath})` directly; bound `depth` (GIT_LIMITS in src/git/validation.ts) since `follow` rename detection is expensive. (b) Adding "history" to GIT_CAPABILITIES in src/git/types.ts:3-14 is a three-adapter change, not one: validateCapabilities in src/git/client.ts:224-233 rejects any adapter that omits a capability or marks it unavailable without a reason, so the features literals at src/git/workspace-adapter.ts:1081-1086, src/git/encrypted-workspace-adapter.ts:98, and src/git/memory-adapter.ts:102-113 must all declare it. MemoryGitAdapter can declare it available and honest — it already keeps a parent-linked commit chain (memory-adapter.ts:70 `commits: Map<string, MemoryCommit>`, written at :261) — and can render per-commit diffs through its own renderPatch at memory-adapter.ts:757. (c) The read path must be added to the adapter interface (`log`/`show` beside `commit()` at src/git/types.ts:~301) and passed through BrowserGitClient with `this.require("history")` and cloneAndFreeze, matching the existing status()/diff() waist; `show` uses `git.readCommit` plus a commit-vs-parent tree walk rendered by the module-private renderPatch at src/git/workspace-adapter.ts:1026. Then surface it: `git log [-n N] [--oneline] [-- path]` and `git show <oid>` in src/git/terminal-commands.ts (dispatch at 63-97, and the help() text at 378-393 must be updated or the bridge lies about its command set), "log"/"show" in the git_inspect enum at src/tools/git-tools.ts:14, and a History tab in src/ui/sources-view.tsx gated on `client.capabilities.features.history.available` with the reason rendered when false, mirroring the fetch/push gating at lines 462-465.

## 6. merge, rebase, cherry-pick, revert, stash, tag, and discard-changes are all absent although isomorphic-git ships most of them
`no-merge-stash-tag-revert-discard` · kind **absent** · effort **large**

**Evidence.** src/git/types.ts:3-14 `GIT_CAPABILITIES` = status, diff, stage, commit, branch, worktree, snapshot-import, clone, fetch, push — nothing else. `BrowserGitAdapter` (src/git/types.ts:288-310) has no merge/stash/tag/reset method. src/git/terminal-commands.ts:95-97 rejects everything outside its switch with 'Unsupported shared Git command'. `git reset` at line 71 is aliased to *unstage only*; there is no `reset --hard`, no `git checkout -- <file>`, and grep for 'discard' in src/ui/sources-view.tsx returns nothing — so a bad edit cannot be reverted through Git at all. `switchBranch` (src/git/workspace-adapter.ts:357-367) additionally refuses any switch with a dirty worktree, which real Git permits. node_modules/isomorphic-git/index.d.ts exports `merge`, `cherryPick`, `stash`, `tag`, `annotatedTag`, `listTags`, `deleteTag`, `abortMerge`, `fastForward`, `findMergeBase`, `renameBranch`, `deleteBranch`, `checkout` (with `force`) and `resetIndex` today.

**Impact.** Branching is write-only: you can create and switch branches but never integrate them. No way to pull in a colleague's branch, no way to park work in progress, no way to tag a release, no way to undo a bad working-tree edit or a bad commit. For a runtime that sells 'real Git', this is the difference between a commit recorder and a development tool.

**Fix.** Add `merge`, `stash`, `tag`, `restore` to GIT_CAPABILITIES (src/git/types.ts:3-14) plus request types, BrowserGitAdapter methods (types.ts:288-310) and new GitOperation members (types.ts:254-266). In initializeSeed (workspace-adapter.ts:598, add loop at :620), collect paths git.add skipped and either pass force: true or surface them as a diagnostic. This is higher-impact than the finding states: src/ui/app.tsx:5271 existingWorkspaceFallbackSeed forwards every user Vault file as files+workingFiles during a one-time real-Git migration, so a user's own .gitignore silently drops their files from Git.
